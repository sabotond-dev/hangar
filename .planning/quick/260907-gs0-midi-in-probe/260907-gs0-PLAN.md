<verified_facts>
Everything below was checked at plan time. Re-read the two firmware citations yourself before
writing the prose that leans on them; do not take them from this block alone.

**Part A - plain host MIDI.** `zona-docs/docs/ZONA_REFERENCE.md:1255-1312` (read-only). Assign
`self.midirx_cb = function(s, h, v)` directly in Setup - `midirx_register` / `gmrr` is broken on a
touch element. `_decode_process` loops all elements with no type test, so the touch element is
included. `h[1]` is INSTR: **13** for MIDI arriving from the host, **14** for the module’s own
outgoing echo. `v[1]` channel, `v[2]` command, `v[3]` parameter 1, `v[4]` parameter 2.

Host MIDI arrives with **no configuration at all**. `grid-fw/common/src/lua/init.lua:10-19` sets
`grxm(rx_type.MIDIVOICE, rx_feat.FORWARD | rx_feat.HANDLE_EXTERNAL)` at every VM start. The
audition’s row 11 suggests `grxm(0,2)`, which is numerically that exact default - so it is
redundant, and the Part A script omits it. Say that in the document; a reader who followed row 11
literally would think the call was load-bearing.

**Part B - MIDI clock.** Clock and transport are off by default: the same `init.lua` block sets
`grxm(rx_type.MIDIRTM, 0)`. Enable with
`grxm(rx_type.MIDIRTM, rx_feat.FORWARD | rx_feat.HANDLE_EXTERNAL)`, numerically **`grxm(2,3)`**
(`rx_type = { MIDIVOICE = 0, MIDISYSEX = 1, MIDIRTM = 2, EVENTVIEW = 3 }`,
`rx_feat = { FORWARD = 0x01, HANDLE_EXTERNAL = 0x02, HANDLE_INTERNAL = 0x04 }`, both at
`init.lua:10-11`). Give **both spellings**; the named one is what a reader can look up, the numeric
one is what fits a budget.

The callback shape is verified at `grid-fw/common/src/lua/decode.lua:43-44` - confirm these two
lines yourself:

```lua
pass_rtm = function(el, x)
  if el.rtmrx_cb then
    el:rtmrx_cb({ x[1], x[2], x[3] }, x[4])
  end
end
```

So `self.rtmrx_cb = function(s, h, b)` takes a header triple and **one** byte, not a table: **248**
clock, **250** start, **252** stop. 24 clocks to the quarter note, so **12 clocks is an eighth**.

`gts` (timer_source) is dead on ZONA, so `rtmrx_cb` is the only clock-sync route that exists
(`.planning/research/ZONA-CAPABILITIES.md:940-942`). That is why a "no" on Part B closes the whole
clock-locked family rather than sending it down another road.

**LED primitives.** `glag(0, i)` is the address of index `i`; column is `i % 9`, row is `i // 9`
(`ZONA_REFERENCE.md:834`). `gln` / `gld` / `glx` are the min / mid / max colour stops and
`glp(led, layer, phase)` sets the phase. `glt` is the animation run switch and neither script needs
it: a `glp` alone changes the LED immediately, it just does not advance. The canonical opener at
`ZONA_REFERENCE.md:98` is the model for the loop.

**The software-side finding, all three halves verified.** `grxm` at `src/lib/sim/lua-host.ts:575`
records a mode and nothing else; worse, the binding at `src/lib/sim/lua-host.ts:399` is
`g.set("grxm", (_slot, mode) => this.grxm(mode))`, which **discards the slot argument entirely** -
the host cannot tell MIDIVOICE from MIDIRTM even in the value it records. `midirx_cb` and
`rtmrx_cb` appear nowhere in `src/` except one sentence of prose at
`src/lib/catalog/audition.spec.ts:248`. HANGAR’s simulator therefore has no inbound-MIDI path of any
kind, and a hardware yes is necessary but not sufficient: a synthetic clock (and a synthetic MIDI
source) has to exist in the Lua host before such a card could animate on the site.
</verified_facts>

<interfaces>
**The two scripts.** Both were syntax-checked at plan time with the pinned minifier
(`GridScript.checkSyntax` true, `GridScript.compressScript` a fixed point - the stored text and the
compressed text are identical). Use them verbatim; the measured lengths are the numbers the document
must state.

**Part A, 264 characters, budget 908:**

```lua
--[[@cb]]for i=0,80 do local h=glag(0,i)gln(h,1,0,8,3)gld(h,1,0,120,40)glx(h,1,214,255,78)glp(h,1,0)end self.midirx_cb=function(s,h,v)if h[1]~=13 or v[2]~=176 or v[3]~=16 then return end local c=v[4]*8//127 for i=0,80 do glp(glag(0,i),1,i%9<=c and 255 or 0)end end
```

The loop gives every one of the 81 LEDs a three-stop ramp on layer 1 and parks it at phase 0, so the
pad sits at a dim green that is **visibly not black**. That is deliberate and worth a sentence: a
dark pad cannot be told apart from a script that never ran, and this probe’s whole value is that its
two outcomes are distinguishable. The callback keeps only host traffic (`h[1]~=13` drops the
module’s own echo at 14), only control change (`v[2]~=176`), only controller 16 (`v[3]~=16`), and
lights columns 0 through `v[4]*8//127` - one column at the bottom of the range, all nine at the top.

**It deliberately does not filter on channel**, unlike the reference’s own example at
`ZONA_REFERENCE.md:1284-1290`, which tests `v[1]~=0`. A DAW transmitting on channel 5 would
otherwise produce a false negative on the one question the whole next phase is waiting on. Say so in
the document, in those terms.

**Part B, 328 characters, budget 908:**

```lua
--[[@cb]]for i=0,80 do local h=glag(0,i)gln(h,1,0,8,3)gld(h,1,0,120,40)glx(h,1,214,255,78)glp(h,1,0)end grxm(2,3)local n=0 local w=-1 self.rtmrx_cb=function(s,h,b)if b==250 or b==252 then n=0 w=-1 end if b~=248 then return end n=n+1 local p=n%12<4 and 255 or 0 if p==w then return end w=p for i=0,80 do glp(glag(0,i),1,p)end end
```

Same base paint, then `grxm(2,3)` to switch realtime messages on, then a clock counter. Start (250)
and stop (252) reset it. Every twelfth clock - an eighth note - the whole pad toggles between phase
255 and phase 0. The `w` guard means the 81 LEDs are rewritten twice per eighth rather than on all
24 clocks of every quarter; mention it, because a reader comparing the two scripts will wonder why
one has a guard and the other does not.
