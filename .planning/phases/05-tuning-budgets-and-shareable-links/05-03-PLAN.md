<objective>
Recover the knob semantics the vendored compiler does not carry, and give both routes one shape.

Wave 3. `KnobKind` is a **label, not a binding**. `_pad.ts` exports the twelve-member union and each
`PadPreset` declares two to four of them, and nothing anywhere says which `PadState` field a given
kind moves. BOTOR resolves it in `grid-editor/src/renderer/main/zona/PadPanel.svelte` with a
hard-coded per-preset `if/else` chain — which is exactly what D-02 forbids HANGAR from copying, and
which is also a file HANGAR must not depend on. `05-RESEARCH.md` § The recovered semantics is the
transcription, read at the same pinned SHA HANGAR vendored from. This plan turns it into data with a
spec that ties it back to the vendored declaration, so a re-sync that changes a card's knobs goes red
**and names the card**.

Two findings shape the work and neither may be re-litigated:

- **`withChange` is module-private** (`_pad.ts:3156`) and must be reimplemented, because deleting
  `state.preset` is load-bearing: `encodeStamp` short-circuits to `p<presetId>` whenever `preset` is
  set, so a tuned state that kept it would encode as the untuned card and silently lose every knob
  (05-RESEARCH § Pitfall 2).
- **Three presets declare only two knobs**, below D-01's floor of three. A universal **brightness**
  knob fixes it with no invention: it is in D-01's own list, it is a 1–5 detent into
  `BRIGHTNESS_TABLE` which carries its own display words, it costs nothing in Lua at the default
  detent, and stamp formats `c` and `d` already carry it.

Purpose: the data and the arithmetic behind every knob, in node, before anything renders it.
Output: three modules, 15 tests.
</objective>

**The descriptor shape.** One shape serves both routes — that is what makes the panel unable to tell
them apart:

```ts
import type { KnobKindName } from "./view";

export type KnobDescriptor = {
  id: string;                       // stable within the entry; the reset target
  label: string;                    // "Speed", "Ring colour"
  kind: KnobKindName;               // picks the widget, never the field
  options: readonly string[];       // ordered, >= 2. A Lua literal per option.
  default: number;                  // an INDEX
};

/** A compiler-driven knob also knows how to move and read a PadState. */
export type PresetKnob = KnobDescriptor & {
  sheet: PadSheet;                                   // fit()'s `pinned`
  apply(state: PadState, index: number): PadState;   // through withChange
  read(state: PadState): number;                     // the inverse; clamps to 0 on no match
};
```

`options` are strings even where they read as numbers, exactly as `LuaKnob.values` already is: one
type keeps the stamp an integer-index problem and lets `view.ts`'s readout rules work unchanged for
both routes. A colour option is `"r,g,b"` on both routes, so `swatchOf` and `hueName` need no branch.

**Two deliberate divergences from BOTOR's panel, both of which must be recorded in the SUMMARY:**

1. **`direction` binds to `look.axis`, not `look.reverse`.** The UI spec's word table for `direction`
   is written for the compiler's `Axis` (`x → Across`, `y → Down`, `diagonal → Rising`,
   `antidiagonal → Falling`); a boolean has no word row and would fall through to a rail with no
   readout. `look.axis` is a real field, it is read by the wave, scan and drift looks
   (`_pad.ts:1043`, `1053`), and `normalisePadState` grounds it for looks that do not use it
   (`_pad.ts:1403`). **Verify it before shipping it**: task 2's no-op gate compiles every option and
   fails if two produce the same Lua. If aurora's look kind turns out not to use the axis, the gate
   goes red and names it — at which point bind `direction` to `look.reverse` with a two-option word
   row and add those two words to `view.ts`'s table in the same commit, recording why.
2. **`colour` binds by a state-driven rule, not a table.** The rule reproduces BOTOR's own per-preset
   choice for all nine cards and is asserted rather than tabulated:

   ```
   colour -> look.colour        when enabled.look && look.kind !== "none"
          -> touch.colour       else when enabled.touch && touchUsesColour(touch.kind)
          -> sends.gridColour   else when sends.showGrid
   ```

**The colour option set** is the five values the Lua entries already ship —
`0,200,255`, `255,90,0`, `0,255,120`, `255,255,255`, `120,0,255` — plus the card's own colour when it
is not already in the list, inserted at its default position. Using one palette across both routes
means the swatch row looks identical whichever engine is behind it, and `view.ts`'s hue-name table is
already verified against exactly those five. **Never `<input type="color">`**: `quantiseColour` snaps
every stored colour to 17-step channels, so a free picker would offer 4,096 steps the state cannot
hold — a picker that lies.

**And for the same reason the option list is stored pre-quantised.** `quantiseColour` (`_pad.ts:490`)
snaps every channel to a multiple of 17 on the way into the state, so a descriptor whose option string
is the raw palette value would write `0,200,255`, read back `0,204,255`, match nothing in its own
option list and clamp to index 0 — task 2's test 4 (`read(apply(base, k, i)) === i`) would go red for
a reason that has nothing to do with the binding. Four of the five palette values move:

| Palette literal | Stored, and therefore the option string |
|---|---|
| `0,200,255` | **`0,204,255`** (200 → 204) |
| `255,90,0` | **`255,85,0`** (90 → 85) |
| `0,255,120` | **`0,255,119`** (120 → 119) |
| `255,255,255` | `255,255,255` (unchanged) |
| `120,0,255` | **`119,0,255`** (120 → 119) |

Do not hand-transcribe the right-hand column: build it by mapping the palette through the vendored
`quantiseColour`, so a change to the 17-step rule moves the options with it. `hueName` is computed
from 30-degree hue buckets rather than a lookup table, so every quantised value lands in the same
bucket as its unquantised original (Cyan, Orange, Spring green, White, Violet) and `05-02`'s word test
needs no change.

**This is a one-step divergence from the Lua route and the SUMMARY must record it.** A Lua entry
substitutes its colour literal into the source **unquantised** — EUCLID's `@RINGC` becomes
`0,200,255` in the emitted Lua — while a preset's colour goes through `PadState` and is therefore
`0,204,255`. The two swatch rows look identical (same hue bucket, same word, a 4/255 difference in one
channel) and the divergence is real, harmless and worth writing down rather than discovering later.

**`LuaKnob`** (`src/lib/catalog/types.ts`) already carries `id`, `label`, `kind`, `token`, `values`,
`default`, and `CatalogEntry.defaults` maps id to index. The Lua mapping is a rename, not a
transformation.
