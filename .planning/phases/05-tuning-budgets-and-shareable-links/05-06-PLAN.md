<objective>
Turn a simulated pad into a picture a link preview can show, with no dependency at all.

Wave 6. SHARE-04 asks for a build-time OG image per configuration, rendered from the simulator. Every
obvious way to make a PNG in Node is disqualified by D-15: `sharp`, `node-canvas`, `skia-canvas` and
`@resvg/resvg-js` are native modules; a headless browser is explicitly forbidden; a paid service is
forbidden by the project. What is left is exactly enough, and it was measured:

- **`zlib.crc32()` exists in Node 24** — verified on v24.14.0 — so no hand-rolled CRC table.
- **`zlib.deflateSync` emits an RFC-1950 stream**, which is precisely what a PNG `IDAT` holds. No
  adler32 by hand either.
- **A realistic 1200×630 mostly-black frame with a lime pad deflates to 4,321 bytes.** Discord's
  practical ceiling is a megabyte. The headroom is enormous.

And the answer to D-15's one delegated research question — text in Node without a browser — is
**no text**. `opentype.js` and `fontkit` parse a TTF but ship no rasteriser; everything that
rasterises is native. Discord renders `og:title` and `og:description` as real text immediately beside
the image, so the name is on the unfurl either way. UI-SPEC X-20 records the decision.

This plan builds the two pure functions and their specs. The script that calls them, the build wiring
and the head tags are wave 7.

Purpose: the picture, provable in node.
Output: two modules, two specs, 9 tests.
</objective>

<interfaces>
**The exact composition** — `05-UI-SPEC.md` § The OG image, and it is a contract, not a suggestion:

| Property | Value |
|---|---|
| Canvas | 1200 × 630, ground `#000000` |
| Tick | **64** — the same representative frame Phase 4 contracted for `prefers-reduced-motion`, so the still image and the still preview agree |
| Pad face | 468 × 468, centred at (600, 315). Nine cells of 52px; each cell paints 48 × 48 with a 2px black gutter on every side |
| Unlit cells | a 6px dot centred in the cell, `#2b3310` — `#d6ff4e` at 0.20 composited onto black, the `--color-line-soft` dot field flattened |
| Frame | rounded rect, 484 × 484 centred, radius 12px, 2px stroke in `#56661f` — `#d6ff4e` at 0.40 composited, `--color-line` flattened |
| Text | **none** |
| Grain, glow, gradient | none |

Both flattened colours are `round(channel * alpha)` over black and the module computes them from
`--color-accent`'s channels and the alpha rather than hard-coding a hex — then a spec asserts the
computed value equals the UI spec's number. That way the identity ladder and the image cannot drift.

**The frame format** is `PadSim.frame` / `SimEngine.frame`: **243 bytes, screen order, RGB**, read as
`frame[n * 3]`, `frame[n * 3 + 1]`, `frame[n * 3 + 2]` for cell `n` in 0..80, exactly as
`src/lib/sim/paint.ts` reads it. A cell is "lit" when any of its three bytes is non-zero.

**The PNG structure**, from 05-RESEARCH § PNG with `node:zlib` only:

- signature `89 50 4E 47 0D 0A 1A 0A`
- `IHDR`: width, height, bit depth 8, colour type **2** (truecolour RGB), all-zero
  compression/filter/interlace
- `IDAT` = `deflateSync(scanlines)` where each scanline is prefixed with filter byte `0` (None)
- `IEND`
- every chunk is `length(4) + type(4) + data + crc32(type + data)(4)`

The researcher's 20-line reference implementation is in 05-RESEARCH § Code Examples. Use it; do not
re-derive it.

**These two modules are node-only** — `png.ts` imports `node:zlib`. Nothing outside `src/lib/og/` and
`scripts/` may import them, and `png.spec.ts` asserts it, because a `node:` builtin reaching a client
chunk is a build failure with a confusing message.
</interfaces>
