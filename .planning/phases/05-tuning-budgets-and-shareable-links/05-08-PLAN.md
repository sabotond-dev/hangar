<objective>
Give the phase its first pixels: one new colour, deliberately, and the knob itself.

Wave 8. Two things happen here and the first one is a decision, not an edit.

**The ninth token.** Phase 4 ruled that no third colour earned itself and predicted the first would
be a Phase 7 flash-write warning. TUNE-05 gets there first, and the case is an accessibility argument
rather than a taste one: full-strength lime is the fill of an **enabled** `TRY ON DEVICE`, and over
budget that button becomes disabled and loses its lime — so the moment the panel most needs to shout
is the moment it would get quieter and less lime. Signalling failure with more lime puts "go" and
"stop" in one hue, in one 372px column, in one instant.

`#ff3b30` is picked for arithmetic: **5.92:1** on black (AA for the 12px numerals) *and* **3.09:1**
against `--color-accent`, so the two bar fills are distinguishable by luminance alone for a viewer
who cannot separate them by hue. Darker fails the first; brighter fails the second.

And `src/lib/ui/identity.spec.ts` is a **shipped Phase 4 gate** that asserts exactly eight tokens and
exactly two permitted hexes. The ninth token contradicts both. So the guard is **widened
deliberately, in one file, in one commit, with the reason written down** — UI-SPEC X-27 — in the same
class as Phase 4's own W-02 change to a Phase 1 licence gate. It is not bypassed, not skipped, not
annotated around. The alternative is a red suite somebody later "fixes" by loosening it further.

**The knob.** Twelve `KnobKind`s collapse to three skins chosen by kind and by `n = values.length`,
with the rail as a **total** fall-through, so no knob can ever fail to render. Every one is a real
form control with a real label: there is no `div` pretending to be a slider anywhere in this phase.

Purpose: the token, the gate amendment, and the control the whole phase is about.
Output: one CSS token, one amended spec, two components.
</objective>

**X-27, exactly.** In `src/lib/ui/identity.spec.ts`:

- `TOKENS` gains a ninth entry `["--color-over", "#ff3b30"]`, which satisfies both the per-token value
  assertion and the `@theme`-block set equality.
- The hex regex over `src/app.css`'s literals widens from two permitted values to three.
- **`alphaOf()` is not applied to `--color-over`** — it is a flat hex, not an alpha of the accent over
  black — so the AA-on-black loop keeps its existing four members unchanged.
- The `rgb()`-arguments assertion is unaffected, because the new token is a hex.
- **The favicon test's own two-hue regex is untouched.** No red enters the mark.

`src/app.css`'s header comment today says there is no third hue anywhere on the site's chrome and
that the spec goes red if one appears. It is amended in the same edit to name the ninth token and its
three permitted uses, so the file and its test never disagree about how many tokens there are.

**`--color-over` is used for exactly three things** and this plan ships none of them (they are the
meter's job, wave 9). It is **never** a button fill, never a button border, never a knob, never body
text, and never applied to `TRY ON DEVICE`.

**The three skins**, from the UI spec:

| Skin | Kinds | Condition | Markup |
|---|---|---|---|
| swatch row | `colour` | every value parses as three integers in 0..255 | `role="radiogroup"` over real radios; the label's text is a visually-hidden colour name, the visible content is the painted square |
| word row | `direction`, `mode`, `bend`, `spring`, `scale`, `note` | resolves through the kind's table **and** `n <= 8` | `role="radiogroup"` with `aria-labelledby`, real `<input type="radio">` inside `<label>`s |
| rail | everything else, always available | `n <= 8` dot rail, `n >= 9` detent track | one `<input type="range" min="0" max="n-1" step="1">`, `opacity: 0`, absolutely positioned over the painted dots or track, filling the 44px box, with a real `<label for>` |

`widgetFor` and `railSkin` from `$lib/tune/view` make the choice; this component never re-derives it.

**The range input's focus ring is drawn on its wrapper** with `:has(:focus-visible)`, using Phase 4's
exact ring (`2px solid #d6ff4e`, `outline-offset: 4px`, `border-radius: inherit`), because the input
itself is invisible. A knob is never focusable without a visible ring.

**Reset one knob**: double-click anywhere on the control area, `Delete` or `Backspace` while focused,
or a 500 ms long press on a coarse pointer. **`Escape` is deliberately not a reset** — Phase 4 binds
it to un-choosing the panel and the two must not collide.

**Every widget shows where home is**: a 2px `--color-line-soft` dot centred 4px below the option at
the knob's default index. It is decorative (1.58:1) because its meaning is carried by `RESET ALL`, a
labelled control on the same screen.

**The swatch exemption.** A colour knob paints its options as real firmware RGB — a cyan square, an
orange square. That is Phase 4's pad exemption narrowed to its minimum: the exemption extends to
colour swatches and to nothing else in this phase. Everything *around* a swatch — the 1px hairline,
the selection ring, the label — stays on the two-colour ladder, and no gradient, tint, glow or filter
of any kind touches a swatch.

**Row layout**: `grid-template-columns: minmax(88px, 34%) 1fr; column-gap: 12px; block-size: 44px`.
**Stacked layout**: label on its own 14px line box, a 4px gap, the control full width in a 44px box —
row height 62px. Stacked applies at `@container (width < 220px)` and **always** for a word row.
`overflow-x: auto` and `overflow-x: scroll` appear **nowhere** in the region: D-11's "horizontal
scroll never" is a grep-checkable prohibition and wave 10's spec greps for it.

**Touch**: `touch-action: pan-y` on every knob row; `-webkit-touch-callout: none; user-select: none`
on every control so the long press does not raise iOS Safari's selection callout; 44x44 minimum on
every option, every swatch and every button.

Create `src/lib/ui/Knob.svelte`. Props: a `KnobView` (type-imported from `$lib/tune/view`), a
`stacked` boolean, and two callbacks — `onchange(index)` and `onreset()`.

Three skins in one component, chosen by `view.widget` and `view.skin`. Each is a real control:

- **rail** — one `<input type="range" min="0" max="n-1" step="1">` at `opacity: 0`, absolutely
  positioned over the painted dots or track, filling the 44px box, with a real `<label for>` carrying
  the visible label. The platform then gives arrows, `Home`, `End` and `PageUp`/`PageDown` for free.
  `aria-valuetext` carries the readout: the integer, the note name, the mode word, or
  `Position {i} of {n}` when the value has no display form. **Never the raw Lua literal.**
- **word row** — `role="radiogroup"` with `aria-labelledby` on the visible label, real
  `<input type="radio">` inside `<label>`s. Native roving focus makes it one tab stop.
- **swatch row** — the same markup as the word row; the label's text is a visually-hidden colour name
  from `hueName` plus its position (`Cyan, 1 of 5`), and the visible content is a 28x28 square painted
  in that RGB inside a 44x44 hit box.

The default marker is a 2px `--color-line-soft` dot centred 4px below the default option, on all
three skins, plus `aria-describedby` on the group once saying `Default is {word or position}.` —
once, never per option.

Resets: double-click on the control area, `Delete` or `Backspace` on the focused control, and a 500 ms
long press under `@media (pointer: coarse)`. All three call `onreset()`. `Escape` is never handled
here — it belongs to Phase 4's un-choose and a knob that swallowed it would break the panel.

States, motion and reduced motion come from the UI spec's tables verbatim: hover 140 ms colour only,
a 1.25x scale on the selected dot or thumb while a pointer is down, no scale and no transition under
`prefers-reduced-motion`. Accent marks the selected value and nothing else.

`data-testid="knob-{view.id}"` on the row, so wave 11's e2e can find any knob by its id.

Every visitor-facing string in this component comes from `$lib/tune/copy` or from the `KnobView`. No
sentence is authored here.

It renders one `Knob` per view and owns exactly two things: the container query and the row/stacked
decision.

- The rack declares `container-type: inline-size`, so rows reflow against **the panel's** width rather
  than the viewport's — the panel is 420px at most and narrower on a phone, and it is the panel the

  192px, which leaves 92px for a control against a 120px floor, so it stacks; at 375px the content box
  is 247px, leaving 147px, and rows stay side by side.
- A word row **always** stacks, at every width, so its options get the full content width to wrap
  into.
- Row gap 4px; the rack drops its trailing gap. `data-testid="knob-rack"`.

Write the height arithmetic into a comment, because wave 10 depends on it and a number nobody can
re-derive is a number that rots: a row-layout knob is 44 + 4 = 48, a word row is 62 + 4 = 66, and the
region with no messages is `194 + 48r + 66w − 4`.

The empty case — an entry with no knobs — renders the one Body line from `copy.ts` and nothing else.
The rack never renders `SURPRISE ME` or `RESET ALL`; those belong to the region, above the meters.
