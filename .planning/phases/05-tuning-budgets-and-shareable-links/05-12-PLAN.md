<interfaces>
**The probe's mechanism.** `TuningRegion.svelte` takes an **entry id** and an optional `reserved`, so
the page is:

```svelte
<TuningRegion entryId="tpad" reserved={{ setup: RESERVE, timer: 0 }} … />
```

`tpad` is in the catalog, is **not** in the front-door row, and is the tightest real budget in the
tree at 902/908. A reserve pushes it over for real: `cost()` charges `reserved` and `validate()`
produces its own worded sentence. Nothing is faked and no test-only prop exists.

**Choose `RESERVE` by measurement**, at execution time, and record it: it must leave at least one knob
index **in** budget and at least one **over**, so both over-budget copy branches — the knob case and
the arrived case — are reachable from the page. Plan 05-04 recorded the measured `tpad` cost and the
reserve it used; start there and adjust until both branches are reachable.

The page also needs the two knob-driven states, so give it a visible readout of the current meter
numbers and the current over-budget line in `data-testid` elements, in the `dev/fidelity` house style:
**write the failure branch into the same element** rather than throwing, so a broken run produces a
readable assertion diff instead of a Playwright timeout carrying no information.

**The WebKit arithmetic, written out** so nobody has to re-derive it:

- `playwright.config.ts` gives chromium **no** `grep`, so chromium runs every test including tagged
  ones.
- `webkit-phone` carries `grep: /@webkit/`, so it runs only tagged ones.
- A test whose title contains `@webkit` therefore **runs twice** and counts twice.
- `e2e/tuning-webkit.e2e.ts` has five tests, all tagged, so it contributes **ten** to the total.

`devices["iPhone 15"]` is `{ defaultBrowserType: "webkit", viewport: 393x659, isMobile: true,
hasTouch: true }`. At 393px the panel is narrower than 420px and the knob rack's container query
stacks its rows — that is the layout DEGR-01 is really about, and it is why the phone tests are not a
copy of the desktop ones.

**Two WebKit facts the tests must respect:**

- `context.grantPermissions(["clipboard-read", "clipboard-write"])` is **Chromium-only**. The WebKit
  test asserts the **confirm state** only — which is exactly what SHARE-02 requires — and never reads
  the clipboard.
- `requestIdleCallback` does not exist in Safari stable. The formatter prefetch takes the
  `setTimeout` fallback there, so the meters must still settle out of `measuring…` — assert that they
  do, because it is the one place the fallback is observable from outside.

**What must be absent on WebKit**: `TRY ON DEVICE` is present, really `disabled`, and carries
`failureCopy("no-web-serial", undefined, "TRY ON DEVICE")` — Phase 4's copy, in Phase 4's place. No
string in this phase apologises for the browser and none invites the visitor to find another one.
</interfaces>

1. **"the front door opens and a pad is animating @webkit"** — the row renders and a canvas provably
   changes between two samples. This is the DEGR-01 floor: the site is worth opening on a phone.
2. **"choosing opens the panel and the knob rack stacks @webkit"** — choose the centre pad, assert the
   panel and the rack are visible, and assert no horizontal scrollbar exists on the rack
   (`scrollWidth <= clientWidth`) — D-11's "never scrolls" measured rather than asserted in prose.
3. **"a knob turn changes the pad and the meters settle @webkit"** — turn a knob, assert the hero
   canvas changed and that both meters have left `measuring…`. The second half is the only external
   evidence that the `setTimeout` prefetch fallback works where `requestIdleCallback` does not exist.
4. **"COPY LINK confirms in its own state @webkit"** — click it and assert the label becomes
   `LINK COPIED` and reverts. **Do not** grant clipboard permissions or read the clipboard: the
   permission API is Chromium-only, and the confirm state is what SHARE-02 requires.

   **State which branch this test expects, in the test's own comment, before writing the assertion.**
   `CopyLink.svelte` has two: the write succeeds and the button confirms, or `navigator.clipboard` is
   missing or the write rejects and the select-and-copy field is revealed instead. The **expected**
   branch on WebKit at a phone viewport is the **confirm** branch — `navigator.clipboard.writeText`
   is supported on Safari 13.1+ and Playwright's WebKit exposes it, and the phase's whole activation
   discipline (a precomputed URL, no `await` before the call) exists so that it survives there. So
   this test asserts the confirm state and additionally asserts the fallback field is **not**
   present, which is what turns a silent branch flip into a red test rather than a passing one that
   proved nothing.

   **If the fallback appears instead, that is a finding, not a test to loosen.** Do not relax the
   assertion to accept either branch. Record in the SUMMARY which branch appeared and the rejection
   reason from the caught error, and check the two candidate causes in order: an `await` that crept
   in front of `writeText` (the activation expiry 05-RESEARCH documents — a real bug, fix it), or
   Playwright's WebKit build refusing the write for want of a permission it does not expose (a
   harness limitation, not a product defect — then this assertion moves to the fallback branch and
   the SUMMARY says so, and DEGR-01's clipboard story rests on `e2e/tuning.e2e.ts` test 8, which
   forces the fallback deterministically in chromium).
5. **"a shared link lands with the knobs restored, and install is present but disabled @webkit"** —
   open a stamped URL, assert the panel is open with the knobs restored, and assert `TRY ON DEVICE`
   is present, really `disabled`, and carries Phase 4's no-Web-Serial reason. Present-but-disabled,
   never hidden: a visitor who cannot install deserves to be told which browsers can.

Run each project separately and then together, and write all three numbers into the SUMMARY:
`--project chromium`, `--project webkit-phone`, and the whole run.
  </action>
