<objective>
The two seams above the transport, and everything that counted to two.

12-02 made element 255 addressable and left `fetchBoth` / `writeBoth` as two-event adapters so that
nothing above it moved. This plan removes the adapters and moves everything above them at once: the
install store's four legs (snapshot, try-on, put-back, clear) and its store proof, the classifier, the
snapshot schema, the tuner's published pair, the `/dev/install/` page, the two runbooks, and every
assertion in `install.spec.ts`, `session.e2e.ts` and `install.e2e.ts` that was pinned to two - **in one
plan**, because two plans each moving half of a count would both compute the wrong total.

**CLEAR resets both elements (research option A), and the reason is D-21.** The line beside CLEAR is
`Reset the current page to factory default` (41 characters, locked). Under option B - touch element
only - a KEEP after a CLEAR would store the library to flash and the line would be untrue by one
element on a page HANGAR did write. Under A, writing an event's own default sets `cfg_default_flag`
and `grid_ui_bulk_page_store` then **deletes** `pp/01/00.cfg` (`grid_ui.c:398-409`, `:1126-1134`), so
nothing HANGAR wrote is left on the module in RAM or flash. One more ACK per clear; that is the whole
cost. The library is inert without a caller, so losing it on CLEAR costs nothing.

**The snapshot schema moves to `.v2` and v1 is read, never overwritten.** `snapshot.ts:59` already
reserves the key beside `hangar.snapshot.v1`. A v1 record has no `system` string; PUT BACK from one
writes the system **default** - the only system element HANGAR can have met, since nothing before this
phase wrote one. Rule 3 (never overwrite) stands: a v1 record is read as `system = default` and left
where it is; a v2 record is written only if absent, as today.

**The tuner publishes `system` as a constant.** `model.ts:203`'s `ConfigStrings` gains `system`, which
does not move with a knob and is not metered; in this plan it is `SYSTEM_DEFAULT_SETUP` for every entry
- one wire shape, and a preset TRY after a Lua TRY leaves the module holding what the screen shows.
12-07 makes it the library for `preview === "lua"` entries.

Purpose: HANGAR writes, snapshots, restores and clears the system element, and every number that
said two now says three, in one place.
Output: two seams moved, one schema versioned, three tests added, five documents corrected, one page
given a third textarea.

**Which partials can occur.** Writes are sequential and a failure aborts: `system` failed -> nothing
landed; `system` ok, `timer` failed -> system landed only; `system` and `timer` ok, `setup` failed ->

classifier's comment, because Pitfall 6 in the research describes it and a reader will look for it.

new library, harmless. `partialBlock(landed, failed)` in `install-copy.ts:344` takes the names; give it
the two lists as words ("the page init and the Timer", "the Setup") and keep the block's title.

## The snapshot schema

`snapshot.ts:59-62`: `SNAPSHOT_KEY = "hangar.snapshot.v1"`, `EventPair {setup, timer}`, `validEntry`
(`:154-165`) requires two strings and a timestamp. After:

- `SNAPSHOT_KEY_V2 = "hangar.snapshot.v2"`; a v2 entry is `{system, setup, timer, takenAt}`.
- `readSnapshot` reads v2 first; if absent, reads v1 and returns the entry with
  `system: SYSTEM_DEFAULT_SETUP` **and says so** in a field or a returned flag the store can log
  (`fromV1: true`), never silently.
- `persistIfAbsent` writes v2 only; **never writes v1, never deletes v1** (rule 3: a record left by a
