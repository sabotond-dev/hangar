<objective>
The phase's first question, asked before a line of the framework is written: **does a knob reach the
module at all?**

Two entries carried the same report in the second bench round - LUMEN *"seems like nothing changed"*
and NINE PADS *"make a 16 pads cause nothing changed"* - and Probe B settled that LUMEN's bytes are
visible on the desk: four distinct steps at 196 / 139 / 84 / 27, 27 clearly lit against dark. So the
LEDs were never the suspect. What remains is the path from a knob to the pair TRY ON DEVICE sends,
and it is testable in node today.

**What is already known, so this plan does not re-discover it.** A throwaway probe run during planning
(deleted, tree clean, never committed) built the tuner for both entries through the tuner's own
callbacks on real timers and read: LUMEN `depth` index 0 and index 3 both land a Setup of 742 with
different bytes; NINE PADS `grid` index 0 lands 580 and index 1 lands 556. **The tuner-level path is
green.** That leaves the browser wiring - `Coverflow.svelte:910` `onconfig={(config) => (configStrings
= config)}`, `TryOnDevice.svelte:247`'s `$effect` into `install.observeConfig`, and
`install.svelte.ts:847` `tryOnDevice` writing `config` verbatim - which no e2e title exercises with a
knob turned before the click. That is the remaining unknown, and it is the second test here.

**Why the crude harness returned undefined.** A Lua entry's landing is not a microtask chain: it waits
for a fresh VM and lands on the real clock, which is why `model.spec.ts:456` uses `pause(COMPILE_DEBOUNCE_MS
+ 400)` and not `settle()`. A harness that advanced microtasks only read `configs.at(-1)` before the
landing. Use the file's own `recorder()` and its `pause`, on real timers, as the Lua-entry test does.

Purpose: the deciding evidence for two bench reports, taken first because a red here reorders the
phase and a green closes a suspect for good.
Output: one node test, one e2e title, and a verdict every later plan reads by name.
</objective>
