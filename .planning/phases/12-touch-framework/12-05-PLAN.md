<objective>
Three fixes that need no library and no bench answer, diagnosed from source.

**ARC** - *"MIDI stops reliably but the visual on ZONA doesn't."* `arc.ts:212`: the stop tap is
`(e==4 or e>8) and cell==40 -> s.s=1-s.s F(...)`, and the same handler's next line, for every live
code, runs `local r=1+x*31//127 if r~=s.r then s.r=r s.f=glim(r//2,1,120)F(s.f)end`. Probe A, Q1: a
still finger is not still - it sends a MOVE every sample. The first MOVE after the stop tap whose
column differs from where the last drag left `s.r` re-arms the swirl at `s.f` while `s.s` stays 0. The
Timer advances no phase (`p=(s.h+s.r*s.s)%256`), so the CC is constant - "MIDI stops" - and the swirl
turns - "the visual doesn't". The preview never shows it because a click produces no MOVE.

**Decided: the +18 patch, not the library.** `if s.s>0 then F(s.f)end` inside the rate branch keeps
`s.d` and `s.r` tracking while stopped so the resume is exact. The library's hysteresis (12-07) does
not answer this: `r` is a 31-step map of `x`, not a cell, and a one-unit wobble crosses an `r`
boundary every four units regardless of which cell the finger is in. The alternative - `if s.s<1
then return end` before the branch, +25 - makes a stopped ARC ignore drags entirely; costed in the
header, not taken.

**CONSOLE** - *"you should be able to change the muted ones only don't send the midi from those."*
11-07 folded `and not s.m[c]` into the fader condition so a muted column stored nothing. The user's
sentence is the other reading: store and repaint, do not send. `if h~=s.v[c]then s.v[c]=h if not
s.m[c]then s:gms(...)end P(s,c)end`, +8. The unmute then sends the *changed* level (`m and 0 or
s.v[c]*127//7`, unchanged). `lua-smoke.spec.ts` test 8 ("leaves a muted CONSOLE column inert")
reverses, on the record.

**NINE PADS** - *"make a 16 pads cause nothing changed."* 12-01 settled that the knob reaches the
wire. The knob exists (`knobs.preset.ts:456-499`; kind `count`, options `9` / `16`, default 0), and
`view.ts:325-370` gives a word row only to `WORD_KINDS`; a `count` knob is a rail - two dots over an
invisible range input with a readout of `9`, fifth in a five-knob rack. **A knob with two integer
values has no visible affordance.** That is a tuning-panel finding, and it is fixed in the widget
rule. The default also moves to 4x4, which is what the user asked for: shape character unchanged
(knob count and option counts unchanged; `shapeOf` sums option counts), every existing NINE PADS
stamp still decodes `restored` at the index it was minted with, and the picture, the OG image and the
recorded cost move.

Purpose: three bench lines closed without waiting for anything.
Output: two entries edited, one preset default moved, one widget rule widened, two tests added.
</objective>
