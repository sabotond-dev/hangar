Create `src/lib/catalog/` - the HANGAR-owned catalog module that every later plan in this phase, and
Phase 4's coverflow, writes into.

Wave 1. `depends_on` is empty; the wave number is the serial execution slot. Nothing here touches
wasmoon, the Lua host or `package.json`, so this plan is self-contained and can be verified with the
dependency tree exactly as it stands today.

**Phase 4 adopts this shape for its seed row**. If Phase 4 invents its own catalog shape first, every
Phase 8 entry needs a migration. This plan fixes the shape while it is free.

- It does not author a configuration. Waves 4 to 6 do that, against the gate this plan seeds.
- It does not build a knob widget, a meter, or a coverflow. Those are Phases 5 and 4.

  module has no dependency on the compile surface and therefore never drags 628 KB of WASM into a
  chunk whose job is to list names.

**1. The entry shape (D-10).**

```ts
export type CatalogSource =
  | { kind: "preset"; presetId: string }
  | { kind: "state"; state: PadState }
  | { kind: "lua"; setup: string; timer: string };

export type CatalogEntry = {
  id: string;                       // url slug, stable forever: ^[a-z][a-z0-9-]*$
  name: string;                     // "EUCLID"
  description: string;              // one line, no newline
  tags: readonly string[];          // feel-based
  featured: boolean;
  addedAt: string;                  // "YYYY-MM-DD", drives the Newest sort
  source: CatalogSource;
  preview: "padsim" | "lua";        // DERIVED from source.kind, stored explicitly
  knobs: readonly LuaKnob[];
  defaults: Readonly<Record<string, number>>;   // knob id -> INDEX into knob.values

  // TRUE iff this entry renders an all-zero frame at EVERY sampled tick with no
  // touch input. Not a preference - a fact about the configuration, asserted
  // against frames.json in both directions by frames.spec.ts test 5. Several
  // genuinely useful cards are dark at rest: tpad writes no LEDs at all, and a
  // card whose only light is a touch response has nothing to show until a finger
  // arrives. Declaring it is what stops "the picture went black" being
  // indistinguishable from "this one is meant to be black".
  restsBlack: boolean;
};
```

`preview` is stored rather than computed at the point of use so the catalog can be read without a
switch, and `catalog.spec.ts` asserts the derivation held for every entry. Export the derivation as
a function so entry files cannot get it wrong:

```ts
export function previewFor(source: CatalogSource): "padsim" | "lua" {
  return source.kind === "lua" ? "lua" : "padsim";
}
```

**2. The knob shape (D-12, TUNE-01).** Knobs on Lua entries are literal token substitution, and
their `kind` comes from the **vendored `KnobKind` union** - the same widget vocabulary the
compiler-driven cards already use. Do not invent a Lua-specific union; that is precisely what D-12
forbids.

```ts
export type LuaKnob = {
  id: string;                       // stable slug, unique within the entry
  label: string;                    // "Tempo"
  kind: KnobKind;                   // the SHARED vocabulary, from the vendored compiler
  token: string;                    // "@TEMPO" - matches ^@[A-Z][A-Z0-9_]*$
  values: readonly string[];        // literal Lua text, in display order, at least 2
  default: number;                  // INDEX into values (D-13: integer knob indices)
};
```

`values` are **strings** even when they are numbers ("110", "0,200,255", "3,5,7"). One type keeps
the length arithmetic in the wave-4 knob gate trivial and keeps the stamp envelope D-13 defers to
Phase 5 an integer-index problem rather than a value-encoding one.

`defaults` duplicates each knob's `default` index keyed by knob id, because Phase 5 reads a knob
state as a record and this is the shape it reads. `catalog.spec.ts` asserts the two agree.

**3. The runtime knob-kind list, with a compile-time exhaustiveness check.** TypeScript unions do
not exist at runtime, and the gate has to check a `kind` string:
