Until Phase 7 can install, the audition goes through BOTOR's shelf, and the research's twelve-row

is already complete and green when this one starts.

Two things make this worth a plan rather than a paragraph:

- **The Lua must be pasteable, not retyped.** Every configuration's shipped text is a template with
  tokens in it; what goes on the module is the render at the defaults. One command must write those
  exact bytes somewhere the user can copy from.
- **A checklist rots.** `docs/PIN-POLICY.md` set this repository's precedent: a checklist item that
  names a command and its expected count stops being runnable the moment it stops being true. The
  same idea applies here - a spec asserts the doc names only real configurations and never loses the
  install-order rule.

The audition's honest purpose is the list of things a simulator provably cannot answer: perceived
polyrhythm, real T100 touch event codes including the fast-tap DOWNUP, `glf`'s rate-only semantics on
real hardware, physical LED diffusion and brightness after the divide-by-512 with no gamma
correction anywhere in the WS2812 path, timer drift under load, whether a genuinely motionless finger
survives a 2 s watchdog, and whether anything freezes or strobes over fifteen minutes.

Purpose: D-16, and the LOW-confidence rows the research flagged for hardware.
Output: one document, 4 tests, one checkpoint.

<interfaces>
**The install order, and why it is first.** HANGAR cannot install until Phase 7, so the audition goes
through BOTOR's shelf with minimalist mode off. **Paste the Timer into event 6 first, then the Setup
into event 0.** The reason is not stylistic: `gtt` is a no-op until the Timer event holds at least
one stored action, and Setup runs immediately in the live VM - so a Setup-first paste arms a timer
that does not exist yet and the pad sits still. `_pad.ts`'s own `writePad` encodes the same rule.
MORPH is the exception that proves it: it has no Timer at all, so it is Setup only, and it is the one
card that starts moving from the Setup alone.

**The seven shipped configurations** (from `08-06-SUMMARY.md`): EUCLID, CHORUS, ARC, GHOST, LATTICE,
MORPH, SONAR.

**MIRROR is not shipped and is blocked**, per D-04, on one five-minute hardware test: does host MIDI
over USB actually reach `midirx_cb` on a ZONA with `grxm(0,2)`? Firmware shows the path -
`grid_decode_midi_to_ui` gates on `grid_rx_should_handle(GRID_RX_TYPE_MIDIVOICE, header)` and
`GRID_RX_MODE_HANDLE_EXTERNAL` is bit `0x02`; `common/src/lua/decode.lua:19-23` calls
`el:midirx_cb({instr, sx, sy}, {ch, cmd, p1, p2})` on every element that has the field - but nothing
proves the traffic arrives or what `instr` it carries. That row belongs in the checklist as an
explicitly **optional** row whose only consequence is unblocking a future entry.

**`renderLua(entry, knobs)`** from `src/lib/sim/lua-pad-sim.ts` produces the exact text. Use it for
the dump - the doc and the module must receive the same bytes, and a hand-copied string in a markdown
file would drift the first time a knob default moved.

**The repository's env-guarded writer precedent** is `golden-frames.spec.ts` (`UPDATE_GOLDEN`) and
`fixtures/synthetic.spec.ts` (`UPDATE_SYNTHETIC`). Both **fail the run by design** because they
rewrite a committed fixture and a regeneration must never be mistaken for a passing run. This one
writes to a gitignored scratch directory and commits nothing, so it does **not** fail the run - say
that in a comment so the divergence reads as a decision rather than an oversight.
</interfaces>

**The checklist - exactly twelve numbered rows**, as a table with the columns
`#`, `Config`, `What to check`, `Why it cannot be simulated`:

1. **any** - Store the Timer first, then the Setup. Confirm the pad starts moving within a second.
   *`gtt` is a no-op until the Timer event holds a stored action.*
2. **EUCLID** - the three rings visibly run at different speeds and the 48-tick pattern repeats.
   *Perceived polyrhythm.*
3. **EUCLID / SONAR** - tap-to-toggle feels reliable and does not double-trigger.
   *Real T100 event codes, including the fast-tap DOWNUP 9 that firmware coalesces into one message.*
4. **ARC** - sliding along X accelerates the swirl **without a phase jump**.
   *`glf` is a rate-only setter on real hardware; a phase reset would be visible and is not simulable.*
5. **ARC** - the 3x3 heart pulse is visible at the chosen colour and brightness.
   *Physical LED diffusion.*
6. **GHOST** - the replayed ghost runs at the speed you drew it.
   *Timer drift under load.*
7. **CHORUS / LATTICE** - hold a chord dead still for three seconds. Does the 2 s watchdog cut it?
   *A motionless finger emits nothing because enqueue is change-gated; whether a real finger is ever
   motionless is physical.*
8. **LATTICE** - the root lattice is legible at the dim out-of-scale colour; raise it if not.
   *Physical brightness of `0,25,50` after the divide-by-512, with no gamma correction anywhere in
   the WS2812 path.*
9. **MORPH** - corner brightness tracks the blend readably from across the room.
   *Perception.*
10. **SONAR** - the sweep reads as a rotation rather than a scan, and armed cells stay visible
    underneath it. *Perceived motion and LED contrast.*
11. **MIRROR (optional - unblocks a future configuration, ships nothing today)** - with
    `grxm(0,2)` and a `midirx_cb`, does an inbound CC from the DAW move a bar at all? If not, MIRROR
    stays unshipped. *The one MEDIUM-confidence claim in the research: firmware shows the path,
    nothing shows the traffic.*
12. **any** - leave a card running for fifteen minutes. Confirm nothing freezes and nothing strobes.
    *The 655 s `glt` ceiling, and pitfall 1 - a keeper on a decaying trail wraps the countdown and
    strobes forever.*

**What to record.** One line per row: pass, fail, or a note. For row 8, the colour actually used if
it had to be raised. For row 11, the answer and, if yes, the `instr` value observed. State that the
results belong in this document under a dated "Results" heading, and that a failing row is a bug
report against the configuration, not against the checklist.

**A closing note on colour.** Every RGB triple in the seven configurations is a starting point, not a
measured result - one layer caps at 49.6 % and there is no gamma correction in the path. Changing a
colour is a knob-value edit in the entry file plus a `frames.json` regeneration, and nothing else.

Add `.tmp-audition/` to `.gitignore`, beside `.tmp-e2e/` and `.tmp-format-parity/`.

Run `npx prettier --check docs/HARDWARE-AUDITION.md` and `npm run lint`.
