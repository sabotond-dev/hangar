<objective>
D-07's probe: the extra Lua slots, proved or refused at the bench, before the compiler is designed.

**The finding this exists to test.** ZONA has **five** 908-character actionstrings per page, not two.
`../grid-fw/common/src/c/grid_ui_system.c:17-33` gives the system element `setup/ini(0)`,
`mapmode/map(4)` and `timer/tim(6)`; `grid_ui_touch.c:85-97` gives the touch element `setup/ini(0)`
and `timer/tim(6)`; `grid_module.c:455` gives ZONA exactly those two elements. That is **4,540
addressable characters**, of which Phase 12 spends the library's measured cost plus 19.

**The mechanism.** `grid_ui.c:373` registers every event body as a named method on a global table:

```c
sprintf(dest, "ele[%d].%s = function (self) %s\"%s\"; ", index, function_name, fn_push, function_name);
```

and the firmware's own default scripts already call one from another - `grid_ui_system.h:25` and
`grid_ui_touch.h:61` both contain `"self:" GRID_LUA_FNC_A_INIT_short "()"`. So `self:tim()` from the
touch Setup should execute the touch Timer's body, and `ele[1]:map()` should execute the system
mapmode's. **Neither has ever been observed for a HOST-WRITTEN script**, and that distinction is the
whole reason this is a bench row rather than a citation.

**What rides on it, measured** (`13-RESEARCH.md` §3.1, produced in this tree with the pinned
`compressScript`):

| Architecture | Where it lives | Cost | Verdict |
|---|---|---|---|
| Naive: one dispatcher serving four element types, four elements placed | touch Setup | **1,166** | 258 over. Dead |
| Naive, **one** element placed | touch Setup | **1,067** | 159 over before anything is placed |
| **Split**: generic runtime `Z` | a second system slot | **861** | needs this probe |
| **Split**: table + map + callback, four elements | touch Setup | **366** | 542 free |
| **Split**, sixteen elements | touch Setup | **811** | 97 free |
| **Fallback**: vertical faders only, dead branches eliminated | touch Setup | **697** | fits today, no probe needed |

**So the answer decides whether Sandbox v1 is the PDF's own surface - a Fader, an XY pad, a Button and
a Knob - or four faders and some buttons.** D-07 says the probe is taken *"before the Sandbox compiler
is designed"*, and this plan is where.

**Why it does not stall the phase.** The answer is consumed by **one** plan, 13-14, twelve waves away.
This checkpoint accepts **"not yet"** as an answer: waves 3 through 13 touch none of it, and if the
probe is still unanswered when 13-14 runs, the fallback branch is taken - which needs no firmware
question, no bench row and no second slot, and which this plan designs in full so the choice costs
nothing later. **What is not acceptable is a guess.**

**One more question rides on the same stop, because it is cheap to ask and expensive to guess.** The
Bible's §12 table and both PDF swatches give the action colour as `#DCFF71`; HANGAR has shipped
`#D6FF4E` since Phase 4 and `IDENT-01` names it with a tilde, so both satisfy the requirement. D-01
makes the PDF primary on look, so the default is the Bible's - but it is the one colour the site is
built on, the next wave writes it into eleven tokens, and swapping it afterwards is one line **only if
nobody has hand-picked a neighbouring value in the meantime**. Asked here, answered before 13-03.

Purpose: the largest architectural fork in the phase settled by observation, early, cheaply.
Output: one document, two measured probe strings, both branches costed, one checkpoint, `+0 / +0`.

## The two probes, as designed - to be measured, syntax-checked and written down

**Probe 1 - does `self:tim()` execute the touch element's own Timer body?**

```
touch Timer   G=42
touch Setup   self:tim() glp(0,0,G,0,0)
```

If the Timer's body ran, `G` is 42 when Setup reads it and cell 0 lights at red 42. If it did not,
`G` is nil and the `glp` call raises - which the module reports as a Lua error and which the user sees
as **a pad that does not light**. The two outcomes are visually distinct with no instrumentation, and
that is the point: **a bench row must be readable from across the desk.**

**Probe 2 - does `ele[1]:map()` execute the system element's mapmode body?**

```
system mapmode  H=99
system Setup    (unchanged - Phase 12's library)
touch Setup     ele[1]:map() glp(0,1,H,0,0)
```

Same reading, on cell 1, at red 99. **Index 1 is the system element** (`grid_module.c:455`), and ZONA
has no mapmode button, so nothing else in the firmware ever fires it - which is exactly why it is the
attractive slot.

**Measure each string** under the pinned minifier, syntax-check it with `GridScript.checkSyntax`, and
write the cost beside it. They are ten to thirty characters; the number matters only because **every
Lua string in this repository is measured before it is claimed**, and a probe that broke that rule
would teach the wrong habit.

**Write both probes as complete, pasteable event bodies for `/dev/install/`'s three textareas** -
system setup, touch setup, touch timer - with the fourth and fifth slots named and left empty where the
page has no field for them. **If `/dev/install/` has no textarea for the system mapmode slot, say so
plainly and state what probe 2 needs**: either a one-line addition to the dev page (a fourth textarea,
which is a dev-only route the research says stays untouched - so this plan asks before adding it) or a
manual send through the existing tooling. **Do not add a field on assumption.** Ask in the checkpoint.

or, if only `self:tim()` works, the runtime moves into the **touch Timer** and the sweep moves with it.
