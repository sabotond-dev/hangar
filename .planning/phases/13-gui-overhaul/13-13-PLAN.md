**§11 says "each item shows a preview, title, kind, timestamp/status" and draws nothing.** The PDF

**Collections ship in v1 (D-13), against the research's recommendation to defer.** The user chose them
because the PDF draws them and they want the PDF. They are **the one feature in the PDF with no
specification behind it at all** - §11 lists recoverable drafts, named copies and favorites, and never
mentions collections. So the plan has to write the specification, and D-13's own instruction is
explicit: *"Where that specification has a fork, the plan asks."* **Four forks, one stop, task 01.**

**Import validation is a refusal, not a repair.** §11: *"Validate imported schemas and show
incompatibilities before opening or applying."* The vocabulary already exists: `stamp.ts`'s `Landing`
union is `restored | older | unreadable | none`, with three landing behaviours and a test suite behind
each. **Reuse it.** A second set of words for the same three situations is how a codebase ends up
explaining the same failure two ways.

**Export is genuinely trivial and the research checked the thing that sounded risky.**
`URL.createObjectURL(new Blob([json], { type: "application/json" }))` on an `<a download>` works on every
browser HANGAR supports, needs **no permission and no gesture beyond the click**. The restriction that
sounds like it applies belongs to sandboxed iframes; `adapter-static` on Cloudflare Workers sets no
`sandbox` attribute anywhere. Import is `<input type="file" accept="application/json">` plus
`File.text()` - **not** the File System Access API, which is Chromium-only and would break the degrade
story on exactly the browsers that already cannot install.

**Sandbox surfaces share as a file, not a link (D-14 Q7)**, and this plan builds the file half. The
Sandbox's own export lands at 13-17; the format and the validator are built here so that plan has
nothing to invent.

## The four forks (D-13), each with its costs, for task 01

**Fork A - may a configuration be in more than one collection?**
- *One collection each* (a field on the record): trivially consistent, one write per move, and a
  configuration is never in two places. But `Live set` and `Studio experiments` are exactly the kind of
  pair a thing belongs to both of.
- *Many* (a membership list per collection): matches how people actually file things, and costs a
  reconciliation on delete - removing a configuration must remove it from every collection, and an
  orphaned id must be dropped on read the way favorites already does.

**Fork B - is delete undoable, and for how long?**
- *Undo in the session only* (the deleted collection is held in memory until the page closes): simple,
  and the undo dies with the tab.
- *A tombstone in storage with an expiry*: survives a reload; costs a second record shape and a rule
  for when it is swept.
- *Confirmation instead of undo*: no undo at all, one dialog. §11 says *"deletion with undo where
  practical"*, so this is the option the spec leans away from.

**Fork C - what does an empty collections list offer?**
- *Nothing but `+ New collection`* (the PDF's own shape when there are none).
- *A suggestion*, e.g. a first collection pre-named `Live set` - which is what the mockup's data
  implies but not what it specifies.
- *The section is hidden entirely* until the first collection exists.

**Fork D - does an export carry collection membership?**
- *Yes*: an exported configuration re-imports into a collection of the same name, creating it if
  needed. Portable, and it means importing one file can create a collection the user did not ask for.
- *No*: membership is local filing and does not travel. Simpler, and an import always lands
  unfiled.
- *Only when the whole library is exported* - which raises a fifth question (is there a
  whole-library export?) and is therefore the option that costs the most.

**The planner's readings, offered and not taken:** A-many, B-session, C-nothing-but-new, D-no. Every one
is cheap to reverse except A.

## The record shapes

```
SavedCopy   { schema, kind, id, name, createdAt, editedAt, source, knobIndices? , surface? }
Draft       { schema, kind, id, name, createdAt, editedAt, source, knobIndices? , surface? }
Collection  { schema, id, name, createdAt, members: string[] }   -- pending fork A
ExportFile  { schema, kind, exportedAt, app: "hangar", record }
```

**`schema` is in the body because a file has no key name.** 13-06 established the rule; this is the
plan that spends it.

## Import validation, in order, refusing at the first failure

1. `app === "hangar"` and `schema` is a version this build reads -> else `unreadable`;
2. an older readable `schema` -> `older`, and the file lands on the base configuration exactly as an
   older stamp does, **never on a subtly wrong one** (`SHARE-03`'s own words);
3. `kind` is `playground` or `sandbox` -> else `unreadable`;
4. for `playground`: the entry id exists **and every knob index is inside that knob's own option list**
   -> else `older` if the entry exists with a different shape, `unreadable` if it does not;
5. for `sandbox`: every region is in bounds, non-overlapping, and within the element cap -> else
   `unreadable` with the **specific** reason, because §8 wants a conflict explained at the affected
   region and an import is the same situation with no region to point at;
6. otherwise `restored`.

**Nothing is written to storage until the whole validation passes.** A half-imported library is worse
than a refused file.
