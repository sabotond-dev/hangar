<objective>
The device band, re-skinned and re-homed, with every safety rule restated as unchanged.

**The spec's §9 state machine against HANGAR's, row by row.** `install.svelte.ts:212` declares fifteen
phases; `session-copy.ts` declares `SessionPhase` and `SlotState`. The mapping is not a redesign - it
is a **labelling exercise plus four rows the spec never had**:

| Spec §9 state | HANGAR today | Verdict |
|---|---|---|
| No connection | `SlotState` S1 with `capabilityOf() = "ok"` | exists, **re-label only** |
| Permission needed / denied | `PERMISSION_DECLINED`, `TWO_STEP` | exists |
| Unsupported environment | `capabilityOf() = "unsupported" \| "insecure"` with two distinct captions | exists, **and is more precise than the spec's single row** |
| Ready | `install.phase = "ready"` after `snapshotting` | exists |
| Draft differs | the **tuner's** dirty flag, not an install phase | exists, **and lives elsewhere**: the context bar's status reads the tuner, not the store |
| Applying | `writing`, plus the over-time "still writing" line | exists |
| Applied temporarily | `settled` | exists |
| Storing | `writing` with `leg = "store"` | exists |
| Stored | `kept` | exists |
| **Transfer uncertain** | **four phases**: `unconfirmed`, `kept-mismatch`, `partial`, `nothing-landed` | **HANGAR is finer than the spec. Do not collapse them** |
| Disconnected | `lost`, with `UNPLUGGED_WHILE_CONNECTED` / `UNPLUGGED_WHILE_WRITING` | exists |
| — | `restored`, `restored-unconfirmed`, `cleared`, `snapshot-failed` | **four states the spec has no row for. They are the safety rail. They stay** |

**Nothing in the Bible requires weakening a Phase 7 rule, and nothing here proposes one.** *Nothing
writes without a click. RAM before flash. Snapshot before write. ACK before "done".* All four carry over
verbatim, and this plan proves each with an assertion that already exists - `install.e2e.ts`'s
by-class zero-writes proof, `install.spec.ts`'s leg ordering, `snapshot.spec.ts`'s persist-if-absent,
and the three-acknowledgement classifier 12-03 widened. **What changes is the words (13-18 and 13-19)
and where the state is rendered.**

**Where each piece lands.** `DeviceSlot`/`DeviceMark` become the header's `● ZONA connected`, filling
the slot 13-05 reserved. `InstallState`'s thirteen blocks become the context bar's **status zone** plus
the dialogs §5 names D02-D06. `DeviceDetails`' five disclosure states - firmware version, serial,
multi-module line, `FORGET`, the snapshot line - become **`Device actions` in the footer**, beside
`Help & shortcuts`, which is where the PDF puts them on all four shell pages.

**`FORGET` earns a sentence.** PROJECT.md's own constraint says *"the site talks to hardware people paid
for"*; `SerialPort.forget()` is three lines and it is exactly the control that earns trust. It exists
today and it moves without losing its confirmation.

**One thing this plan does not build.** The **page target** - the `Target: Page 1 ▾` control the PDF
draws in the context bar's right zone - is 13-12's, and it is the largest device change in the phase.
This plan renders the destination zone with the **reported active page as a label** and a comment
naming 13-12. That is the research's own read-only shape, kept for exactly one wave, so that the two
plans do not build one control twice.

Purpose: the safety machinery survives a redesign intact and visibly, and the proof is per rule.
Output: two components created, four re-skinned, `device-ui.spec.ts` 13 -> 16. Term `+0 / +3`.

## The connection control, and the rule it keeps

`DeviceSlot`'s **button-versus-summary rule** - a plain `<button>` whenever a click does something, a
`<summary>` whenever it does not - is a genuinely good pattern and the header keeps it. Nine slot
states drive it; `capabilityOf()` answers `ok | unsupported | insecure`; and **`DEGR-02` requires the
control to be present and disabled with the reason inline, never hidden**, on a browser that cannot
install. The PDF's header shows `● ZONA connected` on pages 2-5 and `Connect ZONA ↗` on page 1 - the
same control in two states, which is what the `variant` prop on 13-05's header exists for.

**`CONN-02`'s two messages stay two messages** and neither says "Chromium": the unsupported branch names
Chrome, Edge and desktop Firefox 151+; the insecure branch names the fix. Both are Phase 6's strings
and they do not move here.

## The context bar's status zone

```
● Draft saved locally · Changes not applied
```

Two facts in one line: the **draft** (from the drafts store, 13-06) and the **device** (from the
install store). §9 insists these are different objects and *"never use one generic Saved indicator for
all three"* - so the dot's colour and the two clauses come from two sources and the component takes two
props. **A single prop would be the exact mistake the spec warns about**, and the header says so.

The four uncertain phases each render their own line. §16 offers **one** row -
*"The device stopped responding. Your draft is safe; device state could not be verified."* - for all
six of HANGAR's uncertain and failure titles. **This plan renders the existing six**; 13-18 writes the
six new lines and puts them in the batch. **Do not collapse six measured outcomes into one sentence**
is D-05's own instruction as recorded in the research, and it is repeated here because the collapse
would be easy and quiet.

## Device actions, in the footer

`Device actions` opens the disclosure `DeviceDetails` already implements: firmware version, serial
number, the multi-module line (`SAFE-06`'s own sentence about other modules' pages being stored too),
the snapshot line, and **`FORGET`** with its confirmation. Five disclosure states, unchanged.

**`Reset active device page` lives here** (§9's own placement) and names the page in its confirmation -
which is 13-12's page, so this plan renders the **reported** page and 13-12 makes it the targeted one.
