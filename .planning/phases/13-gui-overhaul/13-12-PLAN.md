<objective>
The control that moves the hardware, inside the envelope that makes it acceptable.

**The finding this plan is built on.** `../grid-fw/common/src/c/grid_decode.c:1272` computes
`bool currentpage = page == grid_ui_state.page_activepage;` and **NACKs any CONFIG/EXECUTE write that
is not on the active page**. The read side is the same (`grid_ui.c:471` returns early, then NACKs and
sends the REPORT anyway with `ACTIONLENGTH 0` - which is why `write-guard.ts:37` already calls an empty
string *"exactly the shape a fetch of a non-active page produces"*). And `PAGESTORE`, `PAGECLEAR` and
`PAGEDISCARD` **carry no page parameter at all** (`:976`, `:1048`, `:904`). So of the four things §9
wants a page selector to do - write, read back, store, reset - **not one can address a page other than
the active one.** HANGAR's own `targetOf()` already knew: it builds its `WriteTarget` from
`id.activePage`, the page the module *reported*.

**So the dropdown as drawn cannot exist, and D-06 chose the other way to make it real:** HANGAR sends
`PAGEACTIVE/EXECUTE` and **moves the module's active page**, then writes. The research recommended
read-only for v1 and said *"(b) alone is not acceptable"*; the user chose the switch **with the
research's own option (c) envelope**, and every clause of it is a requirement of this plan:

1. **A page switch is a click**, never a side effect of anything else. Phase 7's never-writes-without-a-
   click rule covers `PAGEACTIVE/EXECUTE` too, and the by-class zero-writes e2e proof is **extended** to
   count it as a write.
2. **The destination review** (§9): first use and **every** destination change get an explicit
   confirmation naming both pages - *"Switch your ZONA to Page 3? It will stop playing Page 1."*
3. **ACK-gated**: send, then wait for the module's own `PAGEACTIVE` **REPORT** to confirm, and only then
   enable Apply. **A timeout is `unverified`, never `switched`.**
4. **Snapshots are per page.** PUT BACK restores the page it snapshotted and **says which page that is
   before it does it**.
5. **One bench row** before it is claimed working: switch, confirm the module reports the new page,
   apply, PUT BACK, switch back, confirm the first page is what it was.
6. **`PAGEDISCARD` researched** as the firmware-native revert and shipped if the bench confirms.

**`PAGEDISCARD` deserves its own paragraph.** It reloads the active page from NVM - a **RAM-only undo
that needs no snapshot** - and §9's D03 row asks for exactly that (*"Revert device preview if
supported"*). HANGAR has no descriptor for it today: `descriptors.ts` exports `hostHeartbeat`,
`fetchConfig`, `sendConfig`, `storePage`, `fetchSerialNumber` and nothing else. It is one descriptor,
one action and one bench row, and it is a cleaner revert than re-writing a snapshot.

**One firmware detail that will bite if it is missed.** `grid_decode.c:1279` sets
`page_change_enabled = 0` on **every successful CONFIG write**, and `:717` says the **only** thing that
restores it is a `HEARTBEAT` TYPE 255 - which HANGAR already sends (`restorePageChange`,
`sequence.ts:374`). So **a switch attempted straight after a write will be refused unless the heartbeat
goes first.** That ordering is not optional and it is the single most likely bug in this plan.

Purpose: a real destination control, built so that nothing about it can surprise the hardware.
Output: four descriptors, one store, one dialog, six tests, one e2e title, one runbook row. Term
`+1 / +6`, e2e `+1 / +1`.

<interfaces>

## What the protocol permits, read from the firmware and the pinned package

| Class | Code | Page field | Firmware behaviour |
|---|---|---|---|
| `CONFIG` | `0x060` | `PAGENUMBER` at offset 11, length 2 | **EXECUTE NACKs unless `page == page_activepage`** (`:1272`); sets `page_change_enabled = 0` on every success (`:1279`) |
| `CONFIG` FETCH | `0x060` | same | early return on mismatch (`grid_ui.c:471`); NACK **and** a REPORT with `ACTIONLENGTH 0` |
| `PAGEACTIVE` | `0x030` | `PAGENUMBER` at 5 | **EXECUTE moves the active page**, only if `page_change_enabled` and no bulk in progress (`:319`, `:325`). **REPORT is the module telling the host which page it is on** |
| `PAGECOUNT` | `0x031` | `PAGENUMBER` at 5 | FETCH only; reports `page_count`, initialised to **4** (`grid_ui.c:77`) |
| `PAGESTORE` / `PAGECLEAR` / `PAGEDISCARD` | `0x061` / `0x064` / `0x063` | **none** | always the active page |
| `HEARTBEAT` TYPE 255 | | | the **only** thing that restores `page_change_enabled` (`:717`); HANGAR already sends it |

**Do not assume four pages.** §9 says *"Do not assume a fixed number of pages… production enumerates
supported pages."* `PAGECOUNT` is a FETCH and the module answers. **Enumerate; do not hard-code 4.**

## The store's states

```
reported   the page the module last REPORTED. The only trustworthy value
requested  the page the user asked for, after the review
switching  EXECUTE sent, waiting for the REPORT
unverified the wait timed out. NOT switched. Apply stays disabled
```

`unverified` is the state this plan exists to get right. **A timeout is not a failure of the module and
not a success**; it is an unknown, and the rendered line says so in the register §16 uses for the other
unknowns. Apply stays disabled until a REPORT arrives, and **the only way out of `unverified` is a
REPORT or a reconnect** - not a retry counter, not a timer.

## The ordering that the firmware forces

```
switch:   heartbeat(255)  ->  PAGEACTIVE/EXECUTE  ->  wait for PAGEACTIVE/REPORT  ->  enable Apply
write:    (target confirmed)  ->  snapshot if absent for THIS page  ->  CONFIG writes  ->  ACKs
```

The heartbeat first is not defensive: `page_change_enabled` is **cleared by every successful write**, so
the second switch of a session would be silently refused without it. `restorePageChange` already exists;
**call it, and assert the order in a test**, because this is the bug this plan is most likely to ship.

## Snapshots, per page

`SNAPSHOT_KEY` is `hangar.snapshot.v2` after 12-03 and is keyed by module identity. It becomes keyed by
**identity and page**. Follow 12-03's own precedent exactly: **a new key beside the old one, the old one
read and never overwritten**, so a snapshot taken before this plan still restores. Say which key name
shipped and how a pre-plan snapshot is interpreted.

**PUT BACK names its page before it acts.** If the user switched after a try-on, the restore targets the
page that was snapshotted - **which may not be the page they are looking at** - and the copy says so
before the click, not after. That is the whole reason D-06 lists per-page snapshots in its envelope.

## `PAGEDISCARD`, researched then shipped or recorded

Read `grid_decode.c:904` and the pinned package's class table. Write the descriptor and the install
action. **It is not claimed working**: it is a bench row in the same runbook row as the switch. If the
bench refuses it, the action is removed and the finding recorded - and the snapshot restore, which
already works, is the fallback that was never removed.

## The bench row

> heartbeat ordering exists for, and the one most likely to be refused.
