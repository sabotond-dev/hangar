## The landing shape, and why it is the tuner's

`model.ts` publishes a landing that the install store consumes: the three strings plus whatever metadata
the store needs. `landLua` publishes Phase 12's library as the system string; the preset landing
publishes the firmware default. **The Sandbox publishes a third variant** - and the install store
**must not be able to tell them apart**. Assert that: build a landing from a surface and one from an
entry, and assert the store's own consumption path is identical.

**If the store needs to know** - for a caption, for a name in a confirmation - it takes a **label** in
the landing, not a branch on a kind. A branch on a kind in the install store is the beginning of a
second write path.

## The three strings under each branch

| Slot | Two proved slots (the recorded answer) | If 13-02's checkpoint bought a third |
|---|---|---|
| system setup | Phase 12's library (unchanged) | Phase 12's library (unchanged) |
| system mapmode | not written | **the Sandbox runtime** |
| touch Setup | `s.tim(s)` + `G` + `M` + the callback | `ele[1]:map()` + `G` + `M` + the callback |
| touch Timer | **the runtime** + the expiry sweep call | the expiry sweep call |

**On the two proved slots it is three strings and nothing about the install shape moves** - which is the

and if it is four, stop and ask.** Record the arithmetic either way.
