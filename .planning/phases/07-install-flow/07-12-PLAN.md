<objective>
The install flow on the real page, in a browser, against the production build.

Wave 12. Plan 07-08 proved the fourteen states through a probe that hides nothing. This wave proves
the panel, the confirmation, the header lock and the live region - the things a visitor actually
meets - on `/c/aurora/` with the shim and the Node responder, and proves the degrade path on WebKit
at a phone viewport, which is the path a large share of visitors will hit and the one no manual
tester remembers to check.

The timing problem is solved with the responder, not with sleeps: a RAM leg lands in about 40 ms and
the header lock would be unobservable, so the tests that need to see `writing` hold the
acknowledgement in Node and assert the busy label, `aria-busy`, the disabled header controls and the
ignored `Escape` inside that window - then let it land. The hold has to respect the queue's
arithmetic: the request id is minted per attempt and the waiter armed before the write, and
`delayAckMs` stalls the page's `write()` itself (the shim's sink awaits Node), so a RAM-leg ACK held
past `executeMs` 250 is stale on arrival and three attempts end `nothing-landed`. A RAM leg is
therefore held **200 ms per ACK** (two events, a window of about 400 ms that Playwright's polling
catches, both landing on attempt 1), and anything that needs a window past 2000 ms - the slow line -
is observed on a **store** leg, whose single attempt runs to `pagestoreMs` 3000.

Five titles, one tagged `@webkit`, so the arithmetic is four plus two: `PREV_E2E + 6`.

Purpose: SAFE-02's hierarchy on screen, SAFE-05's confirmation before the store, SAFE-08's settled
state with no theatre, DEGR-02 on the engine that can never install.
Output: five browser tests; the suite at `PREV_E2E + 6`.
</objective>
