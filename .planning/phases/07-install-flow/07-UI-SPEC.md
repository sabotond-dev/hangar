# Phase 7 — UI Design Contract

> Visual and interaction contract for the three clicks that touch somebody's hardware:
> `TRY ON DEVICE` (RAM), `PUT BACK` (the snapshot) and `KEEP ON DEVICE` (flash, behind an inline
> confirmation) — and every install state between them.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> Binding upstream: `.planning/phases/07-install-flow/07-CONTEXT.md` (D-01..D-19),
> `.planning/REQUIREMENTS.md` (SAFE-01..09, DEGR-02), and the three approved contracts this one docks
> into — `04-UI-SPEC.md`, `05-UI-SPEC.md`, `06-UI-SPEC.md`. Where this document adds detail it never
> contradicts those; where it amends one it says so by name and gives the arithmetic.

## Spacing Scale

Phase 4's tokens, unchanged. **This phase adds no spacing value and no new exception.** The values it
consumes:

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | Nothing. Declared for completeness |
| sm | 8px | Control → its own line, in all three install-row cells; the gap between the confirmation's two action buttons; the gap between the confirmation's stacked sentences |
| md | 16px | The confirmation block's padding; the vertical rhythm between the install row's three cells; the gap between the device-state region's stacked blocks |
| lg | 24px | Phase 4's hairline gaps above and below the install row — unchanged, untouched |
| xl / 2xl / 3xl | 32 / 48 / 64px | Not used in this phase |

**Declared non-token values, all of them inherited and none of them new:**

1. **44px** — the interactive box floor (Phase 4 exception 1). `TRY ON DEVICE`, `PUT BACK`,
   `KEEP ON DEVICE`, the confirmation's `KEEP ON DEVICE`, `NOT NOW` and `COPY LINK` are each at
   least 44×44.
2. **6px / 10px radii** — Phase 4 exception 3. 6px on every button, 10px on the confirmation block.
   No 2px radius appears in this phase.
3. **Two reserved cell heights, and they are measured rather than asserted.** The `PUT BACK` cell
   reserves **72px** of line box (three Body lines) and the `KEEP ON DEVICE` cell reserves **48px**
   (two Body lines), by exactly Phase 5's honesty-slot mechanism: a one-cell grid holding every
   string the cell can show, with the inactive ones `visibility: hidden` and `aria-hidden="true"`.
   These are reservations, not spacing, in the class of Phase 5's 72px honesty slot and Phase 6's
   152px header note. **The reason they exist is a safety reason, not a tidiness one:** the two cells
   sit directly above and below one another, one of them is the site's only destructive control, and
   a line that changes count moves the destructive control under a reaching hand. See "The install
   row".

`overflow-x: auto` and `overflow-x: scroll` appear nowhere in anything this phase adds. Phase 5's
grep-checkable prohibition is extended to the install row and the confirmation block by simple
inheritance: neither of them has a horizontal axis to scroll.

### Accent — the reserved list, restated in full with no additions

Phase 4 reserved six things, Phase 5 added two, Phase 6 added one. **Phase 7 adds none and takes none
away.** The canonical list is still nine:

1. The splash wordmark and the lime rectangles punched through the glyph field.
2. The solid triangles in the name plate.
3. The `TRY ON DEVICE` button fill when it is enabled.
4. The focus ring.
5. The header wordmark.
6. The one walking cell in the 9×9 loading motif.
7. The fill of the two budget meters, while in budget.
8. The selected value of a knob.
9. The lit cells of the device slot's 9×9 mark.

Item 3 now fills a button that genuinely writes to somebody's hardware. The token's meaning is
unchanged — *this is the live control* — and it stays on exactly one control per screen.

**The confirmation's affirmative is not accent-filled**, and that is the SAFE-02 hierarchy made
literal rather than described: an accent-filled `KEEP ON DEVICE` inside the confirmation would be a
second primary on the same panel and would out-shout `TRY ON DEVICE` at the exact moment the site is
asking somebody to do the irreversible thing. It is a bordered secondary. See "The control
hierarchy".

### The ruling this phase was asked for: **no third colour on the flash confirmation**

Phase 4 predicted the first colour that would earn itself would be a Phase 7 flash-write warning.
Phase 5 spent that prediction early on `--color-over`, scoped to three meter uses, and recorded the
test it had to pass first. **This phase declines the colour, and the argument is the accessibility
one the brief asked for, not a taste one.**

**The requirement, stated exactly.** A destructive, persistent action must be distinguishable from a
RAM audition *without colour*. Here is the test with every colour removed from the panel:

| Channel | `TRY ON DEVICE` (RAM) | `KEEP ON DEVICE` (flash) |
|---------|-----------------------|--------------------------|
| **Position** | Region 1 of the panel, at the top, above the honesty slot, the device-state region and the whole tuning region | Below the 24px hairline, in the install row — roughly 400px of panel away, with a rule between them |
| **Size and fill** | Full width of the 372px column, a filled box, a 44px block | Auto width, **no border and no fill at all** — a bare text control |
| **Step count** | One click writes | One click opens a block; a second click, on a differently-weighted control, writes |
| **Copy** | *"Writes this configuration into your ZONA's memory in about a second. A power cycle brings your own back."* | *"This replaces the Setup and Timer scripts on your ZONA's touch element, and it survives a power cycle."* |
| **Focus and keyboard reach** | reachable at one tab stop from the knobs | reachable two tab stops later, and its confirmation moves focus deliberately |

Five independent channels, and the state is fully legible with the hue channel deleted. That is the
same test Phase 5 set for itself *before* it introduced the red, and it is the bar Phase 6 declined to
meet. Phase 7 does not meet it either, for four reasons in order:

1. **A colour would carry nothing the sentence does not already carry.** `--color-over` earned itself
   because a meter is a graphical object with no text of its own at the moment it crosses — the bar's
   fill is the state. The confirmation is text and layout end to end; a red rule beside a sentence
   that already says *"survives a power cycle"* is decoration, and decoration is not an accessibility
   argument.
2. **Reusing `--color-over` would overload the one thing it means.** It is on the same panel, roughly
   200px away, inside the tuning region, where it means *over 908 characters*. A visitor who has
   learned that meaning would meet it again meaning *permanent*. Two meanings in one column makes both
   weaker, and `src/app.css`'s own comment and `identity.spec.ts` behind it record the three uses by
   name.
3. **A fourth hue would break a guard for a use that is decorative.** `identity.spec.ts` fails on a
   tenth token and on a fourth hex in `src/app.css`. That guard should be spent on something that
   cannot be said any other way; this can be said, and is, in four sentences.
4. **The site's own precedent points the other way.** `--color-over` is never a button fill, never a
   button border and never applied to `TRY ON DEVICE`, "because a red CTA would say *dangerous* when
   the truth is *not yet*" (05-UI-SPEC). A red on the flash affirmative would say *dangerous* when the
   truth is *deliberate* — and the visitor has just chosen to be deliberate.

**What carries the warning instead, declared as a contract and not as a hope:**

| Channel | The contract |
|---------|--------------|
| **Copy** | The caption `PERMANENT`, and a first sentence that names the element being replaced and states the power-cycle persistence in one breath |
| **Weight** | The confirmation's caption is **the one caption on this site rendered at `--color-ink` rather than `--color-ink-quiet`** — a single, declared exception to the caption convention, and the only strength escalation in the phase. Its first sentence is `--color-ink` where the panel's other explanatory lines are `--color-ink-quiet` |
| **Layout** | A bordered 10px block that **replaces the control that opened it**, so the panel visibly reorganises around the decision; a deliberate focus move into it; two named exits |

**If the colour is ever added**, it must be `--color-over` reused rather than a fourth hue, its scope
must be exactly the confirmation block's 1px border (never a fill, never a label, never the affirmative
button), and `identity.spec.ts` needs no amendment at all because the token already exists — only
`src/app.css`'s header comment would change, from "exactly three uses" to four, with the fourth named.
**That is the whole delta, and it is recorded here so the morning's answer is one line of work either
way.** The default, and this document's ruling, is **no**.

**The pad exemption is untouched.** `PadSim` still emits real firmware RGB and those pixels are
content. Nothing in this phase authors a colour the simulator did not.

## The control hierarchy (SAFE-02), stated once

Three tiers, and every control in the panel is in exactly one of them.

| Tier | Controls | Treatment |
|------|----------|-----------|
| **Primary** — one per panel | `TRY ON DEVICE` | full width of the 372px column, `min-block-size: 44px`, fill `--color-accent`, label Micro in `#000000`, `border-radius: 6px`. Hover `filter: brightness(1.12)` + `box-shadow: 0 0 24px var(--color-glow)` over 140ms; active `brightness(0.92)`. Disabled: fill `transparent`, `1px solid var(--color-line)`, label `--color-ink-dim`, `cursor: not-allowed`, a real `disabled` attribute — never `aria-disabled` alone |
| **Secondary** — bordered | `PUT BACK`, the confirmation's `KEEP ON DEVICE`, `COPY LINK` (Phase 5's), `TURN IT DOWN` (Phase 5's) | auto width (`inline-size: fit-content`), `min-block-size: 44px`, `padding-inline: 16px`, `background: transparent`, `1px solid var(--color-line)`, `border-radius: 6px`, label Micro in `--color-ink`. Hover: border and label to `--color-accent` over 140ms. Disabled: label `--color-ink-dim`, border unchanged, real `disabled` |
| **Quiet** — borderless | `KEEP ON DEVICE` in the install row, `NOT NOW`, `DISCONNECT ZONA` (Phase 4's), `BROWSE ALL` (Phase 5.1's) | auto width, `min-block-size: 44px`, `padding-inline: 0`, no border, no background, label Micro in `--color-ink-quiet`, to `--color-ink` on hover over 140ms. Disabled: label `--color-ink-dim`, real `disabled` |

**`KEEP ON DEVICE` moves from Secondary to Quiet in this phase** (Z-02). In Phases 4 to 6 it was a
bordered control that could not be clicked; in Phase 7 it can be clicked and it writes flash, so it
becomes the quietest control on the panel — and the confirmation behind it is where its weight is
spent. Phase 4's rule survives intact and gets stronger: *the two install controls are never the same
size, never the same fill, never adjacent.* They are now three tiers apart with a hairline, a tuning
region and a whole other control between them.

**The label is constant and the weight escalates.** The row's `KEEP ON DEVICE` (Quiet) opens the
confirmation; the confirmation's `KEEP ON DEVICE` (Secondary) commits. The two are **never on screen
at the same time** — the block replaces the control that opened it — so a speech-input user saying
"click KEEP ON DEVICE" is never ambiguous, and the label never changes under a visitor mid-decision.

### Region 3 — the device-state region, and why it may grow

Phase 4 named it the connect-state region and Phase 6 removed its `aria-live`. Phase 7 keeps the
element, keeps `data-testid="connect-status"` (an e2e suite asserts it) and adds the install blocks to
the states it can render. It is still **auto height**.

That is deliberate, and the principle behind it is the one Phase 5 was already applying without
naming:

> **The region beneath the primary control may grow when the visitor acts on the device. It must
> never grow when the visitor acts on the knobs.**

Phase 5 reserved the honesty slot's height precisely because that slot changes on a *knob turn*, and
a knob turn's target is the rack — moving the rack under the hand that is turning it is the failure.
Every state change in this phase follows a click on `TRY ON DEVICE`, `PUT BACK` or `KEEP ON DEVICE`,
or an unplug. The visitor's attention is on the device half of the panel, the growth happens below the
control they just pressed, and the tuning region moving down is the honest consequence of an answer
arriving. **No reservation is added to region 3, and none is needed.**

### Region 6 — the install row

Phase 5 shipped it as `display: flex; flex-wrap: wrap; gap: 8px; justify-content: space-between` with
`KEEP ON DEVICE` left and `COPY LINK` right. **It becomes a single column** (Z-03):

```css
.install-row {
  display: flex;
  flex-direction: column;
  align-items: flex-start;
  gap: 16px;
}
```

with the DOM and visual order **`PUT BACK` → `KEEP ON DEVICE` → `COPY LINK`**, each cell being a
control with its own Body line 8px beneath it.

**The arithmetic that forces it.** The panel's content column is 372px at its widest, and it is never
wider — `max-inline-size: 420px` minus 24px of padding each side. Each of the three cells carries a
16px Body sentence beneath its control. Two cells side by side gives each sentence a column of about
178px, which is roughly **20 characters a line** against the 43 this document family measures at
372px. A wrapping row is a column pretending to be a row, and it changes which controls share a line
as labels change state. A column is one layout at every width.

**Order.** `PUT BACK` first because it is the way back and the way back should be the first thing the
eye reaches below the rule; `KEEP ON DEVICE` second because it is the commitment; `COPY LINK` last
because it is not an install control at all.

**`PUT BACK` renders only when a snapshot exists for the module this browser last identified.** When
it is absent, the row is two cells and the column closes up — a change that happens exactly once per
session, at the moment the snapshot lands, and moves only `KEEP ON DEVICE` and `COPY LINK` beneath it.

**Both new cells reserve their height with a sizing twin** (see Spacing, non-token 3):
`PUT BACK`'s line cell is 72px (three Body lines, its longest string is 101 characters) and
`KEEP ON DEVICE`'s is 48px (two Body lines, its longest string is 82 characters). The mechanism is
Phase 5's honesty slot verbatim: one grid cell, every candidate string at `grid-area: 1 / 1`, the
inactive ones `visibility: hidden` and `aria-hidden="true"`. **The reason is safety, not tidiness:**
`KEEP ON DEVICE`'s line changes when a knob moves (its reason becomes "the knobs moved since the last
try-on"), and `PUT BACK`'s line changes after a keep — either would shift the site's only destructive
control vertically under a hand already reaching for it.

**Copy caps, so the reservations cannot silently grow.** Every string in `PUT BACK`'s cell is
**≤ 129 characters** (three lines at 43) and every string in `KEEP ON DEVICE`'s cell is
**≤ 86 characters** (two lines at 43). `install-copy.spec.ts` asserts both, per string, by name.

## The install state machine

Fourteen states, I0 to I13. They are a property of *the chosen configuration against the connected
module*, and they compose with — never replace — Phase 6's nine session states. Four of them (I10 to
I13) are failure states the draft carried as blocks without rows; revision 1 gives each a row, because
a control's enablement is a property of a state and the executor needs the discriminant.

**The gate, in one sentence:** no install state exists until the session is connected (Phase 6's S4),
and no *write* state exists until the snapshot is present.

| # | State | Entered when | `TRY ON DEVICE` | `PUT BACK` | `KEEP ON DEVICE` | Region 3 |
|---|-------|--------------|-----------------|------------|------------------|----------|
| I0 | **`idle`** | no session | **enabled** — the click connects | absent, unless a snapshot survives from a previous session, in which case present and **disabled** | present, **disabled** | Phase 6's pre-click explanation |
| I1 | **`snapshotting`** | session reached S4; both `CONFIG/FETCH` in flight | **disabled** | absent | present, **disabled** | the `READING ZONA` block |
| I2 | **`ready`** | both fetches ACK'd, the snapshot recorded | **enabled** | present, **enabled** | present, **disabled** — `Available after a try-on.` | the `ZONA IDENTIFIED` block |
| I3 | **`writing`** | a click on `TRY ON DEVICE` or `PUT BACK` sent the first `CONFIG/EXECUTE`, **or a `PAGESTORE/EXECUTE` was sent** — from the flash confirmation's commit, or as the store leg of a `PUT BACK` after a `kept` (Z-04) | **disabled**; label `WRITING…` on its own RAM legs, `KEEPING…` on the confirmation's store leg, its resting label during a `PUT BACK`; `aria-busy` whenever its label is a busy label | **disabled**; label `PUTTING BACK…` through both of its own legs, with `aria-busy` | **disabled** | unchanged from the state it came from, under `aria-busy="true"` — except a `PUT BACK`'s store leg, which shows the `RESTORED` caption and first line (I5) |

| I8 | **`lost`** | the session dropped while I3 was in flight | **enabled** once a session returns, else disabled | present, **disabled** until a session returns | present, **disabled** | the lost block |
| I9 | **`refused`** | see the precedence table below | **disabled** with a reason for causes 1, 2, 3 and 5; **enabled** for cause 4 — the click retries the snapshot and writes only if it lands | per the precedence table — absent for causes 1, 3 and 4, disabled for 2, **enabled for 5** (over budget), because it writes the snapshot and never the tuned configuration | present, **disabled** | per the reason |

| I11 | **`unconfirmed`** | the confirmation's `PAGESTORE/EXECUTE` reached its 3000 ms timeout with no acknowledgement and no NACK | **enabled** | **enabled** | **enabled** | the unconfirmed block |
| I12 | **`restored-unconfirmed`** | a `PUT BACK`'s RAM leg landed and its store leg then timed out, or its re-fetch never matched | **enabled** | **enabled** | **disabled** — `Available after a try-on.` | the put-back-for-now block |
| I13 | **`nothing-landed`** | both events exhausted their bounded retries and neither `CONFIG/ACKNOWLEDGE` arrived | **enabled** | **enabled** — a snapshot exists, by construction | **disabled** — `Available after a try-on.` | the nothing-reached block |

**Wherever a row reads `present, disabled` without naming a reason** (I0, I1, I8, and I9 causes 3 and 5), the reason is `Available after a try-on.` — the set of `KEEP ON DEVICE` reasons is closed at six and an executor never adds a seventh. **The header write-lock** (`DISCONNECT ZONA` and `FORGET THIS ZONA` disabled) is engaged in I3 on every leg and in no other state; it releases the moment the write settles into any of I3's nine exits.

**The four failure states, and where each comes from.** `kept-mismatch` (I10) is `partial`'s
sibling, reached from I6's re-fetch when the bounded rounds (three, 07-RESEARCH Pitfall 6) never
return a byte-identical pair — 07-RESEARCH calls the same state `kept-unconfirmed`; this document
keeps the name `kept-mismatch`, and the two are one state. It is unreachable on healthy hardware —
Phase 2 proved byte-identity on a real ZONA across three captures — and it exists so the failure is
never silent. `unconfirmed` (I11) exists because of a measured firmware fact: a `PAGESTORE/EXECUTE`
that arrives while a bulk NVM operation is already running is dropped with no acknowledgement and no
negative acknowledgement at all (`docs/SKELETON-RESULTS.md` § (c), `grid_decode.c:979-981`), so the
3000 ms timeout is the only signal that case ever produces. `restored-unconfirmed` (I12) is its
sibling on the `PUT BACK` side. `nothing-landed` (I13) is `partial` with zero of two instead of one of
two. Each has its own section below.

### I1 — `snapshotting`

Entered the instant the session reports connected, before any write control can enable (SAFE-03,
D-03). Measured cost: two `CONFIG/FETCH`, 11.9 to 29.7 ms each across 148 real requests, so the whole
state settles in well under 100 ms.

- **Region 3:** caption `READING ZONA` (Micro, `--color-ink-quiet`) over one Body line in
  `--color-ink`: `Taking a copy of the Setup and Timer scripts already on your ZONA’s touch element.`
- **Honesty slot:** `Reading what is on your ZONA now, so nothing you do here is one-way.`
  It deliberately does **not** name `PUT BACK` — that control is not on the screen yet, and Phase 4's
  copy rule is absolute.
- **Live region:** silent on entry. On exit into I2 it says once:
  `Your ZONA’s own Setup and Timer are saved. Nothing has been written.`
- **Header:** no change. The device slot is in Phase 6's S4 showing the identity summary, and it stays
  there.

### I2 — `ready`

- **Region 3:** Phase 4's identified block, with **its body amended** (Z-07). Caption
  `ZONA IDENTIFIED`, body:
  `Firmware {major}.{minor}.{patch}, active page {n}. Its own Setup and Timer are saved here, so PUT BACK can undo anything you try.`
  `PUT BACK` is on the screen in this state, so naming it is legal and is the point.
  `DISCONNECT ZONA` stays where Phase 4 put it, at the block's end.
- **Honesty slot:** `Writes this configuration into your ZONA’s memory in about a second. A power cycle brings your own back.`

### I3 — `writing` — and why nothing animates

SAFE-08 forbids a progress bar for a 200 ms operation, and FEATURES B6 says a settled-state
confirmation is the honest substitute. The measurements are more extreme than the requirement
assumed: `CONFIG/EXECUTE` settled at **14.8 to 21.6 ms** across twelve real writes, so the whole
two-event RAM write plus the restore heartbeat lands inside **two frames at 60 Hz**. The store leg's
`PAGESTORE/ACKNOWLEDGE` came back in **13.6 to 38.7 ms** across eleven real stores.

**`writing` has three legs, and one control carries the busy label at a time:**

| Leg | What was sent | The busy label | Where it renders |
|-----|---------------|----------------|------------------|
| A RAM leg from `TRY ON DEVICE` | two `CONFIG/EXECUTE`, Timer then Setup, then `restorePageChange` | `WRITING…` | the primary |
| Both legs of a `PUT BACK` — the RAM leg, then, after a `kept` this session, the store leg | two `CONFIG/EXECUTE`, then a `PAGESTORE/EXECUTE` and the D-12 re-fetch | `PUTTING BACK…`, through both legs — **no fourth label** | `PUT BACK` itself; the primary keeps its resting label, disabled |
| The store leg from the confirmation's commit | one `PAGESTORE/EXECUTE`, then the D-12 re-fetch | `KEEPING…` | the primary — the control that was clicked has left the screen, and the row's `KEEP ON DEVICE` is a quiet disabled control that cannot carry it |

**The complete visual contract for `writing`, on every leg:**

1. The busy label swaps in **instantly — no transition, no fade.** A 160ms crossfade on a 40ms state
   is a smear. `PUT BACK`'s auto-width box grows with its label; nothing sits beside it in the column,
   so nothing else moves, and the cell's reserved height does not change.
2. The control carrying the busy label is a real `disabled` button and carries `aria-busy="true"`.
3. **All three install controls are `disabled`**, whichever one was clicked, on every leg.
4. **Nothing else changes.** Region 3 holds whatever block it was holding, under `aria-busy="true"`,
   with one exception: a `PUT BACK`'s store leg holds the `RESTORED` caption and first line, because
   the RAM leg genuinely landed and saying so is honest (I5). The honesty slot holds whatever string
   it was holding. **No reason line is swapped**, because a sentence that appears and disappears
   inside 40 ms is noise rather than information, and the disabling is protective rather than
   explanatory.
5. **No spinner.** The 9×9 motif is Phase 4's loading state for a *port chooser*, which takes as long
   as a human takes. Here it would flash for one frame.
6. **No artificial minimum duration.** HANGAR never holds a state open to make it visible. A 40 ms
   round trip that lands in `settled` is a correct, complete interaction, and 40 ms is below every
   published threshold at which a human perceives a wait at all.
7. **One escape hatch, and it is arithmetic rather than theatre.** If any leg is still in flight
   after **2000 ms**, region 3 shows one additional Body line in `--color-ink-quiet`:
   `Still writing. Your ZONA is taking longer than it usually does.`
   and the live region says, once, politely: `Still writing.` — so a screen-reader user is not left
   in silence for the whole wait. No bar, no percentage, **no attempt counter**. A retry that succeeds
   is a success, and naming attempts would make a 20 ms operation feel fragile (Z-09). The arithmetic,
   per leg: on a RAM leg 2000 ms is roughly **90×** the slowest `CONFIG/EXECUTE` ever observed
   (21.6 ms), reachable only through the bounded retries; on a store leg it is roughly **50×** the
   slowest `PAGESTORE/ACKNOWLEDGE` ever observed (38.7 ms), and it sits **below** the shipped 3000 ms
   `pagestoreMs` timeout **on purpose** — the line says the module is still busy, not that anything
   failed, and only the timeout produces a failure (I11, I12). [Post-approval amendment, plan check 2:
   in practice the 2000 ms line is a store-leg feature. A RAM leg's bounded retries — three attempts
   at `executeMs` 250 with 120/240 ms backoff, per event — max out at roughly 1,970 ms plus link
   latency before ending `nothing-landed`, so the line fires only on a `PAGESTORE` leg, whose single
   attempt runs to 3000 ms.]
8. **The live region speaks at most twice during `writing`:** `Still writing.` at 2000 ms if the leg
   is still in flight, and once on the outcome. Otherwise silent.
9. **`Escape` is ignored while `writing`** — it neither closes the confirmation nor un-chooses the
   panel. Closing the panel mid-write would remove the only surface that reports the outcome. The
   state is at most about two seconds on a RAM leg and about five on a store leg (the 3000 ms timeout
   plus the bounded re-fetch), by construction, so this is a pause, not a trap (Z-10).
10. **In the header, `DISCONNECT ZONA` and `FORGET THIS ZONA` are `disabled` while `writing`, on
    every leg — explicitly including the store leg** — with the reason inline:
    `Not while HANGAR is writing to your ZONA.` Pulling the port out from under a RAM write is the one
    way a visitor can create `partial` with their own hand, and under a store it is the way to create
    `unconfirmed`; both of those controls do exactly that, and the lock closing over the store leg is
    the hazard Z-15 exists for.

**Exits.** `writing` leaves for exactly one of: I4 `settled`, I5 `restored`, I6 `kept`, I7 `partial`,
I8 `lost`, I10 `kept-mismatch`, I11 `unconfirmed`, I12 `restored-unconfirmed` or I13 `nothing-landed`.
No other state is reachable from it, and it never returns to the state it came from.

### I4 — `settled` (the RAM audition landed)

- **Region 3:** caption `PLAYING NOW`, body in `--color-ink`:
  `{Name} is running on your ZONA now. It lives in memory only — a power cycle brings your own configuration back. Changing page on your ZONA clears it; try it on again if that happens.`
- **The third sentence is FEATURES B7**, the page-change warning: a page change on the module destroys
  its Lua VM, so an audition evaporates and a visitor who was not told reads it as HANGAR failing. It
  is one sentence in the state where it is true, and the audition is the only thing it can happen to.
- **The speed claim is made once, before the click, and is not repeated here.** *"About a second"*
  lives in the honesty slot where it is a promise; restating it in `settled` would be bragging about a
  promise already kept (Z-08).
- **Live region:** `{Name} is running on your ZONA. A power cycle brings your own configuration back.`
- `KEEP ON DEVICE` becomes **enabled** — the one and only path to it.

**`KEEP ON DEVICE` disables again the moment a knob moves.** Its reason becomes
`Try it on again first — the knobs moved since the last try-on.` `SURPRISE ME`, `RESET ALL`,
`TURN IT DOWN` and a landed stamp all count as knob moves. **The rule is: flash only what you have
heard.** Without it, a visitor can audition one configuration, turn a knob, and permanently store a
configuration that never played on their module (Z-05).

### I5 — `restored` (`PUT BACK`'s own settled state)

- **Region 3:** caption `RESTORED`, body in `--color-ink`:
  `Your own Setup and Timer are back on your ZONA’s touch element, exactly as they were when you connected.`
  **Both render on the two `CONFIG/ACKNOWLEDGE` (and `restorePageChange`)**, whether or not a store
  leg follows.
  When the session had already reached `kept`, a second Body line in `--color-ink-quiet`:
  `They are stored too, so they stay after a power cycle.`
  **That line renders only after the `PAGESTORE/ACKNOWLEDGE` and after the re-fetch proves the
  bytes** (D-12) — it is a claim about what survives a power cycle, and it waits for the evidence.
  Between the two: the caption and the first line only, region 3 `aria-busy="true"`, all three install
  controls disabled, the header write-lock engaged, and `PUT BACK`'s own label still reading
  `PUTTING BACK…` exactly as it did on the RAM leg (I3). That interval is I3, not I5; I5 proper is
  entered when the second line can be shown.
- **Live region:** `Your own configuration is back on your ZONA.` — once, on I5's entry, so after the
  store leg when there is one.
- **If the store leg fails after the RAM leg succeeded** — its 3000 ms timeout expires with no
  acknowledgement, or the re-fetch never matches inside the bound — the state is I12
  `restored-unconfirmed`, below.
- `KEEP ON DEVICE` returns to `Available after a try-on.` — the module is no longer playing HANGAR's
  configuration, so there is nothing auditioned to keep.

### I6 — `kept` (the flash store landed and was proved)

Reached only through the confirmation. "Kept" is said **after** the `PAGESTORE/ACKNOWLEDGE` *and*
after the re-fetch of both events returned bytes identical to what was sent (D-12) — the same proof
Phase 2 shipped.

- **Region 3:** caption `KEPT`, then two Body lines:
  - `--color-ink`: `{Name} is stored on your ZONA and will still be there after a power cycle.`
  - `--color-ink-quiet`: `HANGAR read both scripts back and they match, character for character. The pad restarts once as it loads the stored version.`
  The second sentence of that second line is not filler: the module restarts its Lua VM after a store,
  the pad visibly blinks out and comes back, and a visitor who is not told will read it as a failure.
- **Live region:** `{Name} is stored on your ZONA and survives a power cycle.`
- `KEEP ON DEVICE` is disabled with `Kept on your ZONA. Turn a knob and try it on again to keep a new one.`
- `PUT BACK`'s line changes to its second form (see below).

### I10 — `kept-mismatch` (the store ACK'd, the read-back never matched)

Reached from I6's re-fetch when three bounded rounds return no byte-identical pair.

- **Region 3:** title (Micro title) `Stored, but the read-back does not match`, detail in `--color-ink`:
  `Your ZONA acknowledged the store, but reading the two scripts back gave something different. HANGAR will not call that kept.`
  Steps: 1. `Click TRY ON DEVICE, then KEEP ON DEVICE again` · 2. `Or click PUT BACK to restore what was there when you connected`
- **Controls:** `TRY ON DEVICE` **enabled**, `PUT BACK` **enabled**, `KEEP ON DEVICE` **disabled** with
  the sixth reason string, `Try it on again first, then keep it again.` **Why disabled rather than
  live:** what is in the module's memory now is whatever read back — bytes that differ from what was
  heard — and Z-05's rule is *flash only what you have heard*. A live `KEEP ON DEVICE` here would
  store those unknown bytes. `TRY ON DEVICE` puts a known configuration back in memory, lands in I4,
  and I4 enables `KEEP ON DEVICE` by the one path that always does; the step and the reason say the
  same thing in the same order. Both named controls are on the screen in this state — one live, one
  present and disabled with its reason — so the absolute copy rule holds (Z-21).
- **Live region:** the title, verbatim, and nothing else (Phase 6's failure rule).

### I7 — `partial` (one event landed)

SAFE-07's named case, and the whole reason "installed" means an ACK rather than a resolved promise.

- **Region 3:** title `Only one of the two scripts landed`, detail in `--color-ink`:
  `{Timer} reached your ZONA and {Setup} did not. What is on the module now is half this configuration and half your own.`
  Steps, in this order:
  1. `Click TRY ON DEVICE to send both again`
  2. `Or click PUT BACK to restore what was there when you connected`
  Both controls named are on the screen in this state.
- `TRY ON DEVICE` **enabled** (the retry is the same click, not a new label) and `PUT BACK`
  **enabled** — SAFE-07 requires both offered, and they are offered as controls, not as prose.
- `KEEP ON DEVICE` **disabled**: `Not after a half-written try-on. Send it again, or put your own back.`
  **HANGAR never stores a half-written state to flash.**
- **Live region:** `Only one of the two scripts landed.`

### I8 — `lost` (the connection went mid-write)

Phase 6 takes the session to S5 (`unplugged-while-connected`) and the header slot handles that half.
The panel handles the install half.

- **Region 3:** title `The ZONA was unplugged mid-write`, detail in `--color-ink`:
  `Some of this configuration may have reached the module and some may not. Nothing was stored, so a power cycle brings your own configuration back.`
  **When the leg in flight was a store leg** (the confirmation's, or a `PUT BACK`'s second leg), the
  detail is instead:
  `The store was sent and no confirmation came back before the ZONA was unplugged. HANGAR cannot say what a power cycle brings back.`
  *"Nothing was stored"* is said only where it is true — the rule Z-11 applies to Phase 6's utterance,
  applied to this document's own detail. The steps and the controls are the same in both forms.
  Steps:
  1. `Plug the ZONA back in`
  2. `Click {label} again` — `{label}` is Phase 6's Y-13 interpolation: `TRY ON DEVICE` when the panel
     is rendering the block, `CONNECT ZONA` when the header disclosure is
  3. `Then click PUT BACK to restore what was there when you connected`
- **`PUT BACK` stays rendered and disabled**, with `Needs your ZONA connected.` — SAFE-09's "still
  offered" means present and visibly waiting, re-enabling the instant the session returns. The
  snapshot is durable (SAFE-04), so this survives the tab being closed and reopened.
- **Live region — and this is a correction to a Phase 6 string, not an addition.** Phase 6's
  `unplugged-while-connected` utterance is `The ZONA was unplugged. Nothing was written.` **That
  sentence is false when a write was in flight.** The contract:
  - the install utterance wins — `The ZONA was unplugged mid-write.` — and Phase 6's session
    utterance is suppressed for that transition;
  - Phase 6's `session-copy.ts` sentence gains a second form used by the disclosure in the same
    circumstance: `The ZONA was unplugged while HANGAR was writing to it.`
  Two utterances for one event would be double-speak; one *false* utterance would be worse than both
  (Z-11).

### I9 — `refused`, and DEGR-02

DEGR-02: install controls are **present but disabled with the reason inline, never hidden**. Every
refusal below renders a real `disabled` attribute (never `aria-disabled` alone), a `--color-ink-dim`
label, and its reason as adjacent Body text — Phase 4's exact treatment.

**Exactly one reason is shown, highest precedence first:**

| # | Cause | `TRY ON DEVICE` honesty slot | `PUT BACK` | Region 3 |
|---|-------|------------------------------|------------|----------|
| 1 | `unsupported` / `insecure` — permanent capability | `This browser cannot write to a ZONA. Everything else on this page works.` | absent (Z-12) | the `failureCopy(f, undefined, "TRY ON DEVICE")` block in full |
| 2 | `writing` in flight | unchanged — no reason is swapped (I3, rule 4) | disabled (I3) | unchanged |
| 3 | `snapshotting` in flight | `Reading what is on your ZONA now, so nothing you do here is one-way.` | absent — not yet | the `READING ZONA` block |
| 4 | the snapshot could not be taken | the standing `ready` line | absent | the `Nothing to put back yet` block, below |
| 5 | over budget (TUNE-05) | Phase 5's `tryOnBudgetReason(...)`, unchanged | **enabled** — it writes the snapshot, never the tuned configuration, so the 908 budget does not apply to it | unchanged; Phase 5's message block beside the knobs still says everything |

**Precedence rule 1 is an amendment to shipped behaviour** (Z-06). `TryOnDevice.svelte` today keeps
the standing honesty line on `unsupported`/`insecure`, which was correct while that line ended
*"this never writes"*. In Phase 7 the standing line promises a write, so on a browser that cannot
write it would be a lie, and the capability sentence takes the slot.

**The snapshot could not be taken** — cause 4, its own block:
- Title `Nothing to put back yet`, detail:
  `HANGAR could not read the Setup and Timer already on your ZONA, and it will not write over something it has not copied.`
- Steps: 1. `Click TRY ON DEVICE to try reading it again` — the click retries the snapshot first and
  only writes if that succeeds.
- `PUT BACK` is absent (there is nothing to put back). `KEEP ON DEVICE` is disabled with
  `Available after a try-on.`
- **Live region:** `Nothing to put back yet.`

**`PUT BACK` on an incapable browser is absent rather than present-and-disabled, and that is a
decision rather than an omission** (Z-12). DEGR-02 exists so a visitor on iOS learns what this site
would do with a different browser, and `TRY ON DEVICE` and `KEEP ON DEVICE` — present, disabled and
explained — carry that in full. `PUT BACK` is different in kind: it restores *a specific module's own
configuration*, and on a browser that has never seen a module there is no configuration for it to
name. A disabled control offering to restore nothing is a worse answer than no control.

**Empty state.** None, and that is deliberate — Phase 6's Y-20 rule, inherited whole. "No device" is
the resting state of a site that works completely without hardware.

### I11 — `unconfirmed` (the store never acknowledged)

The reason it exists is measured, not imagined: `docs/SKELETON-RESULTS.md` § (c) records that a
`PAGESTORE/EXECUTE` arriving while a bulk NVM operation is already running is **dropped with no
acknowledgement and no negative acknowledgement at all** (`grid_decode.c:979-981`). The 3000 ms
`pagestoreMs` timeout is the only signal that case ever produces, and a timeout with nothing to say
about it would be a frozen `KEEPING…`. It is a state row (I11) and a block in region 3, like I7 and I8.

- **Region 3:** title `Your ZONA did not confirm the store`, detail in `--color-ink`:
  `{Name} is still running on your ZONA, in memory. No confirmation of the store came back, so HANGAR cannot say whether it will be there after a power cycle.`
  Both halves are load-bearing: the configuration is running right now — memory holds it, and nothing
  was pulled out from under the visitor — and whether it survives a power cycle is the one thing
  HANGAR does not know and says it does not know.
  Steps: 1. `Click KEEP ON DEVICE and confirm to send the store again` · 2. `Or click PUT BACK to restore what was there when you connected`
- **Controls:** `TRY ON DEVICE` **enabled**; `PUT BACK` **enabled** (the snapshot exists);
  `KEEP ON DEVICE` **enabled** — memory still holds the configuration the visitor heard, so Z-05 is
  satisfied and the control is live; clicking it opens the confirmation again and a second store goes
  out. Both named controls are on the screen and live, so no reason string is needed.
- **Live region:** `Your ZONA did not confirm the store.` — the title, verbatim.

### I12 — `restored-unconfirmed` (put back in memory; the store leg did not confirm)

I11's sibling on the `PUT BACK` side, and its own block rather than the same one: the sentence that
is true here — the owner's original is running — is the opposite of I11's. Reached when a
`PUT BACK`'s two `CONFIG/ACKNOWLEDGE` arrived and its store leg then hit the 3000 ms timeout, or its
re-fetch never matched inside the bound. The structure is I11's: a title, a detail, a step, a control
row, one utterance.

- **Region 3:** title `Put back for now, not after a power cycle`, detail in `--color-ink`:
  `Your own Setup and Timer are running on your ZONA now, in memory. The store did not confirm, so after a power cycle the version kept earlier may come back instead.`
  Steps: 1. `Click PUT BACK again` — it runs both legs again.
- **Controls:** `TRY ON DEVICE` **enabled**; `PUT BACK` **enabled**; `KEEP ON DEVICE` **disabled** with
  `Available after a try-on.` — the same reason and the same ruling as I5, because memory holds the
  owner's original and not the chosen configuration. A live `KEEP ON DEVICE` here would either store
  the owner's own scripts beneath a line and a confirmation that name *this configuration*, or promise
  to store bytes that are not in memory; neither is honest, so the control waits for a try-on (Z-21).
- **Live region:** `Put back for now, not after a power cycle.` — the title, verbatim.

### I13 — `nothing-landed` (zero of two)

`partial` with neither event acknowledged: both exhausted their bounded retries. On the wire it is the
signature `docs/SKELETON-RESULTS.md` predicted for a silent ring discard — a timeout with no NACK —
which is why the second step names the cable rather than the module.

- **Region 3:** title `Nothing reached your ZONA`. After a `TRY ON DEVICE`, detail in `--color-ink`:
  `Neither script got through. Nothing on the module changed, so your own Setup and Timer are still running and there is nothing to put back.`
  Steps: 1. `Click TRY ON DEVICE to send both again` · 2. `If it happens twice, check the cable is seated at both ends`
  After a `PUT BACK`, the detail is instead:
  `Neither script got through. Nothing on the module changed, so what was playing is still playing.`
  Steps: 1. `Click PUT BACK to send both again` · 2. `If it happens twice, check the cable is seated at both ends`
- **Controls:** `TRY ON DEVICE` **enabled**; `PUT BACK` **enabled** — a snapshot exists by
  construction, because no write state is reachable without one (the gate), so the control is present
  and live even where the detail says there is nothing for it to undo: a control that works is not
  withdrawn for being unnecessary. `KEEP ON DEVICE` **disabled** with the existing
  `Available after a try-on.` — nothing was tried on, and after a failed put-back the way back to it is
  a fresh try-on (Z-05).
- **Live region:** `Nothing reached your ZONA.` — the title, verbatim.

## The inline flash confirmation

D-15: an inline block, not a modal, with `KEEP ON DEVICE` as its only affirmative and `NOT NOW`
beside it.

**Where it renders.** In the install row, **in place of the `KEEP ON DEVICE` cell**. The cell above it
(`PUT BACK`) does not move; the cell below it (`COPY LINK`) moves down by the block's height. Nothing
the visitor is looking at moves, and there is never a second `KEEP ON DEVICE` on the screen.

**The block.**

```css
.keep-confirm {
  border: 1px solid var(--color-line);
```

same holds here: the rest of the panel stays valid, `Tab` walks out of the block in DOM order, and no

disclosure, and it matters:** focus leaving the block does **not** close it. A disclosure is reading
material and closes when you stop reading it; a confirmation is a pending decision and must still be
there when the visitor comes back to it.

| Gesture | Result |
|---------|--------|
| `KEEP ON DEVICE` inside the block | commits; the block is replaced by the row control, disabled; the primary's label reads `KEEPING…` with `aria-busy`; focus moves to **region 3** (`tabindex="-1"`), which at that moment still holds the `PLAYING NOW` block under `aria-busy="true"` — the `KEPT` block arrives on the `PAGESTORE/ACKNOWLEDGE` and the re-fetch proof, not on the click, and the live region carries it |

has stored to flash, follows with a store so the module is genuinely back — and its own line says so
before the click. A confirmation exists to stop somebody unknowingly making a stranger's work
permanent; putting the owner's own work back is the direction that needs no gate, and a gate on the
escape hatch is the one place a gate does harm. SAFE-05 names `KEEP ON DEVICE` and only
`KEEP ON DEVICE`.

## The header device slot, and its disclosure

**The device slot never shows an install state, and its label never reads `writing…`.** Four reasons:

1. Phase 6 contracts the S4 label as the identity summary and sizes the slot's two 14px line boxes on
   it. An install label would be a fifth string in a box built for four.
2. The install is a property of the *chosen configuration*, which lives in the panel — and the panel
   is on screen whenever an install is possible, because `TRY ON DEVICE` and `KEEP ON DEVICE` exist
   nowhere else.
3. Phase 6's Y-11 rule is that one block has two mounts and never renders in both at once. A `writing`
   state in the header and in the panel simultaneously is exactly what that rule forbids.
4. The RAM write settles in 15 to 22 ms per event and the store's acknowledgement in 14 to 39 ms. A
   header label that changes for two frames is noise, not feedback; when a module is genuinely busy,
   the panel's 2000 ms line says so and the header's lock is the header's whole contribution.

**Two things do change in the header, and both are load-bearing:**

| Where | Change |
|-------|--------|
| The S4 disclosure block | Gains one Body line in `--color-ink-quiet`, beneath Phase 6's identity line: `A copy of your ZONA’s own Setup and Timer is saved in this browser, so it can be put back even in a new tab.` It names no control, because the panel may be closed when this is read |
| `DISCONNECT ZONA` and `FORGET THIS ZONA` | Both **`disabled` while `writing`, on every leg — the RAM legs and, explicitly, the store leg** — real `disabled`, `--color-ink-dim` label, with the reason inline beneath the pair: `Not while HANGAR is writing to your ZONA.` They are the two controls that can produce `partial` under a RAM write and `unconfirmed` under a store with the visitor's own hand, and the lock closing over the store leg is the hazard Z-15 exists for |

## The one session live region

Phase 6's `SessionAnnouncer` — one visually-hidden `aria-live="polite" aria-atomic="true"` region,
mounted once in `+layout.svelte`, 500ms trailing coalescer, held until the splash finishes on `/`.
**This phase adds utterances to it and creates no fourth region.** The install state is a property of
the session's module, it is mutually exclusive in time with a session transition, and two regions
speaking about one module would be double-speak.

| Transition | Utterance |
|------------|-----------|
| I1 → I2, the snapshot landed | `Your ZONA’s own Setup and Timer are saved. Nothing has been written.` |
| → I4 `settled` | `{Name} is running on your ZONA. A power cycle brings your own configuration back.` |
| → I5 `restored` | `Your own configuration is back on your ZONA.` |
| → I6 `kept` | `{Name} is stored on your ZONA and survives a power cycle.` |
| → I7 `partial` | `Only one of the two scripts landed.` |
| → I8 `lost` | `The ZONA was unplugged mid-write.` |
| → I10 `kept-mismatch` | `Stored, but the read-back does not match.` |
| → I11 `unconfirmed` | `Your ZONA did not confirm the store.` |
| → I12 `restored-unconfirmed` | `Put back for now, not after a power cycle.` |
| → I13 `nothing-landed` | `Nothing reached your ZONA.` |
| → I9, snapshot could not be taken | `Nothing to put back yet.` |
| I3 `writing`, any leg, still in flight at 2000 ms | `Still writing.` — once, polite; the only utterance that is not a transition |
| I3 `writing`, otherwise | **silent** — it speaks on the outcome |
| Opening or closing the confirmation | **silent** — the focus move is the announcement |
| A knob turn re-disabling `KEEP ON DEVICE` | **silent** — Phase 5's tuning region already speaks about knobs, and this is not a budget crossing |

**Rules, all inherited from Phase 6 and all binding here:**

- **One utterance per event, `aria-atomic`.** A command and a transition are one string, never two.
- **A successful flash store is worth exactly one utterance** — the `kept` string above, spoken once,
  after the re-fetch proof. Not one for the ACK and another for the verification.
- **Failures announce their title with a full stop, and nothing else** — the title's words verbatim, the terminal period added because it is spoken. Successes announce a sentence.
- **`lost` takes precedence over Phase 6's session utterance**, which is suppressed for that
  transition because `Nothing was written.` would be false (Z-11).

## Open questions for the morning

1. **The third colour (Z-01).** The ruling is **no**, and the reversal is one line: reuse
   `--color-over` as the confirmation block's 1px border only — never a fill, never a label, never the
   affirmative — and amend `src/app.css`'s header comment from three uses to four. `identity.spec.ts`
   needs no change at all, because the token already exists. This is `07-CONTEXT.md`'s open question 1
   and it is the cheapest thing in this document to overturn.
2. **`KEEP ON DEVICE` moving to the borderless tier (Z-02).** It makes SAFE-02 literal, but it does
   make the destructive control the quietest thing on the panel. If it should stay bordered, the tier
   table is the only edit and the confirmation's affirmative would then need a different weight.
3. **`PUT BACK` storing after a keep (Z-04).** It makes "the original is always recoverable" literally
   true and it is a flash write behind one click. The alternative is a RAM-only `PUT BACK` whose line
   warns that the stored copy is still HANGAR's, which is honest but leaves the module wrong after a
   power cycle. This is a hardware-safety posture call, and I12 `restored-unconfirmed` is the state the
   store leg lands in when it does not confirm.
4. **Re-disabling `KEEP ON DEVICE` on a knob move (Z-05).** It costs one extra click every time a
   visitor tweaks and then wants to keep. It is right, and it is mildly annoying.
5. **Showing which ZONA the site remembers.** `07-CONTEXT.md`'s open question 2. This document
   contracts a slot for it — the header disclosure's snapshot line — that names no identifier, because
   the durable key's mechanism is the phase researcher's D-04 question. If the answer is a
   human-readable identity, one clause goes into that line and nothing else moves.
6. **An empty snapshot being valid (Z-16).** It is a UI-visible reading of SAFE-03 and it is the
   researcher's and planner's to confirm on the wire.
7. **The 2000ms "still writing" threshold (Z-09).** It is roughly 90× the slowest `CONFIG/EXECUTE`
   and roughly 50× the slowest `PAGESTORE/ACKNOWLEDGE` ever measured, and on the store leg it sits
   below the 3000 ms timeout on purpose. It exists only so a retried or a busy write is never a frozen
   label. If bounded retries turn out to have a
   longer worst case than that, the number moves and nothing else does.
8. **Retiring Phase 4's `Your ZONA is already identified.` (Z-07)** touches copy that a signed-off
   phase authored and that `try-on.spec.ts` may assert. It is required rather than optional, but it is
   a touch to approved words.
