**The writer, generalised** (`src/lib/transport/sequence.ts`):

```ts
export interface EventStrings {
  setup: string;
  timer: string;
}

/** Where a write goes: the ZONA's own address and its REPORTED active page (D-10). */
export interface WriteTarget {
  sx: number;
  sy: number;
  page: number;
}

export const targetOf = (id: Identity): WriteTarget => ({
  sx: id.zona.sx,
  sy: id.zona.sy,
  page: id.activePage,
});

/**
 * Write both events into the module's RAM, in the field-tested order.
 *
 * TIMER (6) FIRST, THEN SETUP (0). _pad.ts:3908-3913 gives the reason and it
 * is not stylistic: gtt is a no-op until the Timer event holds at least one
 * stored action, and Setup runs immediately in the live VM - so a Setup-first
 * write arms a timer that does not exist yet and the pad simply sits still.
 * It is also why the BOTOR mixed-state incident left the Timer landed and the
 * Setup missing rather than the reverse. Sequential, one acknowledgement at a
 * time, each under its own pinned step id, so a half-landed write names which
 * half landed.
 *
 * ONE WRITER FOR THREE CLICKS. TRY ON DEVICE, PUT BACK and the skeleton's
 * write-back all come through here; writeBack below is a two-line adapter.
 * The strings go on the wire VERBATIM - never compressed here (07-RESEARCH,
 * the D-10 measurement: cost().used === setupLua.length with reserve 0/0).
 */
export async function writeBoth(
  q: RequestQueue,
  target: WriteTarget,
  s: EventStrings,
): Promise<void> {
  await q.request(
    sendConfig(target.sx, target.sy, target.page, EVENT_TIMER, s.timer),
    "write-timer",
  );
  await q.request(
    sendConfig(target.sx, target.sy, target.page, EVENT_SETUP, s.setup),
    "write-setup",
  );
}

/** Phase 2's caller, unchanged in behaviour, now an adapter. */
export async function writeBack(q, id, f: FetchedPair): Promise<void> {
  await writeBoth(q, targetOf(id), {
    setup: f.setup.actionString ?? "",
    timer: f.timer.actionString ?? "",
  });
}

/** The module's own key, or a throw the caller degrades from (D-04 amended). */
export async function fetchModuleKey(q: RequestQueue, id: Identity): Promise<string> {
  const cls = await q.request(fetchSerialNumber(id.zona.sx, id.zona.sy), "fetch-serial");
  return moduleKeyOf(cls);
}
```

`storeToFlash(q, id)` loses its `if (!id.storeAllowed) throw` and the sentence in its comment that
described it. The replacement paragraph: the store is a global broadcast, every module on the bus
stores its own active page and answers with its own acknowledgement echoing the same `LASTHEADER`;
the queue resolves on the first and the rest are delivered to nobody (`queue.ts` `settle` nulls the
waiter). That is SAFE-06's whole reason for existing and it is a confirmation sentence in Phase 7,
not a refusal. `id` stays a parameter for the step's provenance and for symmetry; say that it is
currently unread rather than leaving a reader to wonder.

**The scripted ZONA, widened** (`src/lib/transport/fixtures/synthetic.ts`):

```ts
export interface ZonaState {
  sx: number;
  sy: number;
  activePage: number;
  /** RAM. What a fetch returns and what a write replaces. */
  configs: Record<number, string>;
  /** Flash. What a store copies configs into and what powerCycle restores. Defaults to a copy of configs. */
  flash?: Record<number, string>;
  /** WORD0..WORD3. Undefined means the module does not answer a SERIALNUMBER/FETCH at all. */
  serial?: readonly [number, number, number, number];
}

export function serialNumberReportFrame(words: readonly [number, number, number, number]): number[];

/** What a power cycle does: RAM becomes flash. Pure, in place. */
export function powerCycle(state: ZonaState): void;

/** Several modules on one cable. Each answers what it accepts; a broadcast is answered by all. */
export function rigResponder(states: ZonaState[]): (outbound, requestId) => number[][];
```

`zonaResponder` gains three branches and one refusal:

- `CONFIG/EXECUTE` with `PAGENUMBER !== state.activePage` returns `configNackFrame({... lastheader:
  requestId})` and writes nothing - firmware's `currentpage` condition, the backstop Pitfall 4 rests on.
- `PAGESTORE/EXECUTE` copies `configs` into `flash` (allocating `flash` on first use) and then, to
  model the Lua VM restart, copies `flash` back into `configs` - a no-op today, and the shape D-12's
  re-fetch proof depends on. Then the ACK.
- `SERIALNUMBER/FETCH` answers only when `state.serial` is set **and** the request's `DX/DY` are the
  module's own address or the global one; the answer is `serialNumberReportFrame(state.serial)`.
- A fetch of a non-active page still answers an empty string (unchanged).

The SX/SY rewrite in `inbound()` applies to the REPORT as to every other frame, so a rig's serial
reports still arrive from `-127,-127`... **no**: firmware builds the REPORT with
`grid_msg_init_brc(..., GRID_PARAMETER_GLOBAL_POSITION, ...)`, so a SERIALNUMBER report genuinely
carries `SX -127, SY -127`. Build it with `encodeOne` **without** the address rewrite, and say in its
comment that this is the one inbound frame HANGAR receives whose source address is deliberately
unusable - which is the wire fact that forces the FETCH to be addressed.
