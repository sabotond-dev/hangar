# Phase 5.1 — UI Design Contract

> Visual and interaction contract for the browse screen: sixteen live pad cards, search, sort,
> tag chips, the front door's entry control, and the detail-and-back journey.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This document EXTENDS `04-UI-SPEC.md` and `05-UI-SPEC.md`. It restates neither, and it amends
> neither.** Tokens, the four type sizes, the two weights, the spacing scale and its three declared
> exceptions, the motion contract, the accessibility contract and every copy rule are Phase 4's and
> Phase 5's, binding here unchanged. **No tenth token. No fourth hue. No new type size. No new
> weight. No new spacing value. No new SVG. No new npm dependency.** Where this phase decides
> something the upstream documents left open it is listed at the bottom.
>
> **`--color-over` does not appear in this phase.** Phase 5 scoped it to exactly three uses, all of
> them the over-budget state of a 908-character meter, and none of those states exists on a browse
> screen. `src/lib/ui/identity.spec.ts` is untouched by this phase.
>
> Binding upstream: `05.1-CONTEXT.md` (D-01..D-19), `.planning/design/FIRST-EXPERIENCE.md`,
> ROADMAP Phase 5.1 success criteria 1–3, REQUIREMENTS CAT-02 and CAT-03,
> `.planning/research/FEATURES.md` §D (D2 search, D3 tag chips, D4 sort, D5 focus view).

## Spacing Scale

Phase 4's tokens, unchanged. The values this phase consumes:

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | Caption → its control in a stacked toolbar band; gap between sort options; gap between tag chips; gap between card tag chips |
| sm | 8px | Featured band → pad; name plate → description; description → resting-black note |
| md | 16px | Pad → name plate; toolbar band → toolbar band; card tag row's top padding |
| lg | 24px | Grid gap; page gutter below 640px |
| xl | 32px | Page gutter at 640px and above; headline → toolbar; result line → grid |
| 2xl | 48px | Header → headline; grid → fidelity line |
| 3xl | 64px | Not used. The Phase 1 footer's existing `mt-16` is untouched |

**Declared non-token values, and why each is not spacing:**

1. **44px** — the interactive box floor, Phase 4 exception 1. Every toolbar control is at least
   44×44: the search field, its `CLEAR`, each sort option, each tag chip, ~~`MORE TAGS`~~ (never
   built — see the amendment at the head of "The tag chips"),
   `CLEAR FILTERS`, `BROWSE ALL` / `BACK TO BROWSE`, and the card's name plate. Card tag chips are
   **not controls** (W-06) and carry no floor.
2. **6px / 10px radii** — Phase 4 exception 3, unchanged. 6px on the name plate, on every chip and
   button and on the search field; 10px on the pad frame and on the card's focus ring.
3. **A 260px minimum card column, a 1280px content cap and a 480px search-field cap.** These are
   viewport-relative layout metrics in the same class as Phase 4's exception 2 (coverflow geometry),
   not spacing. The 260px is not arbitrary: it is the floor of Phase 4's
   `--pad-hero: clamp(260px, 52vmin, 560px)`, so **a browse card's pad is never smaller than the
   smallest hero pad the site ever draws**. The 1280px matches Phase 4's coverflow band cap. All
   three are multiples of 4 anyway.
4. **64px of trailing padding inside the search field**, reserving room for `CLEAR` so typed text
   never runs under it. This is the internal metric of one control, in the same class as Phase 5's
   88px label column, and it is on the 4-point scale.
5. **`padding-inline: 12px` on every toolbar chip and every sort option** — Phase 5's exception 3,
   the *horizontal* internal metric of one control and never a vertical gap. It applies here to the
   two controls Phase 5 already sized that way: the word row's options (which the sort control is,
   verbatim) and the tag chips, which are the same widget in checkbox form. It is on the 4-point
   scale, and **no vertical measurement in this phase is 12px**.

`overflow-x: auto` and `overflow-x: scroll` appear **nowhere** on a browse screen. The toolbar
wraps and the grid reflows; nothing scrolls sideways at any width, in any state. This is a
grep-checkable prohibition, inherited from Phase 5 D-11 and extended to this phase's toolbar.

**Rules this phase adds nothing to, and one it must obey by name:**

- **The search field's text is 16px.** Not because it is Body by taste, but because iOS Safari zooms
  the viewport when a text input smaller than 16px takes focus. Phase 5 made the same declaration
  for the copy-fallback field; this is the second and last text input on the site.
- Uppercase source text carries `text-transform: uppercase` as well, matching every shipped
  component (`FrontDoor.svelte`, `TryOnDevice.svelte`, `CopyLink.svelte`, `BudgetMeter.svelte`).
- "Quiet" is colour, never a smaller size. A card's description is 16px at 55% lime, not 12px.
- Tag text is never re-cased. `xy-control` renders as `xy-control`; upper-casing it would make a
  data value look like a button label.

### Accent — the reserved list, unchanged

Phase 4 reserved six, Phase 5 added two. **This phase adds none and takes none away.** The canonical
list stands at eight. Two of those eight are exercised here:

- **4. The focus ring** — on the search field, on every toolbar control, and on a card (drawn on the
  card, not on the link, so the visible ring matches the clickable area).
- **8. The live value of a control** — a knob's selected value (including the text of a selected
  word-row option), **the selected sort option**, and **a filter chip's active state**. The sort
  control is Phase 5's word-row widget and a tag chip is the same widget in checkbox form, so both
  fall inside the entry that already exists rather than extending it. **The list stays at eight.**

Nothing else on a browse screen is full-strength lime. The `FEATURED` mark is **not** accent
(W-05). A card's name is not accent. A hovered border goes to `--color-line`, never to accent,
**except** the name plate's border on hover, which is Phase 4's own shipped plate-hover behaviour
and is inherited unchanged.

**One declared non-token alpha, reused and not invented.** Phase 5 declared
`rgb(214 255 78 / 0.08)` as a word-row option's **pressed** background — `Knob.svelte`'s
`.option:active`, a background that exists only while a pointer is down. This phase reuses that
exact value as the **selected** background of an active tag chip, which moves it from transient to
**persistent**: the same alpha, held for as long as the filter is on. It is decoration: its meaning
is carried by the accent text and by the control's own `checked` state, and removing it changes
nothing a visitor needs. No token is added for it, exactly as Phase 5 added none.

**The pads are exempt, and the exemption is not widened.** `PadSim` and the Lua engine emit real
firmware RGB, and those pixels are content. A checker looking at a screenshot of `/browse/` will see
sixteen squares full of non-lime colour; that is correct and required by PREV-02. Everything
*around* them stays two-colour. **No CSS on a browse screen authors a colour the simulator did not**
— no gradient over a pad, no tint, no `filter` of any kind on a card or its canvas, and the
brightness ladder that Phase 4 permits on a coverflow slot wrapper does not exist here because
there is no depth ladder to build.

**No third colour earns itself in this phase.** Nothing on a browse screen is dangerous, nothing
writes, nothing fails destructively. The only two states that need a non-default treatment — a
disabled tag chip and an unavailable card — take `--color-ink-dim`, which is already on the ladder
and already above AA.

## Screen 1 — the front door's entry control (D-04)

The front door is unchanged in every other respect: the splash, the coverflow, the headline, the
name plate, the fidelity line, choosing, the panel and every connect state ship exactly as Phases 4
and 5 approved them. One control is added.

### Where it sits

**The header gains a right-hand slot, opposite the wordmark.** The header becomes one row inside
the existing 32px page gutter (24px below 640px):

```
HANGAR                                                            BROWSE ALL
└ Micro, accent, h1, left, not focusable                          └ Micro, ink-quiet, right, 44px
```

`FrontDoor.svelte` today renders `<h1 class="wordmark">` and `<p class="headline">` as siblings with
`padding-inline: 32px`. The wordmark and the new control become a flex row (`justify-content:
space-between; align-items: center; min-block-size: 44px`) carrying that same gutter; the headline's
48px top margin is measured from the row and does not change.

**This is a decision, and open question 1 is still open** (W-01). The alternative D-04 named —
beneath the name plate — is where the chosen panel slides in and where the fidelity line already
sits; a control there would move when a visitor chooses, and would compete with the row's own
navigation. The header slot never moves, exists identically in the un-chosen and chosen states, and
is where a catalog link belongs.

### Treatment

A bare text button, following the shipped `DISCONNECT ZONA` precedent exactly — Phase 4's only other
quiet header-weight control:

| Property | Value |
|----------|-------|
| Element | `<a href="/browse/">` on `/`; a `<button>` on `/c/{id}/` when it carries a recorded return (see Screen 4) |
| Type | Micro — 12px / 600 / 0.18em / UPPERCASE |
| Colour | `--color-ink-quiet` at rest, `--color-ink` on hover, 160ms `ease-out` |
| Box | `min-block-size: 44px; min-inline-size: 44px; display: grid; place-items: center; padding-inline: 0` |
| Border | none. A bordered button in the header would outshout the wordmark |
| Focus | Phase 4's ring, unchanged |

**During the splash it is invisible and does not fade out of visibility.** It carries the wordmark's
exact `.covered` treatment — `opacity: 0; transition: none` while the splash covers the row, then up
to 1 across the 700ms dissolve (200ms under reduced motion) on the same
`cubic-bezier(0.22, 0.61, 0.36, 1)`. It must be absent from the very first painted frame rather than
fading out of one, which is the same reason the wordmark's rule exists.

### Tab order

`BROWSE ALL` is the **first** tab stop on both routes, before the coverflow listbox. Phase 4's order
is otherwise untouched:

> **`BROWSE ALL` / `BACK TO BROWSE`** → coverflow listbox → `◀` → name → `▶` → `TRY ON DEVICE` →
> knob 1 … knob n → `SURPRISE ME` → `RESET ALL` → `TURN IT DOWN` (over budget only) →
> `KEEP ON DEVICE` → `COPY LINK` → copy-fallback field (when revealed) → footer links

It comes first because it is site navigation and it is first in the DOM. Nothing is reordered.

## Screen 2a — the toolbar

One `<search>` landmark wrapping three stacked bands and the count line. The form never submits;
filtering is live. Each band is a **stacked** label-over-control layout at every width — Phase 5's
rule that a word row always stacks so its options get the full content width to wrap into.

### The search field (D-05, FEATURES D2)

| Property | Value |
|----------|-------|
| Caption | `SEARCH`, Micro, `--color-ink-quiet`, a real `<label for>` — never a placeholder |
| Placeholder | **none.** The label says what the field is; a placeholder would duplicate it and then vanish at the moment it was needed |
| Element | `<input type="search" enterkeyhint="search" autocomplete="off" spellcheck="false">` |
| Box | `min-block-size: 44px; max-inline-size: 480px; inline-size: 100%; border: 1px solid var(--color-line); border-radius: 6px; background: transparent; padding-inline: 16px 64px` |
| Text | Body — 16px / 400, `--color-ink`. 16px is the iOS zoom floor and is not negotiable |
| Native cancel | `::-webkit-search-cancel-button { display: none }` so `CLEAR` is the only clear control on the field |
| Clear | `CLEAR`, Micro, `--color-ink-quiet` → `--color-ink` on hover, a 44×44 `<button aria-label="Clear the search">` positioned at the field's trailing end, **rendered only while the query is non-empty**. The visible word stays `CLEAR`; the accessible name is `Clear the search`, because `CLEAR` on its own does not say what it clears once a screen reader has moved past the `SEARCH` label. On click it empties the query and **returns focus to the field** |
| `Escape` | While focus is inside the field, `Escape` clears the query and keeps focus in the field. Pressed anywhere else on the page it does nothing — scoping it to the field is what keeps it from ever colliding with Phase 4's `Escape` (un-choose), which lives on a different route |
| Focus | Phase 4's ring |

**Matching.** Substring, over the entry's `name`, `description` and its `tags` joined into one
haystack, with **both sides folded identically**: lower-cased, then `normalize("NFD")` with
`\p{Diacritic}` stripped. D-15 asks for case **and** diacritic folding, and folding only one of the
two is the bug that ships — `Zóna` must find `zona` and `zona` must find `Zóna`. The query is then
trimmed and **whitespace splits it into terms; every term must match** the haystack. That term
split is **an addition beyond the feature research's single-substring match** (FEATURES D2), and it
is what makes `ghost loop` find GHOST while a single-substring matcher would not. No `$` power
syntax (D-05 and FEATURES D2 both refuse it). Filtering is synchronous on every keystroke — sixteen
entries cost nothing and a debounce would make the grid feel broken. Only the *announcement* and
the *URL write* are debounced.

### The sort control (D-02, D-10, CAT-02)

**It is Phase 5's word-row widget, unchanged in markup and behaviour**: a `role="radiogroup"` built
from real `<input type="radio" name="sort">` inside `<label>`s, one tab stop, `←` `→` `↑` `↓` move
*and* select, `flex-wrap: wrap; gap: 4px`, each option in a 44px-tall box with 12px inline padding.
Reusing the knob vocabulary for a page control is deliberate: the site has one way of showing "this
is the live value", and this is it.

| | |
|---|---|
| Caption | `SORT`, Micro, `--color-ink-quiet`, `aria-labelledby` on the group |
| Options | `FEATURED` · `NEWEST` · `NAME` — **Micro**, uppercase, not Micro (title) |
| Selected | `--color-accent` (accent reserved-list entry 8, no addition) |
| Unselected | `--color-ink-quiet` |
| Hover | unselected → `--color-ink`, 140ms `ease-out` |
| Default | `FEATURED` |

The one difference from a knob's word row is the case: these are one-word page-control labels, not
values, and uppercase is what tells a visitor that `NAME` reorders the page while `Major` names a
scale. It stays inside Phase 4's uppercase rule because each is a control label.

**The three orders, exactly — and they are the shipped comparators in `src/lib/catalog/index.ts`,
restated over `ListingEntry` in the browse module and gated against the shipped comparators' output — the browse page never imports `$lib/catalog`, and `nameAsc` is not exported (D-10 as amended, D-12):**

| Option | Order | Shipped comparator |
|--------|-------|--------------------|
| `FEATURED` | `featured` true first, then name ascending | `byFeatured()` — `Number(b.featured) - Number(a.featured) \|\| nameAsc(a, b)` |
| `NEWEST` | `addedAt` descending, then name ascending | `byNewest()` |
| `NAME` | name ascending | `nameAsc` |

**`addedAt` is not a tie-break inside `FEATURED`.** Featured first, then name, and nothing between
them — that is what `byFeatured()` does today. Only two distinct `addedAt` values exist across the
sixteen entries, so a date tie-break inside the featured group would have been a coin toss dressed
as an order.

**"Name ascending" is `nameAsc`** — a plain code-point `<` / `>` comparison over `entry.name`,
exactly as the shipped file defines it, and that file's comment is the reason: *the order a page
renders must not depend on the runner's or the visitor's locale.* **No `localeCompare`, pinned or
otherwise, appears anywhere in this phase.** On the sixteen shipped names the code-point order and
an English collation agree entry for entry — `ARC` before `Aurora` (`R` < `u`), `SONAR` before
`Starfield` (`O` < `t`) — because no two names differ only in case, so there is nothing to buy by
diverging. Every sort is total and stable: each comparator ends on the name, and no two entries
share one.

**No popularity metric is shown or faked, anywhere on this page.** There is no like count, no view
count, no "popular", no "trending", no "top", no "most", and no bare number beside a tag that could
be mistaken for one (W-04).

> visible: `36 of 36 configurations.` · `4 of 36 configurations.` · `1 of 36 configurations.`

## Screen 3 — keyboard and the grid

### The pattern, and the accessibility reason for it

**A plain `<ul>` of `<li>`, each holding one real `<a>`, with a roving tabindex over the links.**
Not `role="listbox"`, not `role="grid"`.

> A browse card is a **link to a real prerendered URL**. That is the site's entire shareability
> story: middle-click to open in a new tab, right-click to copy the address, and — the one that
> decides it — a screen reader's links list, which is how a non-sighted visitor surveys a page of
> sixteen destinations. `role="option"` and `role="gridcell"` both **replace** the link role, and
> both destroy all three. Phase 4 was right to make the coverflow a `listbox`, because a coverflow
> *selects a centred value*; a grid of links *navigates*, and the two want opposite semantics.

Roving tabindex is what buys back what a listbox would otherwise have given: exactly **one** card is
tabbable at a time (`tabindex="0"` on the roving card's link, `-1` on the other fifteen), so `Tab`
crosses the whole grid in one press and reaches the fidelity line and the footer, instead of
seventeen presses.

| Input | Behaviour |
|-------|-----------|
| `Tab` into the grid | Focus lands on the roving card — the first card, or the last one focused |
| `←` / `→` | Move focus one card in reading order. Does **not** wrap; the ends are the ends |
| `↑` / `↓` | Move focus one row, by the live column count |
| `Home` / `End` | First / last card |
| `Enter` | Follows the link. **Native — no handler.** |
| `Space` | **Not hijacked.** It scrolls the page, which is what a visitor on a long grid expects |
| Any arrow with a modifier held | Not intercepted, so `⌘←` / `Alt+←` still means Back |

The column count is read from the layout rather than from a media query:
`getComputedStyle(list).gridTemplateColumns.split(" ").length`. It is the only source that cannot
disagree with what is on screen. **Clamp it to at least 1.** On a list that has not been rendered —
hidden, detached, or measured before first paint — the property returns the string `"none"`, which
splits to a length of 1 by accident rather than by design; the contract is `Math.max(1, …)`, treated
explicitly as one column, because an `↑` / `↓` step divides by this number.

When a filter changes the set and the roving card is no longer present, **the roving index resets to
the first card and focus is not moved** — stealing focus out of the search field on a keystroke would
make the field unusable.

### Complete keyboard journey

> `Tab` to `BROWSE ALL` on `/` → `Enter` → on `/browse/`, `Tab` to the search field → type → `Escape`
> to clear → `Tab` to the sort group → `←` `→` to reorder → `Tab` through the tag chips → `Space` to
> filter → `Tab` to `CLEAR FILTERS` → `Tab` into the grid → arrows to a card → `Enter` to open →
> `Tab` to `BACK TO BROWSE` → `Enter` → back where you were.

Every capability on this screen is reachable with no pointer at all.

which it would work, and there is none. See W-09 and morning question 2 — this is the tension
CONTEXT's own open question 2 names.

**The quiet note for an off-row entry.** `FRONT_DOOR` carries the per-entry `motion` and `quiet`

resting-black note when `entry.restsBlack` is true, and nothing otherwise**. That covers Trackpad,

asserted against `frames.json`. The three still-but-lit entries (Nine pads, Joystick, Four faders)
are all in the row and keep their existing lines.

> **Engineering hazard the planner must resolve, recorded here because it is a visible failure.**
> `05-SUMMARY` records that `buildTuner`'s `destroy()` closes the engine the coverflow also holds,
> and that this is harmless only while every Lua entry stays out of `FRONT_DOOR`. On `/c/euclid/`
> the row holds EUCLID alone, so **un-choosing would close the VM behind the only pad on the page
> and blank it.** The contract is simply that it must not: un-choosing a Lua entry leaves its pad

### `BACK TO BROWSE`

**It is the same header slot, with a different label.** The right-hand slot on `/c/{id}/` always
holds exactly one control:

| Condition | Label | Action |
|-----------|-------|--------|
| A browse return is recorded | `BACK TO BROWSE` | Returns to the recorded browse URL with sort, query, tags and scroll restored |
| No browse return is recorded | `BROWSE ALL` | Navigates to `/browse/` fresh |

Same Micro / `--color-ink-quiet` treatment, same 44px box, same first position in the tab order,
same place on the screen. A visitor arriving cold from a shared link is never left without a route
into the catalog; a visitor who came from browse always gets their own view back. **It never sits
near the name plate or `TRY ON DEVICE`** — it is header chrome, it does not move when the panel
opens, and it cannot be confused with an install control.

`BACK TO BROWSE` is three words and uppercase, which is inside Phase 4's rule: uppercase is for
button labels of any length and captions of at most two words.

### What "recorded" means, and what comes back

One `sessionStorage` record under the key **`hangar:browse-return`**, written by `/browse/`
immediately before it navigates to a `/c/…` route, holding:

| Field | Restored as |
|-------|-------------|
| `href` | The full browse URL, including `?sort=`, `?q=` and every `?tag=` |
| `scrollY` | The browse page's scroll offset, restored on mount |

- **`sessionStorage`, so a middle-click into a new tab gets no record** — in a new tab there is
  nothing to go back to, and offering it would be a lie.
- **The URL is flushed synchronously before the navigation.** The browse page's query string is
  written on a 500ms trailing timer, so without an explicit flush a card clicked 200ms after a chip
  toggle would record a stale view.
- Returning uses `replaceState` with `noScroll`, so browse → detail → back reads as one round trip
  rather than growing the history, and the browser's own Back from the restored browse page goes to
  wherever the visitor was before browse.
- The record survives a reload of the detail page (a virtue: the way back is still there) and is
  cleared when the visitor navigates away from the detail route to anything that is not `/browse/`.
- Stepping the row with `◀` / `▶` uses `replaceState` and never leaves the route, so the record
  survives stepping — which is correct: the visitor still came from browse.

Success criterion 3 is met exactly: *open any configuration's focus view and return to browse
without losing position.*

## URL-visible state (D-05)

```
/browse/?sort=newest&q=ghost&tag=gestural&tag=generative
```

| Key | Values | Omitted when |
|-----|--------|--------------|
| `sort` | `featured` \| `newest` \| `name` | it is `featured` (the default), so the plain `/browse/` is the canonical entry |
| `q` | the raw query, URL-encoded | it is empty |
| `tag` | repeated once per active tag, in activation order | none is active |

- **`replaceState` only, never `pushState`.** A history entry per keystroke would trap the Back
  button — the same reason Phase 4 steps the coverflow with `replaceState`.
- Written on a **500ms trailing timer, shared with the announcement**, so a burst of typing or a run
  of chip toggles writes once. Flushed synchronously before any navigation away from `/browse/`.
- **Read on arrival**, so a browse view is a linkable thing. An unknown `sort` falls back to
  `featured`; an unknown `tag` is dropped silently and does not render a chip. No notice is shown
  for a dropped tag: unlike a tuning stamp, the visitor did not author it and there is nothing for
  them to do, and the count line already tells the truth (W-12).
- The tuning stamp stays in the **hash** on `/c/{id}/` and is untouched. D-05's ruling stands: the
  query-string ban applies to the stamp alone.

| Thing | Full motion | Reduced |

The table is short because the decision above made it short: the only motion on a browse screen is

## Copywriting Contract

Phase 4's rules, verbatim: mixed case for sentences, wide-tracked uppercase for button labels and
captions of at most two words, no emoji, no exclamation marks, real apostrophes (`’`, U+2019), a real
ellipsis (`…`, U+2026), a real em dash (`—`, U+2014). Never "Error", never "loading". **No string
names a control that is not on the screen.**

**One rule this phase adds:** quotation marks around a visitor's own query are real typographic
double quotes (`“`, U+201C and `”`, U+201D), never `"`. It is the same discipline the apostrophe rule
already imposes.

"trending", not "top", not "most", not "best", not a like count, not a view count, and not a bare
number beside a tag that could be read as one. CAT-02 and D-02 both require it, and the disabled-chip

## Data corrections this phase requires

Three catalog descriptions carry an ASCII apostrophe, and this phase is what puts them on screen: a
card renders `entry.description`, so a straight `'` would print the one punctuation mark Phase 4's
copy rules forbid. Two are HANGAR-owned and are corrected at source; the third is Radar's sentence,
which is vendored copy (`src/vendor/botor/_pad.ts` `preset.sentence`, mirrored byte-equal in
`front-door.ts` and held equal by `catalog.spec.ts` and `front-door.spec.ts`). **Vendored source is
never edited** (Phase 3's D-04; `vendored-diff.spec.ts`), so the contract rules a display-time
transform instead of a data edit for that case:

| Source | Now | Ruling |
|--------|-----|--------|
| `src/lib/catalog/entries/ghost.ts` | `…a colour that is not your finger's.` | Corrected at source to `finger’s` in the plan that gives the Lua entries their pages |
| `src/lib/catalog/entries/morph.ts` | `…and each corner's brightness is its own weight.` | Corrected at source to `corner’s` in the same plan |
| Radar — `src/vendor/botor/_pad.ts` (vendored), mirrored in `front-door.ts` and the listing | `…the pad sends your finger's position to your computer.` | **Not edited.** Rendered through the display transform below, so the card shows `finger’s` while every equality gate keeps matching the vendored bytes |

**The display transform.** Every description a browse card or a detail page renders passes through
one pure function, `typographic(text)`, that replaces an ASCII apostrophe standing between two
letters with U+2019 and touches nothing else (no quotes, no ellipses, no dashes — those are already
authored correctly). It is applied at render time only; `entry.description`, `listing.ts`,
`front-door.ts` and the OG/meta descriptions stay byte-equal to their sources, and a unit test pins
the three shipped cases plus a no-op case. Nothing compiled changes: descriptions are metadata,
never Lua, so **the character budgets, the `compressScript` fixed points, `frames.json` and every
gate that hashes a rendered pad are unaffected**. The two source corrections are still required —
the transform is the safety net for vendored copy, not a licence to author ASCII apostrophes.

| W-20 | **The browse return is one `sessionStorage` record under `hangar:browse-return`, flushed synchronously before navigating, restored with `replaceState` and `noScroll`** | A middle-click into a new tab correctly gets no back control; the flush exists because the URL is written on a 500ms trailing timer and a card clicked 200ms after a chip toggle would otherwise record a stale view |
