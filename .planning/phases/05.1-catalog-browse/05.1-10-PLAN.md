<objective>
Prove the browse screen in a real browser, against the deployed bytes.

Wave 10. Seven tests, all in the chromium project, all against `build/` served by `worker/index.js`
under `wrangler dev` — never a dev server and never `vite preview`, which boots the Node server from
`.svelte-kit/output/server` and never reads `build/` at all.

**Two of the seven are the ones worth arguing about.**

The **laziness test cannot be a plain cold load**, and getting that wrong would produce a test that
fails for a good reason. D-06 asks for "a cold `/browse/` with no Lua card in view fetches no
WebAssembly" — but with the default Featured sort the first screenful contains several Lua cards, so a
genuine cold `/browse/` at the top of the page *will* fetch the VM, correctly and immediately. The
honest claim is *a visitor who never brings a Lua card into view never downloads the VM*, and the
honest test is a filtered load: `/browse/?q=aurora` (aurora is `padsim`), assert **zero** `.wasm`
responses, then clear the filter and assert the VM arrives. Write the query and the reason into the
test.

The **frame budget is recorded, not gated**. `.planning/research/STACK.md`'s own estimate — 10-16
concurrently visible animating cards before stutter with the vendored `blit`, 30+ after the two fixes
HANGAR already ships — is explicitly marked unverified, and this phase does not turn an unverified
estimate into a threshold. Count the paints, record the number and the visible-card count, and **do
not tune anything**. If it stutters, the first lever is the column count on a phone; it is never
`SIDE_INTERVAL_MS`, which `schedule.spec.ts` pins against the vendored host.

Purpose: CAT-02 and CAT-03 observed rather than asserted from source.
Output: one new e2e file with 7 tests, and one recorded measurement.

<interfaces>
**The seven tests, in this order and with these titles.** Helpers (`sample()`, `waitForPicture()`, the
console-error collector, the `.wasm` response watcher) are the proven shapes in
`e2e/first-experience.e2e.ts` and `e2e/catalog.e2e.ts` — import or re-derive them, never invent a
third way to read a canvas.

1. **"the browse screen lists every configuration with its own description"** — `goto("/browse/")`,
   wait for `browse-grid`, assert sixteen `card-*` elements, assert each carries a non-empty
   description and at least one tag, assert no two descriptions are equal, and assert the count line
   reads `16 of 16 configurations.` The sixteen expected ids come from `src/lib/catalog/listing.ts`,
   imported into the test, so the file and the catalog cannot drift.
2. **"sorting reorders the grid and the address"** — for each of the three options: click it, assert
   the address now carries the expected `?sort=` (and that `FEATURED` produces **no** `sort` key,
   since it is the default and a plain `/browse/` is canonical), and assert the rendered id sequence.
   For `NEWEST` assert **the block boundary** — every `2026-09-04` id before every `2026-09-02` id —
   and never a strict sixteen-element sequence, which would be brittle the day one date changes. For
   `NAME` and `FEATURED` the sequence is deterministic, so assert it in full and quote it in the
   SUMMARY.
3. **"searching and tag chips narrow the grid, and CLEAR FILTERS brings it back"** — type a word,
   assert the count line and the rendered cards; press two chips, assert the intersection; assert at
   least one chip has gone `disabled`; press `CLEAR FILTERS`, assert sixteen cards, assert the address
   is back to a bare `/browse/`, and assert **the sort was not reset**.
4. **"a filtered link renders its own set on the first paint"** — this must be a **cold arrival**, not
   a client-side transition: go to `about:blank` first, then `goto("/browse/?sort=name&tag=playable")`.
   Assert the toolbar shows `NAME` selected and the chip active, and that the grid holds exactly the
   four `playable` configurations — asserted **before** any interaction, so a client-side correction
   after paint would not save it.
5. **"reduced motion stills every card"** — `page.emulateMedia({ reducedMotion: "reduce" })` then a
   cold load; sample two canvases 400 ms apart and assert **identical** pixels; assert the pads are not
   blank (a still frame at tick 64 is a picture, and an all-black sample would pass a
   sameness assertion for the wrong reason — exempt the three declared `restsBlack` entries by reading
   `restsBlack` from the listing, never by naming them).
6. **"the cards animate, and the paint count over two seconds is recorded"** — install the
   `putImageData` counter with `addInitScript` (the shape `e2e/first-experience.e2e.ts` uses), cold
   load `/browse/`, sample an animated card's canvas 400 ms apart and assert the two differ, then read
   the counter after two seconds and **record** it with the viewport, the visible-card count and the
   count of cards whose engine had been built. Assert only `> 0`; the number is evidence, not a gate.
7. **"a browse view with no Lua configuration in it fetches no WebAssembly"** — attach the `.wasm`
   response watcher, cold `goto("/browse/?q=aurora")`, wait for the single card's canvas to have a
   picture, `waitForLoadState("networkidle")`, and assert the collected `.wasm` list is **empty**.
   Then clear the filter, scroll a Lua card into view, and assert a VM `.wasm` arrives with status 200
   and content type `application/wasm` — a wrong MIME breaks nothing visibly and then runs the slow
   path forever, which is why it is asserted rather than assumed. Discriminate the VM from the
   formatter by the **absence** of `lua_fmt_bg` in the URL, exactly as `e2e/catalog.e2e.ts` does, so a
   Vite hashing change cannot turn this red for the wrong reason.

Console errors are asserted empty in at least tests 1, 4 and 7.
