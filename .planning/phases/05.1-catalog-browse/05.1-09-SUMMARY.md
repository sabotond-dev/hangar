## Deviations from Plan

### 1. [Rule 1 — bug] The record is cleared from `beforeNavigate`, not `afterNavigate`

The plan's task 3 says *"Add the record-clearing `afterNavigate` to the detail route."* It was
built that way first, and **it is a no-op for the only case it exists for.**

Kit registers both hooks through the same helper (`client.js:2240-2248`):

```js
function add_navigation_callback(callbacks, callback) {
	onMount(() => {
		callbacks.add(callback);
		return () => { callbacks.delete(callback); };
	});
}
```

The teardown runs while the *new* page renders, which is before `client.js:2042` walks
`after_navigate_callbacks`. So a callback registered in `/c/[id]/+page.svelte` fires for a hop from
`/c/euclid/` to `/c/aurora/`, where the component survives — and never for a departure that unmounts
it.

Measured on a served production build, `/` → `/browse/?q=euclid` → `/c/euclid/` → `history.go(-2)`,
which is one navigation straight past browse to the front door:

| | with `afterNavigate` | with `beforeNavigate` |
|---|---|---|
| landed on | `/` | `/` |
| the header slot then read | **`BACK TO BROWSE`** | `BROWSE ALL` |
| the record | `{"href":"/browse/?q=euclid","scrollY":507}` | **`null`** |

The `afterNavigate` column is the front door offering a way back to a view the visitor has already
left. `beforeNavigate` fires while the component is still mounted, so it fires.

**What `beforeNavigate` costs and how it is paid.** It also fires for navigations that leave the app —
a reload, an address-bar hop, a closed tab — which carry `willUnload` and a null `to`. Those are
skipped deliberately, because 05.1-UI-SPEC.md requires a reload of the detail page to **keep** the
record, and a reload is indistinguishable from an address-bar hop from inside the page. The tie is
broken in the visitor's favour. Step 5 of the journey confirms the reload virtue survived.

### 2. [Rule 1 — bug] `BACK TO BROWSE` drops `replaceState: true`

05.1-UI-SPEC.md's *What "recorded" means* says *"Returning uses `replaceState` with `noScroll`, so
browse → detail → back reads as one round trip rather than growing the history"*, and `return.ts`'s
header repeats it. **Plan 05.1-09's own interfaces table asks for `goto(record.href, { noScroll: true })`
and nothing else**, and the plan is right.

With `replaceState: true`, on Kit 2.70.3:

- `navigate()` at `client.js:1874` does `const change = replace_state ? 0 : 1` and then bumps **both**
  the history index and the **navigation** index by `change` — so a replacing navigation leaves
  `current_navigation_index` exactly where it was.
- the popstate handler at `client.js:2886` decides whether a Back is a real navigation with
  `navigation_index === current_navigation_index && (has_navigated || is_hash_change)` and takes a
  **shallow** branch when that holds: it sets `page.state`, calls `update_url(url)`, restores scroll,
  and renders nothing.
- `Coverflow.choose()`'s `pushState` is what lines the two indices up, because a shallow push does not
  bump the navigation index either.

Observed on a served production build, `/browse/?q=ghost` → `/c/ghost/` → tap the pad →
`BACK TO BROWSE` → the browser's Back:

```
D returned    | url: /browse/?q=ghost | front-door: 0 | browse: 1     (correct, both builds)
E back +500ms | url: /c/ghost/        | front-door: 0 | browse: 1     <- with replaceState
E back +5000ms| url: /c/ghost/        | front-door: 0 | browse: 1     <- still, five seconds later
E back +500ms | url: /c/ghost/        | front-door: 1 | browse: 0     <- without it
```

The address bar reads `/c/ghost/` while the browse screen is on the page, permanently, and a reload
from there would swap the page under the visitor. **The price of dropping `replaceState` is one
history entry per round trip** — measured, `history.length` 4 → 5 — which is what makes step 4's
"no history growth" expectation unmeetable. An address bar that lies about what is on screen costs
more.

The spec sentence should be amended; it is logged in `deferred-items.md` so the phase gate does not
read it and re-implement the bug.

### 3. [Rule 3 — blocking] The `goto` argument is rebuilt through `resolve()`

`goto(record.href, …)` is red under `svelte/no-navigation-without-resolve`, observed:

```
src/lib/ui/BrowseLink.svelte
  113:15  error  Unexpected goto() call without resolve()  svelte/no-navigation-without-resolve
```

The rule accepts a `resolve()` call or a value whose **type** is structurally `ResolvedPathname`
(`no-navigation-without-resolve.js`, `expressionIsAllowedType`, which tests assignability in both
directions and therefore rejects `string` and even `Pathname`). `record.href` is a `string` parsed
out of JSON and every route to making it a `ResolvedPathname` needs a cast, which the plan forbids
alongside suppressions. So the recorded **query** is carried across and the **path** is the
component's own literal:

```ts
    const mark = target.href.indexOf("?");
    const search = mark === -1 ? "" : target.href.slice(mark + 1);
    if (search === "") void goto(resolve(BROWSE_PATH), RETURN_OPTIONS);
    else void goto(resolve(`/browse/?${search}`), RETURN_OPTIONS);
```

Two statements rather than one ternary argument, because the rule reads the call expression it is
handed — the same shape `/browse/` uses for its own address writes. **It is also a safety
improvement** and is documented as one: a record poisoned by anything else in the origin can no
longer navigate a visitor to an address of its choosing; the worst it can do is put a nonsense query
on `/browse/`, which W-12's silent fallback already absorbs.
