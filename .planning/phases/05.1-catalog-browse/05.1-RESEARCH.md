## Summary

Phase 5.1 is not really a "build a grid page" phase. Building the grid is the small half: `SimHost`, `PadFrame`, `PadCanvas`, `createEngine`, `slots.ts` and `frames.json` already do everything a live card wall needs, and `src/routes/dev/catalog/+page.svelte` is already a working precedent for mounting Lua cards behind a dynamic import. The large half is that **D-07 widens `/c/[id]/`'s `entries()` from 8 to 16, and that single change breaks or silently blinds four shipped gates** — `e2e/first-experience.e2e.ts` (which explicitly asserts `/c/euclid/` returns **404**), `src/lib/og/build.spec.ts` (which would stay green while eight new pages point at eight missing OG images), `scripts/gen-og.mjs` (which reads `FRONT_DOOR`), and `src/lib/config-shape.spec.ts` test 14 (whose artefact scan covers only `build/index.html` and `build/c/aurora/index.html`, so it cannot see a heavy `/browse/` chunk at all).

The controlling technical constraint is the 131,101-byte protocol chunk. `src/lib/catalog/index.ts` reaches `@intechstudio/grid-protocol` through exactly one runtime edge — `src/lib/catalog/entries/ported.ts:13`'s `import { presetById } from "../../../vendor/botor/_pad"` — so any page that statically imports `$lib/catalog` puts the whole compiler on its critical path. `/browse/` needs sixteen names, descriptions, tags, dates and Featured flags **in its prerendered HTML**, which is precisely the situation `src/lib/catalog/front-door.ts` was invented for. The answer is a sibling of that file: a new import-free `src/lib/catalog/listing.ts` holding all sixteen, gated against `CATALOG` by strict equality and against `frames.json` for motion — the `protocol-pin.ts` / `front-door.ts` / `share/url.ts` pattern, used a fourth time. The same module is what `/c/[id]/+page.ts`'s widened `entries()`, `scripts/gen-og.mjs` and `src/lib/og/build.spec.ts` should read.

Routing is settled by two facts read out of the installed Kit source rather than from documentation. First, `disable_search()` is applied to `event.url` during prerendering and `render.js` hands that same URL to the page store, so **`page.url.searchParams` throws during prerender** — the query string may only be read behind a `browser` guard or in `onMount`. Second, `pushState`/`replaceState` from `$app/navigation` update `page.state` but **do not update `page.url`** (they only call `history.replaceState`), while a *popstate* back **does** update it. Therefore browse state must live in a local `$state` seeded once from `page.url` at component init, with the query string written back as a projection via shallow `replaceState` — never as a reactive source. And `resolve()`'s type is `T extends RouteIdWithSearchOrHash | PathnameWithSearchOrHash`, so `resolve(\`/browse/?${qs}\`)` both type-checks and satisfies `svelte/no-navigation-without-resolve` with no suppression.

**Primary recommendation:** Add `src/lib/catalog/listing.ts` (import-free, all sixteen entries, spec-gated against `CATALOG` and `frames.json`) first; make it the single source for `/browse/`, for `/c/[id]/`'s widened `entries()`, for `gen-og` and for `build.spec.ts`. Then build `/browse/` as a prerendered page whose sort/query/tag state is a local rune seeded once from `page.url.searchParams` under a `browser` guard and projected back into the URL with shallow `replaceState`. Reuse `SimHost` unchanged with `setHero(undefined)` (every card paints at the 50 ms side rate) and add exactly one host method: `repaintAll()`.

### Pattern 1: The light listing module (the phase's keystone)

**What:** `src/lib/catalog/listing.ts` restates, for all sixteen entries, exactly what a listing needs — `id`, `name`, `description`, `tags`, `featured`, `addedAt`, `restsBlack`, `motion`, `quiet?` — and **imports nothing at runtime**.

**Why:** `src/lib/catalog/entries/ported.ts:13` is the one runtime edge from the catalog to the vendored tree (`import { presetById } from "../../../vendor/botor/_pad"`), and `_pad.ts` imports `@intechstudio/grid-protocol` at module scope — a **131,101-byte** chunk. `src/lib/catalog/types.ts`'s only `_pad` import is `import type`, which is erased. So `$lib/catalog` is heavy solely because of that one line, and a prerendered page that statically imports it puts the compiler on its first paint. This is the identical situation `front-door.ts` documents in its own header, and the identical answer.

**When to use:** any prerendered page that needs catalog metadata at first paint.

```typescript
// src/lib/catalog/listing.ts  (shape only)
//
// This module imports NOTHING at runtime, and listing.spec.ts asserts it.
// The one permitted import is `import type`, which is erased at build time.
import type { FrontDoorEntry, PreviewMotion } from "./front-door";

export type ListingEntry = FrontDoorEntry & {
  readonly tags: readonly string[];
  readonly featured: boolean;
  /** "YYYY-MM-DD". */
  readonly addedAt: string;
  readonly restsBlack: boolean;
};

export const LISTING: readonly ListingEntry[] = [ /* 16 records */ ];

export function listingIndex(id: string): number { /* -1 for unknown */ }
export function listingById(id: string): ListingEntry | undefined { /* ... */ }
```

`import type { FrontDoorEntry } from "./front-door"` is the correct direction: `front-door.ts` stays byte-untouched and still declares no imports, so its own last spec ("front-door.ts declares no imports") stays green.

**The gate (`listing.spec.ts`), five tests, all in the house style:**

1. Every listing record's `id/name/description/tags/featured/addedAt/restsBlack` is **strictly equal** to `byId(id)`'s, and the id sets are identical. (Non-vacuity: assert `LISTING.length === CATALOG.length` and `> 0` first.)
2. `motion` equals the derivation over `frames.json`: `restsBlack → "dark"`, else `some(animating) → "animated"`, else `some(nonZeroBytes > 0) → "static"`, else `"dark"`. Assert both directions.
3. Every non-`"animated"` entry carries a non-empty, single-line `quiet`; for the eight row entries the `quiet` string is **byte-equal to `FRONT_DOOR`'s**, so the two files cannot drift.
4. `LISTING` ids partition into `FRONT_DOOR` ∪ `EXCLUDED_FROM_ROW` — the same partition assertion `front-door.spec.ts` already makes against `CATALOG`, restated here so a new entry that lands in neither is red twice.
5. The source scan: read `listing.ts`, strip comments, collect `from "..."` specifiers, and assert every one is a **type-only** import (`import type`) and that none contains `vendor`, `intechstudio`, `lib/pad`, `lib/catalog`, `./index`, `./entries`, `sim/`, `pad-sim` or `wasmoon`. Assert the walk was non-empty first.

**New copy required (author it, do not derive it):** GHOST, MORPH and TPAD need `quiet` lines (they are `"dark"`), and any Lua entry whose `frames.json` record is `"static"` would need one too — none is today. GHOST's line must say the pad is a recorder that stays dark until you play into it; MORPH's must say its light is a response to a finger; TPAD's already has a documented reason in `EXCLUDED_FROM_ROW`. These are the only three new sentences the data layer needs.

### Pattern 2: Query state as a projection, never as a source

**What:** the browse page's `sort`, `q` and `tags` live in local `$state`, seeded **once** at component init from `page.url.searchParams` behind a `browser` guard, and written back to the address with shallow `replaceState`.

**Why (both halves verified against installed Kit source):**

- `node_modules/@sveltejs/kit/src/runtime/server/respond.js:433-434` calls `disable_search(url)` when `state.prerendering`, and `.../utils/url.js:174-188` defines properties `search` and `searchParams` that **throw** `"Cannot access url.searchParams on a page with prerendering enabled"`. `.../server/page/render.js:185` sets the page store's `url` to that same `event.url`. So reading `page.url.searchParams` in a component during prerender is a build failure.
- `client.js:2504-2540` (`pushState`) and `2551-2581` (`replaceState`) set `page.state` and re-clone `page`, but never touch `page.url`; they call `history.pushState/replaceState(..., resolve_url(url))`. **`page.url` is not updated by shallow navigation.** A `$derived` over `page.url.searchParams` would therefore go stale the instant the first filter is applied.
- `client.js:2871-2905` (popstate, shallow branch) *does* call `update_url(url)` and restores `scroll_positions[history_index]`. So `page.url` is asymmetric: stale on write, fresh on back. Driving state from it would be a latent bug.

```svelte
<script lang="ts">
  import { browser } from "$app/environment";
  import { replaceState } from "$app/navigation";
  import { resolve } from "$app/paths";
  import { page } from "$app/state";
  import { untrack } from "svelte";
  import { parseBrowseQuery, serialiseBrowseQuery, DEFAULT_QUERY } from "$lib/browse/query";

  // Read ONCE, at component init, and only in the browser. untrack is the same
  // idiom Coverflow.svelte uses for initialId: capturing only the initial value
  // is exactly what is wanted.
  const seed = () =>
    browser ? parseBrowseQuery(page.url.searchParams) : DEFAULT_QUERY;

  let sort = $state(untrack(seed).sort);
  let q = $state(untrack(seed).q);
  let tags = $state(untrack(seed).tags);   // string[]; a plain array of strings is fine in a rune

  let mounted = false;   // replaceState throws before the router is initialised

  // The URL is a PROJECTION of the state, written on change and never read again.
  // replaceState and never pushState: sixteen chip presses must not need sixteen
  // Back presses. Same rule as Coverflow.syncAddress().
  function syncAddress(): void {
    if (!mounted) return;
    const search = serialiseBrowseQuery({ sort, q, tags });
    // resolve() accepts a pathname WITH a search string (PathnameWithSearchOrHash),
    // so this is lint-clean with NO suppression and NO cast.
    replaceState(search === "" ? resolve("/browse/") : resolve(`/browse/?${search}`), page.state);
  }
</script>
```

**Anti-pattern:** `const params = $derived(page.url.searchParams)`. It throws at build time and it is stale at run time.

### Pattern 3: One `row` prop turns the coverflow into a detail view

**What:** `Coverflow.svelte` gains `row: readonly FrontDoorEntry[] = FRONT_DOOR`. `/c/[id]/+page.svelte` passes `FRONT_DOOR` when the id is in the row (byte-identical behaviour to today) and a **one-entry row** built from `LISTING` otherwise.

**Why it works, verified by reading `src/lib/coverflow/slots.ts`:** `visibleWindow(centre, radius, 1)` computes `span = Math.min(2*radius+1, count) = 1`, `first = 0`, and returns `[0]`. `step(0, ±1, 1)` returns `0`. `slotOffset(0, 0, 1)` returns `0`. A one-element ring is well-defined at every call site, so a solo pad renders as the hero at slot 0 and stepping is a no-op. Every downstream component — `NamePlate`, `FidelityLine`, `ChosenPanel`, `TuningRegion`, `CopyLink`, `TryOnDevice` — takes a `FrontDoorEntry` and needs no change at all. The tap-to-choose rule, the `pushState({chosen:true})` history entry, Escape, the stamp landing and `replaceEngine` all keep working untouched.

**The two consequential edits:**

1. `Coverflow.svelte` currently hard-references `FRONT_DOOR` in eleven places (`COUNT`, `heroId()`, `centred`, `inWindow`, `syncHost`, the engine loop, `adopt` loop, the `{#each}`). All become `row`. `openingCentre()` must use an index into `row`, not `frontDoorIndex()`.
2. `NamePlate.svelte` renders prev/next triangles. With `row.length === 1` they are dead controls. Add a `solo?: boolean` prop (or derive from a `count` prop) that hides them. This is a deliberate touch of a Phase-4 component — small, and it must be recorded as such in the plan.

**What NOT to do:** do not make `/c/<id>/` render a sixteen-entry ring. D-04 keeps the row's curation untouched, and widening the ring would visibly change `/c/aurora/` — a signed-off Phase 4 route — for no requirement.

### Pattern 4: Three total-order sorts and one folded search, all pure

**What:** `src/lib/browse/sort.ts` and `filter.ts` are pure functions over `readonly ListingEntry[]`, tested in the `server` Vitest project with no DOM — the `slots.ts` house pattern that exists precisely so geometry and ordering are pinned by node tests rather than looking tested inside a component.

```typescript
// src/lib/browse/sort.ts
//
// ONE collator, constructed once, with an EXPLICIT locale. src/lib/catalog/index.ts's
// byName() deliberately avoids localeCompare entirely, with the reason: "the order a
// page renders must not depend on the runner's or the visitor's locale." D-10 asks for
// locale-aware A-Z. Naming the locale satisfies both: real collation (so a future
// accented name sorts sensibly) that is identical on every machine and in every browser.
const COLLATOR = new Intl.Collator("en", { sensitivity: "base", numeric: true });

/** The final tiebreak of every sort, so all three are TOTAL orders. */
const byNameAsc = (a: ListingEntry, b: ListingEntry) =>
  COLLATOR.compare(a.name, b.name) || (a.id < b.id ? -1 : a.id > b.id ? 1 : 0);

/** D-10: featured first, then NEWEST, then name. */
export const featuredOrder = (a, b) =>
  Number(b.featured) - Number(a.featured) || newestOrder(a, b);

/** D-10: newest addedAt first, then name. */
export const newestOrder = (a, b) =>
  (a.addedAt < b.addedAt ? 1 : a.addedAt > b.addedAt ? -1 : 0) || byNameAsc(a, b);

export const nameOrder = byNameAsc;

// Every sort returns a NEW array. LISTING is frozen and never reordered in place.
export function sortListing(entries, sort) { return [...entries].sort(orderFor(sort)); }
```

```typescript
// src/lib/browse/filter.ts
//
// Case AND diacritic folding, locale-independent. `.toLowerCase()` rather than
// `.toLocaleLowerCase()` on purpose: matching must not depend on the visitor's locale
// (the Turkish dotless-i problem), and the collator above already owns collation.
const DIACRITICS = /\p{Diacritic}/gu;
export const fold = (s: string): string =>
  s.normalize("NFD").replace(DIACRITICS, "").toLowerCase().trim();

/** D-05: name + description + tags. No `$` power syntax, no fuzzy matching. */
export function matches(entry: ListingEntry, folded: string): boolean {
  if (folded === "") return true;
  return fold(`${entry.name} ${entry.description} ${entry.tags.join(" ")}`).includes(folded);
}
```

**Tag chip combination — recommend INTERSECTION (AND).** Two reasons, both about this catalog. (a) Union over 41 tags where 32 match one card each means adding a chip almost always *adds a single card*, which reads as a bug rather than as a filter. (b) `playable` is the largest tag at four entries, so intersection never empties a two-chip selection by surprise across the tags a visitor is likely to combine — and when it does empty, the empty state ("Nothing matches those. Clear the filters.") is honest and one press from recovery. State the rule in the UI copy (`showing entries with ALL of:`), because an unstated combination rule is the single most common complaint about tag filters.

**The agreement spec.** `src/lib/browse/sort.spec.ts` should assert that `sortListing(LISTING, "name")` and `sortListing(LISTING, "newest")` produce the same **id sequence** as `$lib/catalog`'s `byName()` and `byNewest()`. Do **not** assert agreement for `featured`: `index.ts`'s `byFeatured()` is "featured first, then by **name**" while D-10 says "featured first, then **Newest**". That divergence is deliberate and must be written into the module comment, or somebody will "fix" one of them.

### Pattern 5: The keyboard grid — roving tabindex over real links

**What:** a `<ul>` with `aria-label`, one `<li>` per card, each holding an `<a href={resolve("/c/[id]", { id })}>`. Exactly one anchor carries `tabindex="0"` (the "roving" one); the rest carry `tabindex="-1"`. A `keydown` handler on the `<ul>` moves the roving index with Arrow keys, Home and End, and calls `.focus()` on the new anchor. Enter and Space need no handler — they are a link.

**Why not `role="grid"`:** the APG Layout Grid pattern is the textbook answer for "a collection of widgets in one tab stop", and it is a legitimate alternative. It costs: `role="row"` wrappers inside a wrapping CSS grid require `display: contents` (a historically fragile accessibility-tree case), and `role="gridcell"` around an anchor suppresses the "link" role announcement. Keeping the anchors as anchors preserves Enter, middle-click, ctrl-click, "Open link in new tab", the status-bar URL preview and the browser's own focus ring — all of which a catalog of addressable configurations genuinely wants, and all of which `aria-activedescendant` throws away.

**The column count must be a pure function, not a measurement.** Put `columnsForWidth(px)` in `src/lib/browse/grid.ts` mirroring the CSS breakpoints exactly, and test it in node — the same reason `radiusForWidth` lives in `slots.ts`. Then:

```typescript
// src/lib/browse/grid.ts — pure, node-tested, no DOM.
export function nextIndex(
  key: string, current: number, count: number, columns: number,
): number | undefined {
  if (count === 0) return undefined;
  switch (key) {
    case "ArrowRight": return Math.min(current + 1, count - 1);
    case "ArrowLeft":  return Math.max(current - 1, 0);
    case "ArrowDown":  return Math.min(current + columns, count - 1);
    case "ArrowUp":    return Math.max(current - columns, 0);
    case "Home":       return 0;
    case "End":        return count - 1;
    default:           return undefined;   // never preventDefault an unhandled key
  }
}
```

Clamping rather than wrapping is the right call for a 2-D grid (`Coverflow` wraps because it is a ring; a grid is not). `ArrowDown` from the last row clamping to the last card is the APG behaviour and it stops a visitor falling out of the grid unexpectedly.

**Accessible name of a card:** the anchor's name should be `"{name}. {description}"` — the pad canvas already contributes `"{name}, live pad simulation"` via `role="img"`, so mark the canvas `aria-hidden` inside the card *or* leave it and accept the doubled name. Prefer: keep `PadCanvas`'s label (it is the content) and give the anchor `aria-label="{name}"` with the description in a sibling `<span>` inside the link. Defer the exact wording to `05.1-UI-SPEC.md`.

### Anti-Patterns to Avoid

- **Statically importing `$lib/catalog` from a browse component or from `/browse/+page.svelte`.** It puts 131 KB of protocol on the page. `config-shape.spec.ts` test 13's `COMPILER_MARKERS` are `["vendor", "intechstudio", "lib/pad"]` — **`$lib/catalog` matches none of them**, so the existing source scan will *not* catch this. See §Pitfall 3 for the two guard widenings that must land with the page.
- **A `+page.ts` on `/browse/` that touches `url.searchParams`.** Build failure. Do not add a `+page.ts` at all.
- **`pushState` for a filter change.** Sixteen presses, sixteen Back presses.
- **A `$derived` over `page.url`.** Stale after shallow navigation; throws during prerender.
- **`content-visibility: auto` on the cards** without `contain-intrinsic-size`. It is the obvious "make sixteen canvases cheap" reflex and it destroys scroll restoration, because an unrendered card has no height until it is scrolled near. If used at all, pair it with an exact `contain-intrinsic-size` — but the cards are fixed-aspect squares in a fixed grid, so `IntersectionObserver` gating already delivers the win and this buys nothing.
- **A second `SimHost` per card, or a second rAF loop.** One host per page, one loop for the whole page. That is the whole design.
- **`SvelteMap` / `SvelteSet` for the engine and canvas maps.** `Coverflow.svelte` carries `// eslint-disable-next-line svelte/prefer-svelte-reactivity` for exactly this reason: a reactive proxy around an object read on every one of 100 ticks per second is the performance cliff the rune rule exists to avoid. Copy the comment with the code.
- **Adding a tenth `--color-*` token or a fourth hex to `src/app.css`.** `identity.spec.ts` test 1 and test 5 both go red. The browse page reuses the nine.

## Common Pitfalls

### Pitfall 1: `page.url.searchParams` throws during prerender
**What goes wrong:** `npm run build` fails with `Cannot access url.searchParams on a page with prerendering enabled`, or — worse — a `+page.ts` `load` reads it and the failure only appears on the *build*, after everything looked fine in `vite dev`.
**Why:** `respond.js:433-434` and `load_data.js:71` call `disable_search(url)` whenever `state.prerendering`, and `render.js:185` gives the page store that same URL object.
**How to avoid:** never add a `+page.ts` to `/browse/`. Read the query only through `browser ? page.url.searchParams : DEFAULT`, at component-init scope, once, wrapped in `untrack`.
**Warning signs:** a `$derived` naming `page.url`; a `load` on `/browse/`; the error appearing at `vite build` but not at `vite dev`.

### Pitfall 2: shallow `replaceState` does not update `page.url`
**What goes wrong:** the address bar shows `?sort=name` but a `$derived(page.url.searchParams.get("sort"))` still says `featured`; then the user presses Back, popstate *does* update `page.url`, and the two disagree in opposite directions.
**Why:** `client.js:2551-2581` sets only `page.state`; `client.js:2871-2905` (popstate, shallow) calls `update_url(url)`.
**How to avoid:** local `$state` is the source of truth; the URL is write-only after the initial seed. Never `pushState` for a filter change, so there is no shallow entry to go back to.
**Warning signs:** any read of `page.url` outside the one-time seed.

### Pitfall 3: the front-door chunk guard cannot see `/browse/`
**What goes wrong:** `/browse/` statically imports `$lib/catalog`, ships 131 KB of protocol on its first paint, and **every guard stays green**. `config-shape.spec.ts` test 13's markers are `["vendor", "intechstudio", "lib/pad"]` and `$lib/catalog` matches none. Test 14 (the built-artefact scan) only inspects `build/index.html` and `build/c/aurora/index.html`.
**How to avoid — two widenings, both load-bearing, both in the same plan as the page:**
1. **test 14:** extend the page list to `["build/index.html", "build/c/aurora/index.html", "build/browse/index.html", "build/c/euclid/index.html"]`. The fourth entry is the new non-row detail page and it is the one that proves D-07's widening did not make the deep-link route heavy.
2. **test 13:** add a catalog-specific rule alongside `COMPILER_MARKERS` — any specifier beginning `$lib/catalog` or `../catalog` that is **not** `.../front-door` or `.../listing` is an offender. This is the fast guard that goes red before any build has run.
**Warning signs:** a browse component's import list naming `$lib/catalog`; a `build/browse/index.html` that references the chunk containing `GRID_PARAMETER_ELEMENT_POTMETER`.

### Pitfall 4: D-07 makes a shipped e2e test assert the opposite of the requirement
**What goes wrong:** `e2e/first-experience.e2e.ts` (test "every configuration in the row is a real file with its own description") loops `EXCLUDED_FROM_ROW` and asserts each `/c/<id>/` returns **404**, then navigates to `/c/tpad/` and asserts the `"Never heard of that one. Here is the shelf instead."` fidelity notice and `aria-activedescendant="slot-aurora"`. D-07 makes all eight of those pages real. The test will fail on the first build after `entries()` widens.
**How to avoid:** rewrite that test deliberately, in one commit, as a **recorded amendment to a signed-off phase's gate** — the same class of change `identity.spec.ts`'s X-27 note documents for Phase 5's ninth token, and the same class as Phase 4's W-02 change to a Phase 1 licence gate. The new assertions: all sixteen `/c/<id>/` return 200 with a unique description; a genuinely unknown id (`/c/no-such-configuration/`) still 404s from the static host and still lands on the shelf with the notice; the eight non-row pages render a **solo** pad centred on themselves, not the eight-pad ring. Write the amendment note into the test file's header, not only into the plan.
**Warning signs:** a plan that widens `entries()` without naming this file.

### Pitfall 5: the OG gate goes green while eight pages point at missing images
**What goes wrong:** `src/lib/og/build.spec.ts` test 4 ("gives every prerendered configuration page a complete Open Graph head") loops `FRONT_DOOR`, and `assertCompleteHead` is what checks `existsSync(build/og/<id>.png)`. Widen `entries()` without widening this and the eight new pages ship `og:image` URLs that 404, with nothing red anywhere. Test 1 (`pngs()` set-equals `FRONT_DOOR` ids) *would* fail — but only if `gen-og` is also widened; if only `entries()` moves, test 1 passes and test 4 passes and the site is broken.
**How to avoid:** widen **all three together, in one wave** — `scripts/gen-og.mjs` (read the listing, not `FRONT_DOOR`), `src/lib/og/build.spec.ts` (tests 1 and 4 read the same listing), and `e2e/artifacts.e2e.ts` ("every configuration's link image is served", currently `FRONT_DOOR`). Best of all: give the routed set **one name** — export `ROUTED` from `listing.ts` and have all four read it.
**Warning signs:** `static/og/` holding 8 files after a build (it holds 8 today; it must hold 16 after this phase).

### Pitfall 6: GHOST is a black square with no explanation
**What goes wrong:** the shipped `deriveMotion()` says GHOST is `"animated"` (its layers are counting down), `FidelityLine` suppresses the quiet line for animated entries, and the visitor sees an unexplained black pad among fifteen lit ones. Same shape for any future entry whose only light is a touch response.
**Why:** `frames.json` records GHOST as `animating: true` at every sampled tick with `nonZeroBytes: 0` at every sampled tick.
**How to avoid:** derive `motion` as `restsBlack → "dark"` **first**. Assert it both directions in `listing.spec.ts`. Three of the sixteen cards (tpad, ghost, morph) are dark and each needs its own honest one-line `quiet`.
**Warning signs:** a listing spec that reuses `front-door.spec.ts`'s `deriveMotion` verbatim.

### Pitfall 7: scroll restoration lands in the wrong place
**What goes wrong:** the visitor scrolls to card 12, opens it, presses Back, and lands at the top — or halfway. Two independent causes: (a) the first client render of `/browse/` shows all sixteen while the URL says `?tag=drums`, so the grid is tall when Kit restores scroll and short a frame later; (b) somebody reaches for `export const snapshot`, whose `restore()` runs **after** `after_navigate_callbacks` and therefore after Kit set the scroll (`client.js:2045-2048`).
**How to avoid:** seed the filter state at component **init** (not `onMount`, not an `$effect`) so the first client render is already the final height, and let Kit's built-in restoration do the browser-Back path with no code. For the `BACK TO BROWSE` control, which is a *forward* navigation and gets no restoration, record `{ href, scrollY }` in `sessionStorage` when leaving browse and `goto(href, { noScroll: true })` then restore explicitly on mount.
**Warning signs:** an `$effect` that applies the filter; a `snapshot` export; a `data-sveltekit-noscroll` attribute anywhere (it would also suppress the wanted scroll-to-top on the forward hop into `/c/<id>/`).

### Pitfall 8: `BACK TO BROWSE` overshoots because choosing pushed a history entry
**What goes wrong:** `Coverflow.choose()` does `pushState("", { chosen: true })`. A visitor who arrives from browse, taps the pad (choose), then presses `BACK TO BROWSE` implemented as `history.back()` lands on the *un-chosen detail page*, not on browse.
**How to avoid:** implement `BACK TO BROWSE` as `goto(recordedHref, { noScroll: true })` plus the explicit `sessionStorage` scroll restore — deterministic regardless of how many entries the detail page pushed. Reserve `history.back()` for the browser's own Back button, which Kit already handles.
**How to know you arrived from browse:** `afterNavigate(({ from }) => ...)` on `/c/[id]/+page.svelte`. `from` is `null` on a cold load (the "enter" navigation), and `from.url.pathname` is exact for an in-session hop. Fall back to `BROWSE ALL` + `goto(resolve("/browse/"))` when `from` is null — D-04 wants a browse control on every `/c/<id>/` page anyway, so the two are one component with two labels.
**Warning signs:** `document.referrer`; a hard-coded `history.go(-2)`.

### Pitfall 9: the D-06 laziness guard cannot be satisfied by a plain cold load
**What goes wrong:** D-06 asks for "a cold `/browse/` with no Lua card in view fetches no WebAssembly". With the default Featured sort, the first screenful is `aurora, pinwheel, ninepads, euclid, chorus, arc, lattice, morph` — five of those eight are Lua, so a genuine cold `/browse/` at the top of the page *will* fetch the VM, correctly and immediately. A test that asserts "no `.wasm` on a cold `/browse/`" would be asserting the wrong thing and would fail for a good reason.
**How to avoid:** make the guard concrete and honest. Load `/browse/?q=aurora` (or `?tag=colour`, which matches only aurora and pinwheel — both `padsim`) and assert **zero** `.wasm` responses; then clear the query and assert the VM arrives. That is the real claim: *a visitor who never brings a Lua card into view never downloads the VM.* Write the query into the test with a comment saying why.
**Warning signs:** an e2e that does `page.goto("/browse/")` and expects an empty wasm list.

### Pitfall 10: reordering the grid moves canvases, and a still pad may go blank
**What goes wrong:** a keyed `{#each}` over the sorted list makes Svelte `insertBefore` the existing `<li>` nodes. Per the HTML spec a canvas bitmap is reset only when `width`/`height` are set, so a move should preserve the picture — but this is a place where browsers have historically differed, and the failure mode is invisible in code review and silent for **static** pads only (an animating pad repaints on the next frame and self-heals).
**How to avoid:** add one method to `SimHost` — `repaintAll()`, which loops the entries and calls the existing private `paint(entry, now)` — and call it after any sort/filter change. It is five lines, it is testable in the existing `host.spec.ts` against the injectable deps, and it makes the question moot. Do **not** re-`register()`: `register()` calls `unregister()` (which sets `canvas.width = 0`) and re-enters with `intersecting: false`, which is exactly the bug `replaceEngine` was added to avoid in Phase 5.
**Warning signs:** a still pad (ninepads, faders, joystick) that is black only after a sort change.

### Pitfall 11: the search input zooms the viewport on iOS
**What goes wrong:** iOS Safari zooms the page when a text field smaller than 16px takes focus, which on the `webkit-phone` Playwright project shows up as a layout shift and for a real visitor as a jarring zoom that never zooms back.
**How to avoid:** the search input is Body 16px. This is already an established rule in this repository — `05-UI-SPEC.md` line 496: *"Every `<input>` that shows text is 16px or larger. The only one in this phase is the copy fallback field, and it is 16px specifically because iOS Safari zooms the viewport when a field smaller than 16px takes focus."* The browse search field is the site's second such input; cite the same rule.
**Warning signs:** a search input styled at the Micro 12px role because it "should be quiet". Quiet is done with alpha, not with size — 04-UI-SPEC line 118.

### Pitfall 12: sixteen canvases at 20 fps on a phone
**What goes wrong:** unverified. `.planning/research/STACK.md` estimates 10-16 concurrently visible animating cards before stutter *with the vendored `blit()`*, and 30+ after the two fixes — HANGAR already ships both fixes (no per-cell `strokeRect`, no `shadowBlur`, one `putImageData`, static CSS layers), and `IntersectionObserver` means the number that matters is *visible* cards, not sixteen. `intervalFor(hero=false, lowPower=false)` is **50 ms (20 fps)** and `isLowPower(cores ≤ 4)` drops it to **100 ms (10 fps)**.
**How to avoid:** do not tune anything speculatively. Add one measurement task: a Playwright run on `/browse/` that samples two canvases 400 ms apart to prove motion, and records `performance` timing for the record. If it stutters, the first lever is the grid's column count on a phone (fewer visible cards), not the paint rate — the rate is already the side-pad rate D-06 asks for.
**Warning signs:** a plan that changes `SIDE_INTERVAL_MS`. That constant is asserted against the vendored host by `schedule.spec.ts` and must not move for a layout reason.

### Pitfall 13: `--color-over` leaks onto the browse page
**What goes wrong:** somebody uses the alarm red for an "empty results" state or a "clear filters" control.
**Why it matters:** `identity.spec.ts` test 5 permits exactly three hexes in `src/app.css`, and `tune-ui.spec.ts` test 4 asserts the alarm red lives in exactly two components and on no button. `05-UI-SPEC` X-01 scopes it to three uses, all of them the over-budget state of a 908-character meter.
**How to avoid:** the browse page uses the lime ladder only. An empty result set is `--color-ink-quiet` prose, not an alarm.

### Reusing `SimHost` for the browse wall

```typescript
// Inside BrowseGrid.svelte's onMount. The shape is Coverflow.svelte's, minus
// the ring: no hero, no setInWindow, no touch. IntersectionObserver alone gates.
host = new SimHost();
host.setHero(undefined);          // nothing on this page takes a finger

void (async () => {
  // DYNAMIC, never static. A static import of $lib/sim/engine puts the vendored
  // compiler - and through its Lua branch the fingerprinted glue.wasm URL - into
  // this page's chunk, and the cold-load assertion goes red.
  const { createEngine } = await import("$lib/sim/engine");
  const { byId } = await import("$lib/catalog");
  // ... one engine per entry, skipped-on-throw exactly as Coverflow does.
})();
```

Note the ordering rule D-06 states and that `SimHost` already implements: `register()` sets `intersecting: false` and paints once immediately, then the observer's first callback wakes the card. A Lua card's engine is only *created* when the card is first needed — so build engines lazily, per card, on first intersection, rather than eagerly for all sixteen. The cleanest form is a per-card `onvisible` callback from the observer that builds the engine on first fire and then `replaceEngine`s it in; `SimHost` exposes no visibility callback today, so either add one or have `BrowseCard` own its own tiny `IntersectionObserver` for the *build* decision while `SimHost` keeps owning the *tick* decision. **Recommend the latter** — it keeps `SimHost` unchanged apart from `repaintAll()`, and the two observers answer two different questions.

### The one new `SimHost` method

```typescript
/**
 * Repaint every registered pad from its engine's current frame, without
 * touching the engines, the observers or the backing stores.
 *
 * NOT register(). register() calls unregister(), which sets canvas.width = 0
 * and re-enters with intersecting: false - the exact bug replaceEngine was
 * added to avoid in Phase 5. This exists for one caller: the browse grid, after
 * a sort or filter has moved cards in the DOM. A still pad does not tick, so
 * nothing else would repaint it.
 */
repaintAll(): void {
  if (this.destroyed) return;
  const now = this.deps.now();
  for (const entry of this.entries.values()) this.paint(entry, now);
}
```

## Open Questions

1. **Where does `BROWSE ALL` sit on the front door?** (CONTEXT open question 1.)
   - What we know: D-04 says "beneath the name plate or in the header"; `FrontDoor.svelte` is the composition shell for both `/` and `/c/<id>/` and already owns the wordmark, the headline and the row.
   - What is unclear: the placement is a design call.
   - Recommendation: build it as a `BrowseLink.svelte` taking a `label` and a `href`, rendered by `FrontDoor.svelte` in a named slot, so moving it is one line in one file. Let `05.1-UI-SPEC.md` fix the position. Do not block on it.

2. **Do the seven Lua entries join the coverflow row?** (CONTEXT open question 2.)
   - What we know: D-04 and D-07 both say the row is unchanged in this phase. `front-door.spec.ts` asserts every row entry has `preview === "padsim"` — a Lua entry in `FRONT_DOOR` fails that test today, and `EXCLUDED_FROM_ROW`'s stated reason for each is "new configurations join it deliberately, not by arriving in the catalog."
   - Recommendation: **out of scope for this phase.** It is a curation decision and it would require relaxing a Phase 4 gate. Note it in the phase summary as a follow-up for the user.

3. **Tag chips: which tags, and AND or OR?**
   - What we know: 41 tags, 32 singletons, largest is `playable` at 4.
   - Recommendation (§Pattern 4): chips for the nine tags with count ≥ 2, intersection semantics, the rule stated in the UI copy, the other 32 reachable through search. If the user wants all 41, add a disclosure. This is Claude's discretion under D-05, so decide it in the plan and record the reason.

4. **Does moving a `<canvas>` in the DOM always preserve its bitmap?**
   - What we know: the HTML spec resets the bitmap only on a `width`/`height` set; Svelte's keyed `{#each}` moves nodes with `insertBefore` rather than recreating them.
   - What is unclear: cross-browser behaviour under a re-parenting move, and specifically WebKit, which the `webkit-phone` project exercises.
   - Recommendation: do not investigate — make it moot with `SimHost.repaintAll()` after every reorder (§Pitfall 10), and add a `@webkit`-tagged e2e that sorts and then asserts a **still** pad (`ninepads` or `faders`) is still lit. That costs two against the e2e total; it is worth it.

5. **How many cards are visible at once on the target viewports, and does sixteen at 20 fps hold?**
   - What we know: `.planning/research/STACK.md`'s post-fix estimate is 30+ comfortable, and HANGAR ships both fixes. `SIDE_INTERVAL_MS` is 50 ms; `LOW_POWER_SIDE_MS` is 100 ms.
   - What is unclear: this is explicitly an unverified estimate.
   - Recommendation: one measurement task in the first wave that lands the grid. Record the number in the summary. Do not pre-optimise.
