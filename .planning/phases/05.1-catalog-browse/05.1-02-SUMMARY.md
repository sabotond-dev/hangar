### The plan's stated consequence is wrong, and the UI spec's is right

The plan's objective predicts *"a code-point comparator sorts every all-caps name ahead of every
mixed-case one, so `NAME` reads `ARC, CHORUS, EUCLID, GHOST, LATTICE, MORPH, SONAR, Aurora, Dial, …`"*.
**It does not**, and the sequence above is the observed output of the shipped `byName()` on today's
data.

The reasoning error is that a string comparison is lexicographic from the FIRST differing character,
not a partition by case. Only two of the sixteen names collide on their first letter, and both of
those resolve the way an English reader expects anyway:

| Pair | First difference | Order |
|---|---|---|
| `ARC` vs `Aurora` | `R` (82) vs `u` (117) | ARC first |
| `SONAR` vs `Starfield` | `O` (79) vs `t` (116) | SONAR first |

Everywhere else the first letters differ and case never enters into it: `CHORUS` before `Dial`
because `C` (67) < `D` (68), `Four faders` before `GHOST` because `F` < `G`, and so on. An all-caps
block would only appear if two names shared a prefix and differed by case, and none do.

**05.1-UI-SPEC.md § The sort control already said exactly this** — *"On the sixteen shipped names the
code-point order and an English collation agree entry for entry — `ARC` before `Aurora` (`R` < `u`),
`SONAR` before `Starfield` (`O` < `t`) — because no two names differ only in case, so there is nothing
to buy by diverging."* The spec is correct and unamended; only the plan's prose was wrong. The
acceptance criterion that asked for the sequence in the SUMMARY is what surfaced it.

### The three implementation rules, and their reasons

- **`fold` is `s.normalize("NFD").replace(/\p{Diacritic}/gu, "").toLowerCase().trim()`.**
  `.toLowerCase()` and never `.toLocaleLowerCase()`: under a Turkish locale the latter folds `I` to a
  dotless `i`, so a visitor typing `DIAL` would stop finding Dial. Test 1 asserts the composed
  `café` and the decomposed `café` both fold to `cafe`, and scans the stripped source for
  `toLocaleLowerCase` and `Intl`.
- **Multi-term is AND and there is no `$` syntax.** `"nine drums"` returns `["ninepads"]` where
  `"drums"` alone returns `["ninepads", "euclid"]`; `"$tag:drums"` returns `[]`, and dropping the
  prefix finds the two again — so the zero is the literal, not a broken matcher.
- **Tags intersect.** `["generative"]` → 3, `["gestural"]` → 3, `["generative", "gestural"]` →
  `["ghost"]`, and the test asserts the result is smaller than **either** input, which is precisely
  what a union cannot be.

### The column ladder is the CSS, not a table beside it

`columnsForWidth` computes `n * 260 + (n - 1) * 24 <= width` for `n` down from 4, which reproduces
`repeat(auto-fill, minmax(260px, 1fr))` at 24px gaps exactly. The approved boundaries fall out of it:
1112 → 4, 828 → 3, 544 → 2, below → 1. Asserted at each boundary, one above and one below, at the
spec's four example content widths, at 1280 (the content cap), at 1920 (**never a fifth column**) and
at 0 (never a zeroth).

### `columnsFromTemplate` — the clamp is load-bearing, not decorative

`"none"` and the empty string are dropped as tracks rather than counted, so an unrendered grid
reaches `Math.max(1, 0)` and the clamp is what supplies the answer — one **explicitly**, not one by
the accident of `"none".split(" ").length`. `undefined` and a whitespace-only value take the same
path. The last assertion in the test then feeds the result straight into `nextIndex` and shows
ArrowDown still moving on a grid measured before first paint.

### `nextIndex` clamps into range, and that is a decision

The plan says "clamps, never wraps"; ARIA APG's *grid* pattern says a Down press on the bottom cell
does not move at all. This module clamps into `[0, count - 1]` instead, and the reason is the short
last row: on a filtered set of thirteen at four columns, ArrowDown from card 9 lands on card 12
rather than refusing to move and stranding the last card. The UI spec is explicit that this is a
**list of links with a roving tabindex and not `role="grid"`**, so APG's cell rule does not bind, and
`Home`/`End` already establish that the ends of the list are the reachable ends. Asserted in both
directions and at both ends, with `undefined` for every unhandled key and for every key on an empty
grid.

## Decisions Made

1. **`nextIndex` clamps into range rather than staying put** on a row step that leaves the grid.
   Reasoned above; the alternative (APG's grid rule) is named in the module comment so a future
   reader knows it was considered rather than missed.
2. **`typographic` uses a capture plus a lookahead, never a lookbehind.** `(?<=\p{L})` would be
   cleaner to read and arrived only in Safari 16.4; a `SyntaxError` at module-parse time takes the
   whole page down, and browse-only visitors are the ones PROJECT.md says the catalog has to carry.
   The capture-plus-lookahead form consumes only `letter + '`, which is also what makes `a'b'c` curl
   both.
3. **`disabledTags` reports a chip a query alone has emptied.** The UI spec's sentence is "with
   nothing active, no chip is ever disabled", and that holds here without a special case. When a
   query is the thing doing the emptying the chip is still reported, deliberately: a click that
   cannot change the grid should not look live.
4. **`allTags` is exported although nothing uses it yet.** The plan's interfaces block names it for
   the query parser's unknown-tag drop (05.1-03), and `chipTags` is defined in terms of it, so it is
   a real seam rather than a speculative export.
5. **`filterListing` does not drop an unknown tag** — it intersects to nothing, which is the
   behaviour the plan specifies. Dropping unknown tags is the query parser's job in 05.1-03, and
   splitting it that way keeps this module free of any notion of a "known" vocabulary.
