| Run | Paints in 2 s | Viewport | Cards on screen | Engines built |

| isolated file run (task 3) | **148** | 1280x720 | 4 of 16 | 4 |

| whole-suite run (task 4) | **152** | 1280x720 | 4 of 16 | 4 |
| isolated file run (task 4) | **156** | 1280x720 | 4 of 16 | 4 |

**The arithmetic.** `intervalFor(hero = false, lowPower = false)` is `SIDE_INTERVAL_MS` = 50 ms, so a
fully visible animating card approaches 40 paints in two seconds and a wall of `n` of them approaches
`40n`. Four cards were on screen and four engines were built, so the ceiling is **160**. Observed
139-156 is **87% to 98% of the ideal** — the loop is not dropping frames on this machine at this
width, and the four-card figure is what the layout produces: `columnsForWidth(1216)` is 4 (four
260 px cards plus three 24 px gaps is 1112, which fits), and one row of tall cards fills a 720 px
viewport.

**No threshold was added and nothing was tuned.** `.planning/research/STACK.md`'s own estimate —
10-16 concurrently visible animating cards before stutter with the vendored `blit`, 30+ after the two
fixes HANGAR already ships — is explicitly marked *"Unverified estimate — profile it"*, and this plan
does not turn an unverified estimate into a gate that would go red on somebody else's machine for
reasons that are not regressions. The test asserts only `painted > 0`. For the record, the visible
wall here is four cards, which is under even the pessimistic end of that estimate, so this
measurement does not test the estimate either way.

The front door's own recorded number in the same runs, for comparison: 208-216 paints in two seconds
at the same viewport (`e2e/first-experience.e2e.ts`, unchanged).

## The WebAssembly proof, and the request list

`?q=aurora` is load-bearing and the reason is written into the test. `aurora` matches exactly one
listing entry and that entry is declared `padsim`, both asserted from the data before the navigation.

**Observed on the cold `/browse/?q=aurora` load, through `networkidle`:**

```
.wasm responses: []          (zero — neither the 271 KB VM nor the 628 KB formatter)
```

The **protocol chunk** half is asserted against the SERVED HTML rather than against the live DOM, and
that choice is the whole point: Vite's preload helper inserts `<link rel="modulepreload">` elements
for a *dynamic* import's dependencies too, so by the time the grid has built an engine the document
carries links a first paint never saw. What the Worker serves for `/browse/` is race-free.

```
build/_app/immutable/chunks/*.js carrying GRID_PARAMETER_ELEMENT_POTMETER:  C1rLf53t.js  (1 carrier)
_app/immutable/*.js named by the served /browse/ HTML:                      12 modulepreload links
                                                                            + 2 entry import() calls
carriers among them:                                                        []
carriers among the .js responses actually fetched during the load:          1
```

The last line is the other direction of the same claim, and it is asserted: the chunk is **deferred,
not absent**. `BrowseGrid.svelte` pulls it through `await import("$lib/sim/engine")` when it builds
its first engine, which is after paint. Without that assertion a build that had lost the catalog
entirely would pass the first one.

**Then the filter is cleared and the first Lua entry in Featured order (`arc`) is scrolled into
view**, and a VM `.wasm` arrives:

```
status 200, content-type application/wasm
url .../_app/immutable/assets/glue.<hash>.wasm   (discriminated from the formatter by the ABSENCE
                                                  of lua_fmt_bg in the URL, as e2e/catalog.e2e.ts does)
```

The MIME is asserted rather than assumed because a wrong one breaks nothing visibly — the loader
falls back from `instantiateStreaming` to `WebAssembly.instantiate` with only a console warning and
then runs the slow path forever.

## Deviations from Plan

### 1. [Rule 1 — Bug] The browser Back button into a filtered browse view rendered the whole shelf

**Found during:** carried in from 05.1-09's `deferred-items.md`, item 1, which named 05.1-10 as the
suggested owner. Authorised for this plan.
**Files modified:** `src/routes/browse/+page.svelte`
**Commit:** `cbe797d`

**Reproduced first, in four journeys, on the served production build.** The defect needs the filtered
address to have been composed by a shallow `replaceState`; a Back into an address the document was
*loaded* with was already correct, which is why the first shape of the eighth test passed against the
unfixed page and had to be rewritten:

```
B  cold /browse/, press playable, open a card, Back   -> 16 cards, 0 chips, url ?tag=playable
C  the same with no wait for the address to settle    -> 16 cards, 0 chips, url ?tag=playable
D  cold /browse/?tag=playable, press drums, card, Back-> 4 cards, 1 chip,  url ?tag=playable&tag=drums
E  front door -> BROWSE ALL -> chip -> card -> Back   -> 16 cards, 0 chips, url ?tag=playable
```

**Journey D is what names the cause.** What comes back is neither the default nor the popped address:
it is the address the browse *document was entered with*. `Kit 2.70.3 client.js:2573` —

```js
const opts = {
  [HISTORY_INDEX]: current_history_index,
  [NAVIGATION_INDEX]: current_navigation_index,
  [PAGE_URL_KEY]: page.url.href,          // <- the PAGE STORE's url
  [STATES_KEY]: state
};
history.replaceState(opts, '', resolve_url(url));   // <- and a DIFFERENT url in the address bar
```

`replaceState` records `page.url.href` into the history entry, and `page.url` is precisely what
`replaceState` never updates. Every shallow write therefore leaves the entry remembering the entry
URL; the popstate handler reads that key back (`client.js:2883`,
`new URL(event.state[PAGE_URL_KEY] ?? location.href)`) and hands `update_url` a stale URL. The address
bar is right, because `history.replaceState(opts, '', …)` really did change it.

**This corrects a sentence this repository carried in two places.** `05.1-RESEARCH.md` Pitfall 2 and
the header of `+page.svelte` both said `page.url` is *"stale on write and fresh on back"*. It is stale
in **both** directions. The `+page.svelte` header now carries the amendment; `05.1-RESEARCH.md` is
left as written and the correction is logged in `deferred-items.md` for the phase gate, since a
research document is a record of what was known when it was written.

**The repair is a second seed, never a moved one.** The init-scope seed stays exactly where it is —
it is what makes a cold arrival on a filtered address paint its own set on the first frame (D-16,
Pitfall 7a), and 05.1-08 measured that moving it into `onMount` costs a spurious live-region
announcement. The new block runs only after a navigation has completed and only for
`navigation.type === "popstate"`, and it reads the browser's own answer:

```ts
afterNavigate((navigation) => {
  if (!browser || navigation.type !== "popstate") return;
  const restored = parseBrowseQuery(new URLSearchParams(window.location.search), TAGS);
  if (addressTimer !== undefined) { clearTimeout(addressTimer); addressTimer = undefined; }
  sort = restored.sort;
  q = restored.q;
  tags = [...restored.tags];
});
```

**Both negative checks observed.**

- With the whole block removed, test 8 goes red naming the defect: `locator resolved to 16 elements —
  unexpected value "16"` where four were expected. Restored.
- With `page.url.searchParams` in place of `window.location.search` — the mechanism the plan brief
  proposed — the four probe journeys were **byte-identical to the unfixed page**: B, C and E still
  read `cards=16 chips=0`, and D still restored the arrival state rather than the composed one. That
  is the measurement that forced the source change, and it is why the block reads `location`.

**Known and accepted:** Kit restores the scroll offset before it runs the after-navigate callbacks
(`client.js:2003` then `:2042`), so on a Back the grid shrinks one frame after the scroll has been
set. That is a smaller wrong than the screen and the address bar contradicting each other on a link
the visitor can copy and send to somebody, and it is written into the file.

**Chunk-seam guards, all green after the change:** the page gained no static import — `afterNavigate`
comes from `$app/navigation`, which it already imported — so `config-shape.spec.ts` (14),
`browse-ui.spec.ts` (6), `identity.spec.ts` (6) and `tune-ui.spec.ts` (5) are untouched and the whole
`test:quick` total is unmoved at 66 / 691.

### 3. [Rule 2 — Missing critical coverage] The live region's silence, asserted

**Files modified:** `e2e/browse.e2e.ts`

05.1-08 found that the property an `onMount` seed would break is not the first paint at all — it is a

### 4. [Rule 3 — Method] The protocol-chunk claim is asserted against the served HTML

**Files modified:** `e2e/browse.e2e.ts`
**Commit:** `245aeac`

The obvious implementation — collect responses up to the moment the filtered set is on screen — is a
race: `expect(...).toHaveText(...)` polls, and the dynamic import that pulls the chunk fires from the
grid's `onMount` within milliseconds of hydration. The obvious alternative — read
`link[rel=modulepreload]` from the live DOM — is wrong for a different reason: Vite's preload helper
*adds* those links for a dynamic import's dependencies, so the settled DOM is not a first-paint graph.

The test therefore fetches `/browse/` through Playwright's `request` fixture and reads the module
names out of the served bytes. Race-free, about the deployed artefact, and complementary to
`config-shape.spec.ts` test 14, which walks the same graph transitively in node.
