## The rendered default Featured order

Recorded because it is a visible consequence of D-10 as amended and 05.1-UI-SPEC.md's morning
question 4 asks about it. Read out of `build/browse/index.html` and confirmed on a served build:

```
ARC · Aurora · CHORUS · EUCLID · LATTICE · MORPH · Nine pads · Pinwheel
Dial · Four faders · GHOST · Joystick · Radar · SONAR · Starfield · Trackpad
```

ids, in order: `arc, aurora, chorus, euclid, lattice, morph, ninepads, pinwheel, dial, faders,
ghost, joystick, radar, sonar, starfield, tpad`.

**The plan predicted "ARC, CHORUS, EUCLID, LATTICE, MORPH-or-not…" and Aurora lands second, not
last-of-the-featured.** The comparator is `Number(b.featured) - Number(a.featured) || byNameThenId`,
and `byNameThenId` compares by CODE POINT, so an uppercase name sorts before a mixed-case one:
`"ARC" < "Aurora"` because `R` (0x52) precedes `u` (0x75). Eight featured entries then eight others,
each group in the same code-point order. The consequence is that the eight hand-authored Lua
configurations (uppercase names) and the eight ported ones (mixed case) interleave in a way that
reads as arbitrary unless you know the rule. **This is a fact for the user to choose from, not a
defect**: the alternative is a case-folding collator, which D-10 as amended deliberately rejected so
the order a page renders never depends on the runner's or the visitor's locale.

The Name sort, for comparison, is the same code-point order with the featured group dissolved:
`arc, aurora, chorus, dial, euclid, faders, ghost, joystick, lattice, morph, ninepads, pinwheel,
radar, sonar, starfield, tpad`.

## Deviations from Plan

### 1. [Rule 2 — missing critical detail] The seed is at component init, and D-16 says `onMount`

**Deliberate and pre-authorised by the plan**, recorded here as the plan's `<output>` block requires.
05.1-CONTEXT.md D-16 words the rule as "inside `onMount`". The two reasons D-16 gives — prerender
safety and the staleness of shallow routing — are both satisfied by an init-scope read behind a
`browser` guard, and an `onMount` seed is strictly later for no gain (05.1-RESEARCH.md Pitfall 7a).
It is one word of mechanism, not of intent.

**And the negative check did not reproduce the flash the plan described.** This is the plan's most
interesting finding and it is recorded rather than papered over.

The plan asked for: *"load `/browse/?q=aurora`, watch sixteen cards paint and then collapse to one."*
The mutation was applied (`initial = DEFAULT_QUERY` plus a seed inside `onMount`), the build was
confirmed to have shipped it (the built chunk shows the three assignments inside the mount callback),
and **the DOM trace was byte-for-byte the same shape as the correct build**:

```
correct  : 16cards@28ms -> 16cards@227ms -> 16cards@233ms -> 1cards@274ms+ann -> 1cards@282ms+ann
onMount  : 16cards@33ms -> 16cards@234ms -> 16cards@242ms -> 1cards@257ms+ann -> 1cards@266ms+ann
batches showing 16 cards WITH Kit's announcer already present: 0 in both
```

The reason is Svelte 5.57's mount flush: `onMount` runs inside the same task as hydration, so the
collapse and Kit's `#svelte-announcer` insertion land in one MutationObserver batch either way and
no frame is ever painted between the two states. An end-to-end browser-Back-into-a-filtered-view
probe agreed (`DELTA: 13px` on both). **The sixteen cards that do paint first are the prerendered
HTML, which has no query string and cannot have one** — that frame exists on both builds and is not
what the seed placement controls.

**What the mutation DOES break, observed, is the live region.** With the seed in `onMount`,
`BrowseToolbar`'s effect records the DEFAULT signature on its first pass and the seed then looks like
a visitor-made change, so the region announces a filter nobody applied, over whatever the visitor was
reading:

| Address | init-scope seed (shipped) | `onMount` seed (mutated) |
|---------|---------------------------|--------------------------|
| `/browse/` | `""` | `""` |
| `/browse/?q=aurora` | `""` | `"1 of 16 configurations."` |
| `/browse/?tag=drums` | `""` | `"2 of 16 configurations."` |

05.1-UI-SPEC.md's Accessibility Contract requires exactly the left column: *"On first load it says
nothing, because nothing has changed; the expansion has already said it."* Restoring the init-scope
seed restored silence. **That is the observation this negative check should be written as from now
on**, and 05.1-10's e2e suite can assert it in one line.

### 2. [Rule 2] `browse-ui.spec.ts` test 6 asserts its elements before its count

See the negative-check table above. Found by the plan's own mutation table, fixed in the spec, and
the reason is written into the file.

### 3. [Rule 3] `npm run build` cannot run while `wrangler dev` is serving `build/`

`adapter-static` calls `rimraf` on `build/` and Windows refuses with `EPERM` while workerd holds the
directory. Every mutate-build-observe cycle in this plan therefore killed the whole wrangler tree
(npx-cli → wrangler.js → wrangler-dist/cli.js → workerd.exe, as Phase 1 recorded) before building and
restarted it afterwards. Port 4173 was confirmed free before every served run and after the last one.

### 4. No `+page.ts`, against the UI spec's Component Inventory

05.1-UI-SPEC.md's Component Inventory reads *"New route: `src/routes/browse/+page.svelte` and
`+page.ts` (`export const prerender = true`)"*. It is not built. `src/routes/+layout.ts` already
declares `prerender = true` and `trailingSlash = "always"` for the whole site, `vite.config.ts`'s
`prerender.entries: ["*"]` picks the route up, and a `+page.ts` here would be a place for
`disable_search()` to bite. The route prerenders: `build/browse/index.html` exists at 31,743 bytes.

### 5. `BrowseGrid`'s `onreorder` prop is not wired

05.1-06 added it "so the page can flush its address after a reorder". Wiring it would write the
address on every keystroke, which is what the 500 ms trailing timer exists to prevent. The prop stays
optional and unused, with the reason in a comment beside the `<BrowseGrid>` tag; `beforeNavigate`
flushes instead, so nothing leaves the page with a stale address.
