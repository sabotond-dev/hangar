<objective>
The toolbar: one search landmark holding the field, the sort, the chips, the clear control, the count
and the page's only live region.

Wave 7. It is the whole visible surface of CAT-02, and every widget in it is one this site already
ships:

- **The sort control is Phase 5's word row, verbatim** (W-03) — a `role="radiogroup"` over real
  `<input type="radio">` inside `<label>`s, one tab stop, arrows that move *and* select, wrapping at
  4px gaps, each option a 44px box with 12px inline padding. The site has one way of saying "this is
  the live value" and reusing it costs no new pattern, no new accent use and no new keyboard model.
  The only difference is the case: `FEATURED` · `NEWEST` · `NAME` are uppercase because they are
  one-word page-control labels, which is what tells a visitor that `NAME` reorders the page while
  `Major` names a scale.
- **The chips are real checkboxes**, so `Space` toggles and "individually removable" is satisfied by
  pressing one again. There is no `x`, no glyph and no second control per chip (W-14).
- **The live region is Phase 5's meter pattern applied to a count**: the visible line updates
  instantly and is `aria-hidden`, and a single visually-hidden `aria-live="polite" aria-atomic="true"`
  region speaks on a 500 ms trailing timer.

Two rules that are the reason this screen does not need a number beside a tag. **Tags combine with
AND** — that is what a filter means. And because 32 of the 41 shipped tags sit on exactly one
configuration, AND would empty the grid on the second press most of the time, so **a chip that would
return zero given the currently active set is a real `disabled` checkbox** with no adjacent reason
line: the cause is the active chips two centimetres away and the count line beneath them. A count
printed on a chip would be the one number on this page a visitor could mistake for popularity (W-04).

Purpose: CAT-02, made operable.
Output: two components, no new unit test, and a toolbar that keeps its promises to a screen reader.
</objective>

**`BrowseToolbar.svelte`**

```svelte
let { entries, sort, q, tags, chips, disabled, showing, total, onsort, onquery, ontag, onclear }: {
  /** The full listing, for the chip vocabulary. Never the filtered set. */
  entries: readonly ListingEntry[];
  sort: BrowseSort;
  q: string;
  tags: readonly string[];
  chips: readonly string[];        // chipTags(entries)
  disabled: readonly string[];     // disabledTags(...)
  showing: number;                 // after filtering
  total: number;                   // entries.length
  onsort: (next: BrowseSort) => void;
  onquery: (next: string) => void;
  ontag: (tag: string) => void;
  onclear: () => void;
} = $props();
```

One `<search>` landmark wrapping three stacked bands and the count line. Every band is a stacked
label-over-control layout at every width. The form never submits; filtering is live and synchronous on
every keystroke — sixteen entries cost nothing and a debounce would make the grid feel broken. **Only
the announcement and the address write are debounced**, on one shared 500 ms trailing timer.

Copy, verbatim from the contract: `SEARCH`, `CLEAR`, `SORT`, `FEATURED` · `NEWEST` · `NAME`, `TAGS`,
`CLEAR FILTERS`, `{n} of {total} configurations.`

`data-testid`s: `browse-toolbar`, `browse-search`, `browse-search-clear`, `browse-sort`,
`browse-tags`, `browse-clear-filters`, `browse-count`, `browse-live`.

**Two decisions this plan makes and records, because the UI spec and the CONTEXT disagree by a hair:**

1. **The standing chip row is the nine tags carried by two or more configurations, and there is no
   `MORE TAGS` disclosure.** `05.1-CONTEXT.md` D-15 is binding: *"the nine tags carried by two or more
   entries are chips; the 32 single-entry tags stay searchable text on the card."*
   `05.1-UI-SPEC.md` W-19 proposed putting the other 32 behind a `MORE TAGS` toggle; CONTEXT wins and
   the toggle is not built. Say so in the SUMMARY, with the reason, so a reader of the spec is not
   left looking for a control that was deliberately not shipped.
2. **An active tag always renders a chip, even a single-entry one.** A shared `?tag=looper` link must
   show its own chip or the visitor has no way to remove it — that is D-05's "individually removable"
   and it is the one place where a tag outside the nine appears in the toolbar. Append active
   non-standing tags after the nine.

**Focus is never orphaned.** `CLEAR FILTERS` renders only while the query is non-empty or a tag is
active, so on activation it removes itself — focus moves to the search field. The field's own `CLEAR`
renders only while the query is non-empty and returns focus to the field. These are the only two
places on the screen where a control can vanish while holding focus, and both are handled
deliberately.

`Escape` clears the query **only while focus is inside the field**, and does nothing anywhere else
(W-18) — Phase 4 binds `Escape` to un-choosing on a different route, and scoping keeps the two from
ever colliding.

`CLEAR FILTERS` clears the query and every tag and **does not touch the sort**: a sort is a view
preference, not a filter, and silently resetting it would undo something the visitor did not ask to
undo.
