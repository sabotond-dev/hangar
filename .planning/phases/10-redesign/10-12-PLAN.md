**D-05's control is destructive in a way the other three are not.** The other three either install
something or restore something; this one **removes**. It inherits every Phase 7 rail: a snapshot must
exist first, nothing without an explicit click, an ACK before it is called done, `PUT BACK` still
offered afterwards.

**A-26 — CLEAR writes RAM and never flash.** D-05 asks for the current page's configuration to be
cleared; it does not ask for a permanent wipe, and **a permanent wipe of somebody's flash is the
single most destructive thing this site could do.** Two `CONFIG/EXECUTE` frames carrying empty Setup
and Timer, **no `PAGESTORE/EXECUTE`**, and a power cycle brings back whatever is stored. The copy says
exactly that, twice.

**A-28 — three failure states reused, not three invented.** `partial` already means "one of two
landed", `lost` "the connection went", `nothing-landed` "zero of two" — which is exactly how a clear
fails. The copy is selected by `lastAction`, which the store already tracks. **Fifteen states, not
eighteen.**

**G-06 is a no-op on the assertion, and that is the finding.** `install.spec.ts` test 4 counts writes
**by class**, and CLEAR writes `CONFIG/EXECUTE` — the class already counted — so the enumeration needs
no widening and its reach is already total. What actually widens is `InstallAction`, and the compiler
enforces that for free. **The amendment is documentary**: the test's comment and `docs/TESTING.md:840`
become four so a later reader does not think the fourth click was missed. (The doc line is 10-13's.)

**A staleness this plan corrects by name.** `REQUIREMENTS.md:169` says `session.spec.ts` test 15 has
**eight** needles. It has **nine** today — `.write(`, `RequestQueue`, `hostHeartbeat`, `sendConfig`,
`storePage`, `fetchConfig`, `storeToFlash`, `writeBack`, `setInterval`. That was stale before this
phase. It becomes **ten** here, and the record is corrected in the same named amendment.
