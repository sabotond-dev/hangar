<objective>
**HANGAR takes ownership of the nine preset definitions**, because reading them out of
`src/vendor/botor/_pad.ts:4214` is what made eight of the user's bench notes unfixable here for a
structural reason rather than a technical one.

They are not vendored *behaviour*. Each is a short mutator over a descriptor — **Aurora's is empty**,
Pinwheel's is three lines, the longest (Joystick) is nine — sitting inside a module-private twenty-line
`preset()` factory. The compiler and the simulator, which *are* vendored behaviour and *are* what makes
the preview firmware-faithful, stay exactly where they are.

**The guarantee that changes shape, and this is the honest part.** Today `ported.ts:96` reads `name`
and `sentence` **through** `presetById` precisely so a BOTOR rename cannot silently disagree. Once
HANGAR owns the values, that read-through is gone.

**What replaces it is strictly stronger, and it costs something.** A divergence spec that, for each of
the nine, diffs HANGAR's `PadPreset` against the vendored one **field by field** — `id`, `name`,
`sentence`, `category`, `knobs`, `exclusive`, `quiet` **and the whole of `state`** — and fails on any
difference not listed in an explicit `INTENDED_DIVERGENCE` table with a reason. Today two strings are
held. After this, everything is held. A BOTOR re-sync that renames a card, adds a knob kind or changes
a colour still goes red and still names the card. **The difference is that HANGAR now has to *say*
which divergences are on purpose.**

That is the trade, and the plan states it in those words rather than presenting the replacement as a
free upgrade.

**And one thing must not move.** `preset-baseline.json` and `golden-frames.json` were captured against
the **vendored** nine, and their specs must keep importing `PRESETS` from `src/vendor/`. They stop
being the catalog's gate and become purely the port's gate — **which is what they always actually
were**. HANGAR's nine are covered instead by `src/lib/catalog/frames.json`, which already carries a row
per catalog entry.

Purpose: the structural blocker behind eight bench notes removed, with a stronger guarantee in place of
the one it costs.
Output: one module, one spec, six repointed readers, and nine re-measured cost declarations.
</objective>

## What is true today

The nine are built by a module-private `preset()` factory at `_pad.ts:4189-4211` and exported as
`PRESETS` (`:4214`) and `presetById` (`:4386`). `PadPreset` carries `id`, `name`, `sentence`,
`category`, `knobs: KnobKind[]`, optional `exclusive` / `quiet`, `state: PadState`, and a declared
`cost`.

**Six runtime readers**, not counting specs:

| Site | Reads |
|---|---|
| `src/lib/catalog/entries/ported.ts:96` | `name`, `sentence` |
| `src/lib/pad/index.ts:60` (`compilePreset`) | `state` |
| `src/lib/pad/index.ts:41` | re-exports `PRESETS`, `presetById` to the rest of HANGAR |
| `src/lib/sim/engine.ts:120` | `state` for the preview |
| `src/lib/tune/state.ts:112` | `state`, cloned per tune session |
| `src/lib/tune/knobs.preset.ts:730` | `knobs` (the kind list) **and** the shipped `state` — every knob default is derived from it and **throws at import time** if the value is not in its own option list |

Plus eight spec files, `scripts/capture-preset-baseline.mjs`, and two committed fixtures.

## The mechanism

A new `src/lib/catalog/presets.ts` re-declaring the nine, importing only **types and pure helpers**:

```
import {
  defaultState, normalisePadState,
  type PadPreset, type PadState, type KnobKind,
} from "../../vendor/botor/_pad";
```

All three of `defaultState`, `normalisePadState` and the `PadPreset` type are already exported, so
HANGAR reimplements only the twenty-line private factory: `defaultState()` → apply the mutator →
`state.preset = id` → `normalisePadState(state)`.

**`PadPreset` and `PadState` stay vendored.** HANGAR owns the nine **values**, never the shapes. A
plan that copies the type definitions across has misunderstood what is being taken.

Then flip the six runtime readers from `../../vendor/botor/_pad` to `$lib/catalog/presets`.

## The line that must not be got wrong

`src/lib/fidelity/preset-baseline.spec.ts` and `src/lib/fidelity/golden-frames.spec.ts` **keep
importing `PRESETS` from `src/vendor/botor/_pad`.**

`preset-baseline.json` was captured by running BOTOR's own compiler in BOTOR's own tree at the pinned
commit. Its header: *"the fixture is the original's behaviour, and the copy is what is on trial."*
Pointing that spec at HANGAR's nine would make it compare HANGAR against HANGAR — a tautology dressed
as a fidelity gate, and the most expensive kind of green.

`scripts/capture-preset-baseline.mjs` reads `pad.PRESETS` with `EXPECTED_PRESET_COUNT` and is
**unchanged**: it captures the vendored shelf, which is the point.

HANGAR's nine are covered instead by `src/lib/catalog/frames.json`, which already carries a row per
catalog entry per sampled tick, and by the divergence spec below.

## The divergence spec

`src/lib/catalog/presets.spec.ts`, four tests, in the shape `EXCLUDED_FROM_ROW` and
`upstream-manifest.json`'s `intendedDivergence` already use:

1. **Field-by-field diff.** For each of the nine, compare HANGAR's `PadPreset` against the vendored one
   across `id`, `name`, `sentence`, `category`, `knobs`, `exclusive`, `quiet` and **the whole of
   `state`**, deeply. Any difference not in `INTENDED_DIVERGENCE` fails, naming the card and the field
   path.
2. **`INTENDED_DIVERGENCE` is justified and closed.** Every row: card id, field path, reason (a
   sentence), plan id, date. A row whose fields are now identical **fails**, so the table cannot rot.
3. **The nine are the same nine.** Same ids, same order, same count as the vendored array — HANGAR
   owns the values and does not get to quietly add a tenth or drop one. If a later phase wants a tenth
   preset, it changes this test deliberately.
4. **The costs are real.** Each declared `cost` re-measured through the compiler after
   `await padReady()`, `max(compressed, raw)`, and asserted equal.

**`INTENDED_DIVERGENCE` is EMPTY when this plan lands.** 11-06 fills it with the five preset asks. That
ordering is deliberate and matches 11-03: the record is proved to work before anything is put in it.
