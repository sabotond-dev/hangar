<objective>
Two class bugs, each of which explains several of the user's reports at once, and each of which must
become a **gate** and not just a fix — because both are conventions that files silently missed, not
arithmetic slips somebody got wrong once.

**Class A: the LED phase never reaches zero.** The firmware advances a layer with
`ledbuf->pha += ledbuf->fre` on a `uint8_t` — it **wraps**, it does not clamp and it does not stop —
and freezes wherever it happens to be when the timeout expires. With `start = 255` and `rate = 250`
the step is 6, and `6k` is always even while 255 is odd, so **the walk can never reach 0 from 255**.
Measured in HANGAR's own simulator: **CHORUS leaves all 81 cells stuck at up to 126 of 255 forever**
and **MORPH leaves every crossed cell at rgb [47,66,66]**. Those are the user's *"color stucks after
touching it"* and *"the LED's colors stuck again"*, word for word. Four literal sites plus CHORUS
computed. **Cost: +0 characters.**

**Class B: `e >= 5` swallows the fast tap.** Firmware coalesces a sub-cycle press-and-lift into ONE
message with event code **9 (DOWNUP)** and no separate DOWN or UP. Five surviving entries write
"contact ended" as `e == 3 or e >= 5` with no `and e < 9` escape, so a fast tap is classified as a
lift and **produces nothing at all**. Counted through the real Lua host: **LATTICE fast tap 0 messages
against 2 slow; CHORUS 0 against 6; MORPH 0 against 4; GHOST 0 against 8.** That is LATTICE's *"not
precise enough"*. **Cost: +8 characters per site.**

**Six entries already write the guard correctly and two already write the decay idiom correctly.** So
neither is a house convention that was never established — both are conventions that some files did
not follow, and nothing checked. **A fix without a gate lets the next authored entry reintroduce it**,
and this phase authors four new entries after this one.

Purpose: seven bench reports cleared at between +0 and +8 characters a site, and both classes made
unrepeatable.
Output: nine entry edits, one spec file created, two behavioural probes, and an empty
`KNOWN_VIOLATIONS`.

| `chorus.setup` | `glpfs(a,2,255-sqrt(p*p+q*q)*22//1,@BLOOMRATE,0)` + `glt(a,2,64)` | 177 | **the computed form** — see below | measure |

**GHOST is fixed here even though 11-11 rewrites it from scratch.** The gate lands in this plan and
must be green when it does; the redesign then inherits a convention that is already enforced rather
than one it has to remember.

**Two knob value lists must be re-cut, and this has a consequence the plan must state out loud.**
The parameterised idiom `glpfs(a,l,252,256-252//T,0)` + `glt(a,l,T)` lands on 0 **only when `T` is an
exact divisor of 252**. The fifteen legal values under 256 are
`4, 6, 7, 9, 12, 14, 18, 21, 28, 36, 42, 63, 84, 126, 252`.

- **EUCLID `@TRAIL`** ships `["21","42","64","100","150"]`. 21 and 42 qualify; 64, 100 and 150 do not.
- **MORPH `@DECAY`** ships `["20","42","80","120"]`. Only 42 qualifies.

**Changing a knob's VALUES while keeping its arity keeps every shared link decodable — the stamp
encodes an index, not a value — and silently changes what an existing link renders.** `stamp.spec.ts`
compares indices and stays green either way, so no test will tell you. Keep the same number of values,
keep them in ascending order so the knob still reads as a ramp, and choose the nearest legal value to
each shipped one so an existing link lands as close as the rule permits. **Say so in the SUMMARY, per
entry, old value beside new.** This is Pitfall 5 in the research and it is the only change in this
plan with a user-visible failure mode.

**CHORUS's bloom is the hard one and it is not a constant change.** The start is computed per cell
(`255 - dist*22`), the rate is positive, and the freeze is `start + rate*64 mod 256`; `@BLOOMRATE`'s
values `2, 4, 6, 8, 12` all give `rate*64 ≡ 0 or 128 (mod 256)`, so the bloom freezes at **exactly its
opening brightness** or half a cycle from it. No constant fixes it.

**The form it needs is the one 11-01 rescued from `gridlock.ts`** — a per-cell timeout derived from
the per-cell start:

```
local p=glim(248-<distance>*<spread>,0,248) glpfs(a,l,p,4,0) glt(a,l,(256-p)//4)
```

with `p` a multiple of 4 so `(256-p)//4` is exact. Two consequences to cost and to state:

1. The start must become a multiple of 4 (248 rather than 255, and the per-cell decrement a multiple
   of 4), which slightly dims the bloom's leading edge. That is a picture change and `frames.json`
   proves it.
2. **`@BLOOMRATE` stops being a rate.** In the computed form the rate is fixed at 4 and what the knob
   controls is the **spread** — how many phase units of head start each ring of distance loses. If the
   knob's meaning changes, its **label and its help text change with it**, and its values must all be
   multiples of four the way `gridlock.ts`'s `@SPREAD` were. **That is a knob-semantics change, not a
   bug fix, and it must be named as one in the SUMMARY.**

**CHORUS has 177 characters free in Setup and needs +8 for class B as well.** Cost the bloom re-cut
**before** designing it. If the two together do not fit, that is a finding: report the shortfall in
characters and propose the cheapest honest alternative (the simplest being a shorter distance
expression), rather than dropping either fix silently.

**Where the residue does and does not show, measured, so nobody spends effort on the invisible:**
EUCLID, SONAR and GHOST all carry a bad literal and all three have a Timer that repaints the same
cells before residue accumulates — **measured residue after 25 s: zero cells**. Fixing them here is
correctness hygiene, not a bug fix, and their bench complaints are about precision, swipe and sync.
CHORUS and MORPH are the two the user actually saw.

## Class B — five sites, one declared exception

The touch event vocabulary, `e = status & 0x0f`, forwarded untranslated from the maXTouch T100:

| `e` | Name | Meaning | Confidence |
|---|---|---|---|
| 0 | NONE | no event this cycle | inferred |
| **1** | **MOVE** | contact moved | **user-verified on hardware** |
| 2 | UNSUP | un-suppressed | inferred |
| 3 | SUP | suppressed by grip/palm rejection | inferred |
| **4** | **DOWN** | contact started | **user-verified on hardware** |
| **5** | **UP** | contact ended | **user-verified on hardware** |
| 6 | UNSUPSUP | un-suppressed and suppressed in one cycle | inferred |
| 7 | UNSUPUP | un-suppressed and lifted in one cycle | inferred |
| 8 | DOWNSUP | down and suppressed in one cycle | inferred |
| **9** | **DOWNUP** | **down and lifted in one cycle — a very fast tap** | inferred, and treated as real throughout the catalog |

`TCHEVENTCFG = 0x00`, so nothing is disabled and every type is reported. Palm messages are dropped
before the callback, so a palm produces no callback at all.

**The three guards, and which is correct for what:**

| Intent | Correct guard |
|---|---|
| this contact ONSET | `e == 4 or e > 8` |
| this contact ENDED | `e == 3 or e >= 5 and e < 9` |
| this contact is LIVE (down or moving) | `e ~= 1 and e ~= 4 and e < 9 then return` |
| act on taps only, not drags | `e ~= 4 and e < 9 then return` |

**Do not restate this table anywhere new.** It already exists twice — `pad-sim.ts:228-241` and
`../zona-docs/docs/ZONA_REFERENCE.md` s4.6 — and a third statement will drift. The gate cites them.

**The five sites, measured against the pinned minifier:**

| Site | before → after | delta | free after |
|---|---|---|---|
| `lattice.setup` `e>=5` → `e>=5 and e<9` | 615 → 623 | +8 | 285 |
| `morph.setup` same | 507 → 515 | +8 | 393 |
| `chorus.setup` same | 729 → 737 | +8 | 171, **before** the bloom re-cut |
| `ghost.setup` same | 305 → 313 | +8 | 595 |

**Correct already, and named so the gate's exception list is not padded:** ETCH, FORGE, KEYS, SLAM,
SNAKE and QUADRANT write `e >= 5 and e < 9` or `e > 4 and e < 9`. ETCH, KEYS and SLAM are gone; FORGE,
SNAKE and QUADRANT survive.

**`stage.ts` is a FALSE POSITIVE and must be declared, not excused.** It writes
`if e==4 or e>8 then ... elseif e>=5 then Z(s.l,4) end`. Code 9 takes the **first** branch, so it
never reaches the `elseif` — the guard is correct because of the chain around it, not because of its
own text. A syntactic scan cannot see that. Put it in `DECLARED_EXCEPTIONS` with the reason in a
sentence, the way `EXCLUDED_FROM_ROW` and `INTENDED_DIVERGENCE` are written, so the next reader learns
why rather than learning that the gate has holes.

## The two behavioural probes

Syntactic gates catch the shape. These two catch the behaviour, and one of them caught four entries in
a single run during research.

**The matched-pair residue probe.** Run an entry twice for the same tick count, once with a gesture
and once without, **double-tapping any latch back to its start so a genuine state change is not
counted as residue**, and assert no cell differs after settling. About twenty lines. It catches every
future class-A regression behaviourally rather than syntactically, including ones no `glpfs`/`glt`
pair scan can see.

**The fast-tap parity probe.** `touchTap` (the one path that synthesises code 9) and a slow
down/move/up on the same cell must produce the **same MIDI**. Compare the message lists, not their
lengths, so a note-off without its note-on fails rather than passing on a count.
