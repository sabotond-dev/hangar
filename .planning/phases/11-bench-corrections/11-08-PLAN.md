Three entries the user could not draw on.

> EUCLID: *"doesn't sense the finger its really difficult to add or remove, and its not precise at all,

> SONAR: *"not precise enough, notes should disappear after a while. include synchronization, clock

**The named cause is event filtering, not arithmetic**, and it is a different class from 11-02's fast
tap: these three handle code 9 correctly and simply **never look at drags**.

```
euclid  if e~=4 and e~=9 then return end
sonar   if e~=4 and e~=9 then return end
steps   if e~=4 and e<9  then return end
```

**Accepting MOVE is not enough on its own, and this is the part that costs characters.** All three
**toggle** a cell, and a swipe delivers a MOVE every 10 ms — so a finger resting inside one cell would
toggle it back and forth at **100 Hz**. A per-contact last-cell guard is required, and it is what most
of the budget goes on.

**Two of the four asks are not built, and they are named rather than dropped.** Clock sync — EUCLID's
*"MIDI sync the circles"*, SONAR's *"include synchronization, clock sync"*, STEPS's *"same as"* — is
**blocked twice over**, and even a yes on the first blocker leaves the second standing. This plan
plans nothing that depends on it and says so where the entries live, so the next person to read
`euclid.ts` finds the reason rather than a gap.

Purpose: three entries answer a finger, with the toggle-storm the naive fix would cause designed out.
Output: three entries edited, one behaviour test, and one clearly-labelled non-delivery.

## The guard, and what it costs

The shape, costed on EUCLID against the real minifier:

```lua
self.q={}
...
if e~=1 and e~=4 and e<9 then s.q[i]=nil return end
local m=x*9//128+y*9//128*9
if s.q[i]==m then return end
s.q[i]=m
```

**EUCLID Setup 702 → 778, `+76`, 130 free, `checkSyntax` accepts.** Affordable, and it is the tightest
of the three by a wide margin. **SONAR (432 Setup, 475 free) and STEPS (388, 518) have far more
headroom**, so if the shape has to be trimmed for EUCLID it should still be written in full for the
other two rather than degraded uniformly — one entry's budget is not a house style.

Note the guard **clears on contact end** (`s.q[i]=nil`) as well as filtering repeats. Without the
clear, a second contact on the same cell after a lift would be swallowed. Write the clear in the 11-02
convention.

**Two details worth checking rather than assuming:**

1. **EUCLID's cell index is not the pad's cell index.** `euclid.ts` maps a touched cell to a ring
   position through `self.i[m]`, and returns early when the cell is not on a ring. The guard should
   remember the **cell** (`m`), not the ring position, so that swiping across a non-ring cell and back
   onto the same ring cell behaves sanely. Read the mapping before writing the guard.
2. **STEPS's grid is 8x8 inside a 9x9 pad.** `steps.ts` computes `n=c+r*8` and returns early when
   `c>7 or r>7`. The guard's key must be consistent with whichever index the toggle uses, or a swipe
   along the ninth column will behave oddly at the boundary.

## SONAR's other two asks

**"The center should be always lit up."** SONAR's Setup paints all 81 cells at `glp(c,1,0)` and lights
armed cells from the touch callback. Cell 40 is the sweep's origin. Lighting it permanently is a
`glc` + `glp` pair in Setup on a layer the sweep does not overwrite — **check which layer the Timer
writes** (`sonar.ts:59` arms layer 2 for the sweep and layer 1 for armed cells) before choosing, and
confirm the centre stays lit **while the sweep passes over it**, which is the case the user will
actually look at. 475 free; cost it.

**"Notes should disappear after a while."** SONAR fires note-on as the sweep crosses an armed cell and
today the note-off timing is what it is; read the Timer at `sonar.ts` before designing. Two honest
readings, and **they are not equally likely**:

- **The note is released after a fixed time** — a note length. Straightforwardly a `gms` 128 issued a
  known number of ticks later, or immediately, depending on how the sweep is structured.
- **The armed cells themselves clear after a while** — the pattern fades. That is a bigger behaviour
  change and it is not what *"notes should disappear"* most naturally says.

**Read the current note handling first.** If notes already hang because a note-off is missing or
mistimed, the ask is a bug report and the fix is small. If they are already released, the ask is for a
shorter length and the fix is a constant. **Say which it turned out to be**, because the two produce
very different SUMMARY entries and the user's words support either.

## Clock sync: not built, and named

Both gates are shut and the second does not open when the first does.

1. **The hardware answer is unknown.** `docs/MIDI-IN-PROBE.md` is a written, minifier-checked, 264-
   and 328-character pair of probe scripts for exactly this question, and its last line reads **"None
   yet. This probe has not been run."** The document is explicit that `gts` is dead on ZONA and
   `rtmrx_cb` is the only clock route the hardware has, so **a no on Part B does not send this family
   down a different road; it closes it.**
2. **Even a yes does not unblock the site.** HANGAR's Lua host has **no inbound MIDI path of any
   kind**: `grxm` is a recorded no-op that discards its slot argument, and `midirx_cb` and `rtmrx_cb`
   appear nowhere under `src/`. A clock-locked card would run on a real ZONA and sit **motionless in
   its own catalog card**. The prerequisite is a synthetic MIDI source and a synthetic clock in
   `src/lib/sim/`, which is a phase, not a task.

**Write both blockers into `euclid.ts`'s and `sonar.ts`'s headers**, in two sentences each, beside the
existing design notes — not into a planning document. The next person to read the entry should find
the reason there. `steps.ts` cites SONAR's note rather than restating it a third time.

**Do not plan, sketch, stub or scaffold anything that depends on the answer.** 11-16 hands the probe
to the user as a hardware row.
