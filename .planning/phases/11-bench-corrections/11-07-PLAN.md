<objective>
CONSOLE drew three separate complaints from the bench, more than any other entry, and it is the
**second-tightest Setup in the catalog** — 785 of 908, **121 free**. That combination is why it gets a
plan to itself.

> CONSOLE: *"should react to touch or swiping as well not just pushing, also clamp issue in the top row
> because its not precise. you should not be able to interact with the 'muted' faders."*

**The clamp complaint has a named cause and it is arithmetic, not event handling.** Sweeping a finger
down column 4 through the real Lua host emits exactly eight values:

```
0, 15, 31, 47, 63, 79, 95, 111        (controller 20)
```

Row 0 is the mute strip, so `r` runs 1..8, `h = 8 - r` runs 7..0, and the emitted value is
`h*127//8`, whose maximum is `7*127//8 = 111`. **The mute row owns the top of the fader's travel, so
the fader has eight steps and cannot reach the top.** Both readings of *"clamp issue in the top row
because its not precise"* land on that same fact.

**`h*127//8` → `h*127//7` is +0 characters** — both literals are one digit — and it makes the eight
steps span 0..127 exactly.

**The roadmap groups CONSOLE with the swipe family and that grouping is wrong.** CONSOLE already ships
`if e~=1 and e~=4 and e<9 then return end`: it accepts MOVE today and its fader body already tracks a
swipe. **Only its mute row is onset-gated** (`if e==4 or e>8`). That is a much smaller change than the
per-contact cell guard EUCLID, SONAR and STEPS need in 11-08, and conflating them would spend
characters CONSOLE does not have.

Purpose: three bench complaints on the catalog's second-tightest card, two of them for five characters
between them.
Output: one entry edited, two behaviour tests, and a measured margin.
</objective>

**CONSOLE as shipped**, `console.ts:130`, Setup only, no Timer, 785 of 908:

```lua
self.touch_cb=function(s,i,e,x,y)
  if e~=1 and e~=4 and e<9 then return end
  local c=x*9//128 local r=y*9//128
  if r==0 then
    if e==4 or e>8 then
      local m=not s.m[c] s.m[c]=m
      s:gms(@CH,176,@CC+c,m and 0 or s.v[c]*127//8,0)
      P(s,c)
    end
    return
  end
  local h=8-r
  if h~=s.v[c] or s.m[c] then
    s.v[c]=h s.m[c]=nil s:gms(@CH,176,@CC+c,h*127//8,0) P(s,c)
  end
end
```

Read the whole file, including `P(s,c)`'s two-layer paint, before touching any of it.

**The three asks, costed:**

| Ask | Change | delta | free after |
|---|---|---|---|
| Full scale | `h*127//8` → `h*127//7`, **at both sites** — the fader body and the unmute restore | **+0** | 123 |
| Muted faders inert | the fader body returns early when `s.m[c]` is set | **+5** | 118 |
| The mute row takes a swipe | `if e==4 or e>8` in the `r==0` branch relaxed to accept MOVE | measure | — |

**Two sites, not one.** `h*127//8` appears in the fader body **and** inside the mute branch, where the
unmute restores the fader's stored value. Changing one and not the other means an unmute jumps to a
different value than the fader shows. **Grep the file rather than trusting this sentence.**

**"You should not be able to interact with the muted faders" is a real behaviour change and it
conflicts with what the card does today.** As shipped, touching a muted fader **unmutes it**:
`s.m[c]=nil` in the fader body. That is a shipped design decision — a fader you touch is a fader you
want — and the user is overriding it. Two consequences:

1. **Once muted faders are inert, the only way to unmute is the mute row.** Confirm that is reachable
   and obvious before shipping it, because a mute you cannot undo except from one specific row is
   worse than the complaint. The mute row is row 0 of the same column, so it is reachable; **say so
   with the geometry rather than assuming it.**
2. The `+5` figure assumes the early return replaces the `s.m[c]=nil` clear. **Measure it.**

**The mute row and the swipe.** The `r==0` branch gates on onset (`e==4 or e>8`) because it
**toggles**: accepting MOVE without a guard would toggle the mute at 100 Hz while a finger rests on
it. Two honest shapes, and the plan must choose one and say why:

- **A per-contact last-cell guard**, the same shape 11-08 gives EUCLID: remember the last mute cell
  each contact toggled and ignore repeats. Correct, costs the most, and is the same idiom as the
  neighbouring plan.
- **A swipe that SETS rather than TOGGLES** — dragging across the mute row mutes everything it
  crosses, and the toggle stays on the press. Cheaper, and arguably what a mixer's mute row should do,
  but it is a **different behaviour** from what the user asked and must be presented as a choice
  rather than shipped as an interpretation.

**Cost both before choosing.** CONSOLE has 118 free after the first two asks, and the per-contact
guard on EUCLID cost 76. **If the guard does not fit, that is a finding**: report the shortfall, state
which shape does fit, and let the SUMMARY carry the decision to 11-16 rather than trimming the ask.

**One thing that is NOT the answer, and it is the obvious wrong one.** *"Not precise enough"* on a
cell-grid entry is never a coordinate-resolution problem. Firmware reports 0..127 by dividing the
native 0..1023 by 8; for a nine-cell grid each column is 14.22 units wide, so 7-bit quantisation
determines a column boundary to within about **0.07 of a cell**. Unlocking 10 bits with
`self:txma(1023)self:tyma(1023)` improves that to 0.009 of a cell — imperceptible — and costs **+30**.
**Do not spend CONSOLE's 121 characters on it.** It matters only for continuous output, which is why
STRIP uses it and no cell-grid card does.

**The value sweep is the test.** Drive a finger down each column through the real Lua host and collect
the emitted controller values. Before: eight values topping out at 111. After: eight values spanning
0..127 with **127 present**. Assert the presence of 127 and the count of distinct values, not the
whole list — a list assertion would go red on any future re-scaling for no reason.
