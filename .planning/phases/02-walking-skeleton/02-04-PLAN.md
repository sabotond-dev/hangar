<standing_rules>
- **The restore rule (mandatory, phase-wide).** A successful `CONFIG/EXECUTE` clears
  `page_change_enabled` in firmware (`grid_decode.c:1279`) and only an inbound `HEARTBEAT` with
  `TYPE 255` restores it (`grid_decode.c:717`). Every arm of the run — heartbeat on and heartbeat off,
  and any arm abandoned after a write — ends with one, logged as its own step. The page does this
  automatically and also carries a `Restore heartbeat` button. The checklist has a dedicated row for
  it and the run is not complete until that row passes. Without it the user's ZONA cannot change page
  until it is power-cycled.
- **The executor never touches the hardware and never deploys.** `npm run deploy` is the user's
  (Phase 1 D-08). The checklist offers both routes: deploy for HTTPS from any machine, or
  `npm run preview` on `localhost`, which is also a secure context.
- **Never `file://`.** It is not a secure context, `navigator.serial` is simply absent, and the page
  correctly shows its degrade state — which reads as a broken page and wastes an hour.
- **Stale-wrangler preflight before ANY build or e2e run** (Phase 3 pattern): `netstat -ano | grep -w
  LISTENING | grep ":4173"`; walk to the `npx-cli` root; `powershell -NoProfile -Command "taskkill
  /PID <root> /T /F"`. Killing `workerd` alone does not work.
- Playwright output goes to `.tmp-e2e/`, never `test-results/`. No test title contains `failed`.
- No Claude attribution anywhere, no emojis, including in the runbook.
- Files created in a task are `git add`ed before any negative check is run against them.
</standing_rules>

Preconditions for the run, stated so a failure is not misdiagnosed (02-RESEARCH.md
"Manual-Only: criteria 1-4"):

- Grid Editor **fully quit** — tray icon, Quit, not just the window closed. Except for step 0, which
  needs it running on purpose.
- The module carries its **factory configuration** (D-02). The factory Setup is dim and static, so
  "behaves as before" is proven by the re-fetched strings, not by eye.
- **Only the ZONA is attached.** Another Grid module makes the page disable the store button, which is
  correct behaviour (D-12) and ends the run early.
- Served over HTTPS on the deployed preview URL, **or** `http://localhost` via `npm run preview`.
- **Keep the tab in the foreground for the whole run.** A backgrounded tab throttles timers to 1 Hz
  and invalidates every latency measurement.
- Chrome, Edge, or Firefox 151+. On Firefox expect a site-permission add-on prompt **before** the port
  chooser — that is normal Firefox behaviour for this API, not an extension install.

Expected shapes, so a surprise is recognised as one rather than as a fault:

- The factory touch Setup is 641 characters in the pinned package's own default table and the Timer is
  22. A factory module should return strings of about those lengths. Treat a mismatch as interesting
  and record it — the run echoes back whatever it fetched, so it is still a no-op either way.
- During the store the module's border LEDs animate yellow-dim and then settle
  (`grid_decode.c:986-987`). That is the store working.
- The store reloads the page from flash and restarts the module's script
  (`grid_decode.c:956-960`). The stored bytes are unchanged; the running script is restarted. With the
  static factory config this is invisible.
</interfaces>

  <what-built>
Everything except the run itself.

- `src/lib/protocol/` — the four outbound descriptors with the desktop's verbatim parameter names,
  the frame scanner, the decode guard that checks truthiness before the class decoder, the response
  matcher that correlates an acknowledgement by the id firmware echoes and never correlates a report
  that way, and the refusal that keeps a write from happening on an untrustworthy fetch.
- `src/lib/transport/` — the real Web Serial transport (2 Mbaud, a 4096-byte read buffer, owned close
  ordering, `navigator.serial` connect and disconnect listeners), a fake that replays genuine encoded
  bytes and injects five faults, and the request queue: one outstanding request, deadlines measured
  from `performance.now()`, retry bounded at three, a negative acknowledgement rejecting immediately,
  and a heartbeat that can never resolve a waiter.
- `src/lib/transport/sequence.ts` — the whole no-op cycle as tested functions, ending with the type
  255 heartbeat in a `finally` so it is sent even when a write is refused.
- `/dev/skeleton/` — a prerendered, unlinked diagnostic page with seven controls, the host-heartbeat
  and pacing toggles, a frame log, and an Export JSON button.
- 440 unit tests and 10 end-to-end tests green, and `build/dev/skeleton/index.html` present.

What is NOT proven, and is exactly what this checkpoint is for: that any of it works against a real
module. Every frame so far has been one HANGAR encoded and HANGAR decoded.

  <how-to-verify>
Open `docs/SKELETON-RUNBOOK.md` and follow it. The steps, restated here so this checkpoint is
self-contained:

**Before you start**

1. Quit Grid Editor completely — tray icon, Quit, not just the window. (Except step 0, which needs it
   running on purpose.)
2. The ZONA carries its factory configuration.
3. Only the ZONA is attached — no other Grid module, or the page will disable the store button.
4. Chrome, Edge, or Firefox 151 or newer. On Firefox a site-permission prompt appears **before** the
   port chooser; that is normal.
5. Keep the tab in the foreground for the whole run. A background tab throttles timers and ruins every
   latency number.

**Getting the page open** — one of these two, and only you can do either:

- `npm run deploy` from this machine, then open `https://<your preview URL>/dev/skeleton/` and enter
  the Basic Auth credentials. Use this if you want to run from another machine.
- `npm run preview`, then open `http://127.0.0.1:4173/dev/skeleton/`.
- Never open the built `index.html` from disk. `file://` is not a secure context and the page will
  correctly, and confusingly, show its no-Web-Serial state.

**The run**

0. **Port conflict.** With Grid Editor still running and connected, click `Connect` and pick the ZONA.
   The page should name Grid Editor and list the recovery in order — quit the Editor from its tray
   icon, unplug, wait, replug, reload, connect — instead of a raw `Failed to open serial port.` Then
   quit the Editor and reload.
1. **Connect and identify.** Click `Connect`. Before picking, note what the chooser lists: it should
   be one device, with no bootloader entry. Pick the ZONA. Within about a second the page should show
   `ZONA`, its revision, its firmware version, its SX and SY, heartbeat `TYPE 1`, and an active page
   number.
2. **Fetch.** Click `Fetch`. Both strings should appear verbatim with their character counts, each
   with an acknowledgement latency in milliseconds. Neither should be empty and neither should be 909
   characters or longer. Setup will be several hundred characters; Timer will be short.
3. **Write back, then store.** Click `Write back (RAM)`. The page writes Timer first, then Setup, and
   reports each acknowledgement separately with its own latency. Then click
   `Store to flash - writes the config that is already there`. The module's border LEDs will animate
   yellow-dim during the store and then settle — that is the store working. Expect three
   acknowledgements and no negative acknowledgement.
4. **Re-fetch.** Click `Re-fetch`. The page should report byte-identical: yes, for both events.
5. **Heartbeat off arm.** Reload. Set host heartbeat to **off**. Repeat 1 to 4. Note whether inbound
   heartbeats keep arriving for at least ten seconds and whether all three acknowledgements still
   arrive, against the definition printed on the page.
6. **Burst probe.** On each arm, click `Run burst probe` at 10 ms and again at 0 ms. Twenty read-only
   fetches each; note the timeouts, negative acknowledgements and latency spread the page reports.
7. **Restore — do not skip this on any arm.** The page sends one `HEARTBEAT TYPE 255` at the end of
   every run and reports `page change restored`. If anything went wrong at any point, click
   `Restore heartbeat` yourself before closing the tab. A config write leaves the module unable to
   change page until that heartbeat arrives or the module is power-cycled.
8. **Export.** Click `Export JSON` on each arm and keep the files.
9. **Free observation.** Quit the browser, reopen it, open the page, and read the line reporting how
   many ports `navigator.serial.getPorts()` returned. Note the number.

**What to hand back**

- The exported JSON files, one per arm — say where they are (a path, or paste them).
- Anything the page showed that the runbook did not predict.
- Whether step 0's port-conflict message read as helpful or as jargon.

**If it goes wrong at any point:** click `Restore heartbeat`, then describe what you saw. A run that
ends in a named failure state with the restore sent is a useful result, not a wasted session — the
failure paths are exactly what Phase 6 and Phase 7 are built around.
  </how-to-verify>
