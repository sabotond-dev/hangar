The questions to answer, from D-08:

| | Question |
|---|---|
| (a) | Is an outbound 300 ms host heartbeat required? Did the module keep heartbeating and keep acknowledging without it? |
| (b) | Is the desktop's fixed 10 ms pre-send sleep load-bearing at 2 Mbaud? |
| (c) | Measured acknowledgement latencies for `CONFIG/FETCH`, `CONFIG/EXECUTE` and `PAGESTORE` against the desktop's 250 / 500 / 3000 ms, and the honest timeouts HANGAR should ship. |
| (d) | Was the active-page report observed unprompted, and what page number did it carry? |
| (e) | Were heartbeats from any other module seen? |
| (f) | Does the Lua formatter WASM resolve from a plain static build? |

(f) is already answered: Phase 3 proved it in a real browser against the production build under the
Worker (`03-06-SUMMARY.md` — 628,148 bytes served as `application/wasm`, empty console). Answer it by
reference and move on; the skeleton never loads the formatter at all.

The predictions this run confirms or falsifies, so the document can say which happened:

- (a) **Not required**, HIGH confidence from firmware source: the module heartbeats on an
  unconditional 250 ms timer (`grid_esp32_port.c:209-223`, `:415-418`), its type flips to 1 on USB
  connect with no host involvement (`:463-471`), and nothing in the `CONFIG` or `PAGESTORE` decode
  paths consults `editor_connected` — its only use anywhere is gating LED preview generation
  (`grid_ui.c:746-748`).
- (b) A mechanism, not a prediction: a `CONFIG/EXECUTE` is `49 + ACTIONLENGTH` bytes — 690 for a
  641-character Setup, 957 at the budget — against a 512-byte CDC RX buffer
  (`tusb_config.h:39`) feeding a 2048-byte ring that **silently discards a whole message** when it
  cannot fit (`grid_transport.c:151-153`). The burst probe is the measurement.
- (c) Start at 1000 / 500 / 3000, and set the shipped values at roughly ten times the observed p99 for
  the fast paths.
- (d) The active page rides on **every** heartbeat once USB is connected
  (`grid_transport.c:199-203`), four times a second. There is no fetch for it and none exists.

Two caveats that must appear in the document because Phase 7 depends on them:

- The store's success callback reloads the page from flash and restarts the module's script
  (`grid_decode.c:956-960`). "Provable no-op" is a claim about the stored bytes, not about the running
  script. With the static factory config it is invisible; with an animating config it is a visible
  reset.
- `requestPort()` granted this origin access to that port. The grant is visible in the browser's
  site settings and may persist. `SerialPort.forget()` is Phase 6's.
