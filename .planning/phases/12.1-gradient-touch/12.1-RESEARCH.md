## The five findings that shape the plan

1. **The sensor saturates inside the outer LED ring, and the cell pitch is about 17-18 raw units, not
   14.2.** Probe A Q5 read the physical corners at (127,1), (1,1), (0,126) - the full 0..127 range
   within one unit at the edge - and bench 3 read a finger centred on LED (row 1, col 7) as the corner
   cell (0, 8). Both are only consistent if LED index 7 sits at x >= 114 and LED index 1 at y <= 13:
   with the centre at (64, 68) that is a pitch of >= 16.7 per LED, and the outermost LED centres
   extrapolate to about -6 and 134 - **outside the sensor's 0..127**. The firmware's own T100
   configuration says why: `XLOCLIP`/`XHICLIP` 45 and `YLOCLIP`/`YHICLIP` 50 trim the controller's
   reported range inside the physical matrix (`mxt144u_cfg.raw:60`, bytes 11-12 and 22-23; MEDIUM on
   the offsets, LOW on the unit). The naive `x*9//128` was wrong by a third of an LED at every edge and
   right only at the centre. Section 1 carries the derivation; the probe measures it.
2. **The gradient does not fit in one slot beside the expiry machinery, and it does not have to.**
   `G` alone is 329 characters; with the map (`U` 126, two knot tables 65) and the block clear (`V` 62,
   `E` +32) the whole library is **1,384** in one string (section B.3, every variant measured, the
   smallest honest one 1,043). The system element's Timer event (255/6) is a 908-character slot
   nobody has claimed (`SLOT-ARITHMETIC.md` §2: *"nothing, never asked"*), D-19 retired the refusal to
   write it, and the cross-slot call mechanism is proved on the user's ZONA twice
   (`13-gui-overhaul/PROBE-RESULTS-2026-09-10.md`). Split: **255/0 at 782 (126 free), 255/6 at 683
   (225 free)**, joined by a ten-character `self:tim()`.
3. **`Q`'s hysteresis stays, moved into calibrated space; the gradient does not make it unnecessary.**
   The brief supposed the gradient removes the cell to flicker between. It removes it for the
   *light*, not for the *toggle*: EUCLID, STEPS, RADAR POINTS and SONAR still flip one step per press,
   and a finger resting midway between two LEDs would toggle both alternately at 100 Hz under a bare
   argmax - the exact Q2 failure. So `W` now holds the previous LED while the calibrated coordinate is
   within 45/64 of its centre; the probe's 71/72 line becomes a seven-value hold band (69..75) in the
   VM, the same width 12-07 measured, now centred where the LEDs actually are.
4. **The preview must push the mouse through the same map, and it already has one place to do it.**
   `mapAxis` (`src/lib/sim/touch.ts:42-46`) is the only mouse-to-coordinate door for the hero and the
   coverflow, and `cellToCoord` (`src/lib/sim/demo.ts:112-115`) is the only door for authored demo
   gestures. Both get the knots; neither `Coverflow.svelte` nor `HeroSurface.svelte` needs a line
   changed until the axis argument is threaded through, which can wait for 13-07 and 13-09 to land.
5. **Two of the three tap complaints are calibration, one is hardware.** A tap on EUCLID's outer ring
   (LED index 1 or 7) lands, uncalibrated, on the pad's outer LED ring - which is on no Euclid ring
   at all (`euclid.ts:179`, `if not v then return end`) - and nothing happens. That is *"i need to tap
   multiple times"*. The map fixes it. Q3's dropped single taps are the controller's detect
   integration and threshold; no configuration sees an event that was never sent. Nothing in EUCLID's
   own onset handling is at fault (section E).

## Section 1 - What the bench and the probe already say, in the firmware's units

### 1.1 The unit

Every CC the two probes reported is the touch element's default coordinate: **0..127 per axis**,
integer. `grid_ui_touch.c:75-78` sets `x_min = y_min = 0`, `x_max = y_max = 127`;
`grid_ui_touch.c:113` scales the controller's 10-bit value as
`new = lerp(min, max + 1, raw / 2^adc_bit_depth)` = `floor(raw / 8)` at the defaults, then clamps
(`:115`) and mirrors if min > max (`:117-119`). Probe A's script sent `s:gms(i,176,20,x,0)` - the
value unscaled - so **CC20 = x and CC21 = y as the Lua saw them**. The controller's own value is
16-bit on the wire (`grid_esp32_touch.c:840-841`, `msg[2] + (msg[3] << 8)`) with
`XRANGE = YRANGE = 1023` configured (`mxt144u_cfg.raw:60`, Linux-anchored offsets 13-14 and 24-25),
so the Lua sees 10 bits reduced to 7; `self:txma(1023)` (TRACKPAD) makes the lerp the identity and
the same map applies at eight times the scale. HIGH.

**There is no calibration, no edge mapping, no per-axis correction anywhere in the firmware's path
from the controller to Lua.** `grid_ui_touch_store_input` (`:101-143`) is lerp, clamp, mirror, a
per-id change gate on (x, y, event), and a ring write. What the controller reports is what Lua gets.
HIGH - read end to end.

### 1.2 What the corner and centre readings imply

| Reading (Probe A Q5) | Value | What it says |
|---|---|---|
| corner | 127, 1 | x pins at the top of the range at the physical corner |
| corner | 1, 1 | both axes pin at the bottom |
| corner | 0, 126 | y pins at the top |
| centre | 64, 68 | x centred; y four units low, consistent with Q1's still finger at (65-66, 66-67) |

A finger in a physical corner reaches 0 or 127 within one unit. So the sensor's reported range is
**fully used before or at the physical edge** - it never runs out of range, it runs out of pad. That
alone does not say where the outer LEDs sit. Bench 3 does: *"if my finger is directly on top of the
LED in row 2 column 8 the top right LED lights up, same in each corner"* - one-based row 2 / column 8
is zero-based (1, 7), and it read as cell (0, 8). Under the naive map that needs `x >= 114` (col 8
begins at `114*9//128 = 8`) and `y <= 13` (row 0 ends at `13*9//128 = 0`... `14*9//128 = 0` too;
row 1 begins at 15). With the centre LED at (64, 68) and a uniform pitch `d`: `64 + 3d >= 114` gives
`d >= 16.7`; `68 - 3d <= 14` gives `d >= 18`. **The pitch is roughly 17-18 raw units per LED, not
128/9 = 14.2**, and the outermost LED centres extrapolate to about `64 - 4*17.5 = -6` and
`64 + 4*17.5 = 134`: **beyond the range**. The sensor reports 0 or 127 from about a third of an LED
pitch inside the outer LED centre outward. MEDIUM - an inference from two bench sentences and one
probe row; the probe in section A replaces it with nine measured knots per axis.

The controller configuration is consistent with that picture, which is why it is worth stating even
at MEDIUM/LOW confidence. `mxt144u_cfg.raw:60` (T100, standard layout; the Linux driver anchors
CTRL 0, CFG1 1, TCHAUX 3, XSIZE 9, XRANGE 13, YSIZE 20, YRANGE 24 - the others are the public T100
order between them):

| Byte | Name | Value | Reading |
|---|---|---|---|
| 9 / 20 | XSIZE / YSIZE | 12 / 12 | a 12 x 12 electrode matrix |
| 10 / 21 | XPITCH / YPITCH | 0x32 = 50 / 50 | 5.0 mm electrode pitch **if** the unit is 0.1 mm (LOW - unit from the public T100 description, not verified) - a 60 x 60 mm matrix |
| 11-12 | XLOCLIP / XHICLIP | 45 / 45 | the low and high ends of X trimmed before the range is scaled to 0..1023 |
| 22-23 | YLOCLIP / YHICLIP | 50 / 50 | Y trimmed a little more than X |
| 13-14 / 24-25 | XRANGE / YRANGE | 1023 / 1023 | the reported range after clipping |

If the clip unit is also 0.1 mm, the reported 0..1023 spans 51 mm in X and 50 mm in Y of a 60 mm
matrix, and if the nine LEDs sit on a pitch near 7 mm (56 mm outer-centre to outer-centre) the
reported range runs out about 2.5 mm - a third of an LED - inside the outer LED centres, which is
exactly the -6 / 134 extrapolation above. That is three LOW-confidence numbers agreeing with one
MEDIUM inference, not a measurement. **Question for the user: is the LED pitch known?** It is only a
sanity check - the probe measures the map directly and needs no geometry.

The Y clip being larger than the X clip (50 versus 45) also predicts a slightly *smaller* pitch in
raw units on Y than on X, and a centre that may not be exactly 64 on both axes. Q5's (64, 68) is
within finger-placement noise of that; the probe will say. **The map should be per-axis** - do not
assume the two tables are equal.

### 1.3 The boundary, restated in these units

Q2's one-unit-wide boundary (71/72) is unchanged in kind: the controller reports integers and the
naive divisor flips at 71.1. What changes is *where the boundaries fall*: at 17.5 per LED the true
LED midpoints are at about 72.5 and 90 (x), not 71.1 and 85.3 (x) as the naive map puts them, and the
outer two boundaries are off by most of a cell. 12-07's hysteresis was correctly centred on the
wrong lines. Section B moves it.

## Section A - The calibration probe (Probe C)

### A.1 Design

The MIDI monitor route worked for Probe A (the user copied CC rows verbatim), so the readout is
**MIDI, one triple per LED, on the lift** - not a flood, and nothing to transcribe while a finger is
down. The pad's own job is to **show the target**: one white LED at a time, lit by *address* and never
from the finger's coordinates, so the probe cannot display the map it is measuring. The user rests a
finger dead-centre on the lit LED, holds a beat, lifts; the probe sends the last position it saw
before the lift as CC20 (x), CC21 (y) and CC22 (target number 1..21) on channel 1, darkens that
target and lights the next. A second finger is ignored; a 22nd lift does nothing.

**Targets, in order (21):** row 4 left to right (cells 36..44), then column 4 top to bottom without
the centre (4, 13, 22, 31, 49, 58, 67, 76), then the four corners (0, 8, 72, 80). Row 4 gives the
nine X knots, column 4 the nine Y knots, and the corners check that the map is separable (a corner
should read as (KX[0], KY[0]) etc. within about 2 units).

**Why the last sample before the lift and not the lift's own coordinates:** a lifting finger rolls; the
UP message carries wherever it left. The last DOWN/MOVE sample is where the finger rested. Q1 shows
the rest wobbles by one unit; that is the measurement's noise floor and it is fine.

### A.2 The paste

pinned `compressScript` after `initLuaFormatter()`, run through its full 21-target walk in wasmoon

### A.4 How the map is derived from the report

- Targets 1..9 (cells 36..44) give **`KX[0..8]`** = the CC20 of each, in order.
- Targets 10..13 (cells 4, 13, 22, 31) give **`KY[0..3]`**; target 5 (cell 40) gives **`KY[4]`** from
  its CC21; targets 14..17 (cells 49, 58, 67, 76) give **`KY[5..8]`**.
- Targets 18..21 (corners) are the **separability check**: target 18 should read about
  `(KX[0], KY[0])`, 19 `(KX[8], KY[0])`, 20 `(KX[0], KY[8])`, 21 `(KX[8], KY[8])`. If any corner is
  off by more than 3 units on an axis, the map is not a product of two one-dimensional maps and this
  document's model is wrong - stop and report, do not fit.
- The knot tables must be **strictly increasing**. If two neighbouring readings are equal (both
  saturated at 0 or 127, plausible for the outermost pair on an axis that clips hard), nudge the inner
  one by one unit and record that the outer LED's centre is unreachable. `U` divides by the knot
  difference and Lua 5.4 raises on integer floor-division by zero.
- With two passes, average and round; with one, use it as read. A one-unit wobble is under 1/16 of an
  LED pitch and invisible in the gradient.
- The tables go into **one TypeScript source of truth** (`src/lib/catalog/calibration.ts`, section
  B.5), from which the Lua tables, the simulator's forward map and the tests are all derived.

**Is the sensor's active area symmetric, and is the map the same on both axes?** Unknown until the
probe. The configuration (Y clipped by 50, X by 45) and Q5's (64, 68) both suggest **no** - slightly
different pitch and centre per axis - which is why there are two tables and why the probe walks both
axes rather than assuming one.

### A.5 A variant with an on-pad readout (optional, 662 of 908)

If the MIDI monitor is unavailable, the same probe can also show each reading on the pad after the

show y the same way, on a blue layer 2, until the next press. Measured at 662, canonical,

## Section B - The primitive

### B.1 Shape

Everything the entries call keeps its name and signature except that `Q` now reads the calibrated
map, and two functions join:

| Name | Signature | Does |
|---|---|---|
| `U(v, k)` | raw axis value, knot table -> **0..512** (LED `n` at `n*64`) | the calibrated LED coordinate, piecewise-linear over nine knots, clamped to the table's ends |
| `G(s, i, e, x, y, l, b)` | touch element, contact, code, raw x, raw y, layer, peak phase | **the bilinear finger**: clears the contact's previous 2x2 block, and unless `e` is an end code lights the 2x2 block around the calibrated position with weights `(64-f)(64-g)`, `f(64-g)`, `(64-f)g`, `fg` over 4096, scaled by `b`; remembers the block in `B[i]` and the layer in `L` |
| `V(n)` | block origin | clears the 2x2 at `n` on layer `L` (called by `G` and by `E`) |
| `N(x, y)` | raw x, raw y -> cell 0..80 | the **nearest calibrated cell, no hysteresis, no state** - for a press-time lookup (ARC's stop cell; 13-15's region lookup) |
| `W(u, p)` | calibrated coordinate, held index or nil | hysteresis **in calibrated space**: hold `p` while `|u - p*64| < 45`, else `(u+32)//64` |
| `Q(s, i, e, x, y)` | unchanged | unchanged contract, cells now from `U` through `W` |
| `E(s, i)` | unchanged | now also clears the contact's block through `V` before calling `R` |
| `X`, `A`, `D`, `R` | unchanged | unchanged |

**Why `f` and `g` are in 64ths and the weights are integers.** Firmware Lua is 5.4 with integers;
`glp` wants an integer phase. `U` returns `n*64 + f` with `f` in 0..63 (64 at the far end of the last
segment, which the clamp `glim(u//64, 0, 7)` turns into `c = 7, f = 64` - the ninth LED is reached as
the *second* column of the eighth block, so no index ever leaves 0..8 and no cell is written twice).
`b * (64-f) * (64-g) // 4096` is at most `b`. No floats anywhere, no float-to-integer conversion for
`glp` to reject.

**The weights are linear, on purpose.** The firmware's phase-to-output curve is convex: one layer at
phase 0 emits `colour/20 * 254/512` (about 2.5 %), at 128 about 25 %, at 255 about 50 % of the colour
byte (`grid_led.c:46-85` lookups, `:298-302` `glc` setting min = c/20, mid = c/2, max = c, `:408-463`
the sum and the single divide by 512). A weight of one half therefore lands on 25 % duty, which the
eye reads as roughly 55-60 % brightness. Linear weights already read close to linear. A square-law
`G` was costed (+15) in case the bench says the dim end is too bright; it is not the default. MEDIUM
(the perceptual exponent is assumed, the firmware curve is read).

### B.4 Why nine knots and not two

The two-knot linear `U` saves 64 characters and would be right only if the sensor is linear across
the pad *and* the outer LED centres are inside the range. Section 1.2 says the second is false: the
outermost knots will read 0 and 127 (saturated), and the true centres lie outside. A linear map
through the saturated ends would place LED 1 at `1/8` of the range (16) when it actually sits at
about 11 - two thirds of an LED off. The nine-knot table absorbs the compressed outer segments and
any mid-pad non-linearity for free. With two slots there is no budget reason to prefer linear.
**Decision for the plan: nine knots per axis, per-axis tables, from the probe; if the probe shows
the seven interior knots within 2 units of a straight line through the ends, the executor may note
it and still ship nine.**

## Section D - The simulator

### D.1 What the preview does with a pointer today

`src/lib/ui/Coverflow.svelte:519-520` and `src/lib/ui/intro/HeroSurface.svelte:136-137` (the latter is
13-07's file, being edited now - cited, not read as stable) call
`mapAxis(event.clientX - rect.left, rect.width, engine.coordMax)`;
`mapAxis` (`src/lib/sim/touch.ts:42-46`) is `floor(offset/extent * (max+1))` clamped - **the naive
inverse of `x*9//128`**: each ninth of the canvas lands on one LED column. That was right when the
library read cells naively; it is now a lie in the direction that flatters the preview. The mouse
over LED 7 must produce what the *sensor* reports for a finger over LED 7 - about 116, not
`7.5/9*128 = 106`.

Authored demo gestures (`src/lib/sim/demo.ts:112-115`, `cellToCoord(cell, coordMax) =
floor((cell+0.5)*(max+1)/9)`) have the same naive inverse; a demo "finger on cell 0" today produces
raw 7, which the calibrated `G` would draw as 36 % LED 0 / 64 % LED 1 - a visibly off-target demo.

### D.2 The change

**The forward sensor map, in one place, from the same knots the Lua uses.**

- `touch.ts`: `mapAxis(offset, extent, max, axis: "x" | "y" = "x")` - compute the LED coordinate
  `u = offset/extent * 9 - 0.5` (LED `n` at `u = n`), interpolate the knot table at `u` (clamped to
  0..8), floor, then scale by `(max+1)/128` for the hi-res case (`coordMax` 1023: multiply by 8, which
  is the firmware's own `txma(1023)` identity). Below `u = 0` and above `u = 8` the map saturates at
  the outer knots, as the sensor does. The default `"x"` keeps both existing call sites compiling and
  correct on x; the two callers gain `"y"` on their second line once 13-07 and 13-09 have landed
  (section F). `touch.spec.ts` asserts LED centre `n` -> `KX[n]` / `KY[n]`, midpoints -> the knot
  midpoints, and the edges -> 0 / 127.
- `demo.ts`: `cellToCoord(cell, coordMax, axis)` returns the knot itself (scaled for hi-res). Two
  call sites (`:138-139`). `demo.spec.ts` moves.
- `frames.json` and `static/og/*.png` regenerate for every entry whose demo gesture or resting frame
  changes (the demo-driven cards - GHOST, MORPH and any added since 10-05 - and every re-fitted entry
  whose Setup now colours layer 0, since a coloured dark layer raises the resting bytes by the floor).
- `lua-host.ts`: `LuaHostOptions.systemTimer?: string`; `install()` and `restart()` run it as
  `self={tim=function(s) <timer body> end}` followed by the 255/0 body, so the Setup's `self:tim()`
  really runs the Timer body in the host as it does on the module (the host's `SELF_PRELUDE` then
  redefines `self` as the touch element, as today). `lua-pad-sim.ts` passes both strings for every
  `lua` entry. `host-surface.spec.ts` admits the new globals through `LIBRARY_GLOBALS` (derived from
  both strings). `lua-host.spec.ts` asserts `restart()` rebuilds `B` empty and that a missing
  `systemTimer` leaves `G` undefined (so the Sandbox cannot forget it silently).
- The interactive gradient then needs nothing else: `G` runs in wasmoon, the layer-0 phases render
  through the vendored `pad-sim.ts` render (`:1487-1507`, the same lookups and the divide by 512).
  **`pad-sim.ts` is not touched.** The phase walk is not touched.

**Does the pointer path need the inverse map?** No - it needs the **forward** map (LED position ->
sensor value); the Lua applies the inverse (`U`). The preview's honesty comes from both being derived
from one table. The only inverse in the tree is `cellToCoord`, and it becomes a table lookup.

Write order 255/6, 255/0, 0/6, 0/0. Fetch order free. CLEAR writes four defaults. Snapshot holds four.

### The one table
```
src/lib/catalog/calibration.ts   KX, KY (measured), MEASURED flag, strictly-increasing assertion
  -> library.ts        renders "KX={...}KY={...}" into the 255/0 string
  -> sim/touch.ts      mapAxis forward map (mouse -> sensor value)
  -> sim/demo.ts       cellToCoord = the knot
  -> *.spec.ts         expected cells read from the table, never literal
```

### Pattern: G before the entry's own early return
MORPH returns on `e==3 or e>=5 and e<9` before anything else; `G` must see end codes to clear the
block, so it is called first. Every other caller already lets `Q` see every code; `G` goes on the
line before `Q`.

### Pattern: light by address, measure by value
The probe lights targets by cell address and reports the sensor's value; it never draws from `x,y`.
Any future probe of the map keeps that separation or it measures its own display.

### Anti-patterns
- **A bare argmax for a toggle.** Removes the flicker from the light and puts it back in the note.
- **`local` state in 255/6.** Same rule as 12-07: every name is a plain global or the Setup cannot
  see it.
- **Writing 255/0 before 255/6.** `self:tim()` finds no method; the Setup raises once on the desk.
- **Threading the axis argument into `HeroSurface.svelte` / `Coverflow.svelte` while 13-07 / 13-09
  run.** The default argument exists so this can wait.
- **Costing at the defaults.** CHORUS 72, CONSOLE 69, MORPH 80 free are picker-corner numbers.

## Common Pitfalls

### Pitfall 1: The probe displays what it measures
Any on-pad feedback derived from `x,y` biases the user toward the displayed cell. Probe C lights
targets by address only. Warning sign: a probe script containing `x*9` or `U(`.

### Pitfall 2: `self:tim()` unproved on a page load
Install works regardless (the write runs the body); a KEEP + power cycle is where it fails. The first
hardware row is that cycle. Warning sign: `attempt to call a nil value (global 'G')` after a
power-cycle, none after TRY.

### Pitfall 3: Equal knots
Two saturated readings at an end make `k[i+1]-k[i] = 0` and `U` raises on `//0`. `calibration.ts`'s
spec asserts strictly increasing; the derivation rule nudges.

### Pitfall 4: RADAR / SONAR's centre marker on the finger layer
`V` clears the 2x2 block; when the block covers cell 40 the sweep origin goes dark. The re-fit
re-lights it after every `G` call (+20 each). Warning sign: the centre dot vanishing under a finger.

### Pitfall 5: Demo cards off target
`cellToCoord` left naive puts demo fingers a third of a cell inward at the edges; the gradient shows
it. `demo.spec.ts` asserts the knot.

### Pitfall 6: Count chains across concurrent phases
Band 1 adds tests while 13-08..13-13 carry chains. State the band's delta once by name (12-12's
precedent) or the next 13 plan's `PREV_TESTS` is wrong by exactly that delta.

### Pitfall 7: `A` sends raw coordinates
LUMEN's CC pair reaches 0/127 at the sensor's saturation, a third of an LED inside the outer LEDs.
Unchanged by this phase unless the user asks (question 4); a header sentence either way.

### Pitfall 8: Measuring `G` under a stub `glim`
This research's VM used a JS stub; the plan's smoke test must go through `createLuaHost` so the
host's integer `glim` and the real `glp` argument checks are exercised.

### The forward map in the preview (shape, not final code)
```ts
// src/lib/sim/touch.ts
import { KX, KY } from "../catalog/calibration";
export function mapAxis(offset: number, extent: number, max: number, axis: "x" | "y" = "x"): number {
  if (extent <= 0) return 0;
  const k = axis === "x" ? KX : KY;
  const u = Math.min(Math.max((offset / extent) * 9 - 0.5, 0), 8);   // LED n at u = n
  const i = Math.min(Math.floor(u), 7);
  const v = k[i] + (k[i + 1] - k[i]) * (u - i);                       // sensor value, 0..127
  return Math.min(Math.max(Math.floor((v * (max + 1)) / 128), 0), max);
}
```
