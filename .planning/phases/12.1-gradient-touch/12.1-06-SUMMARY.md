# Phase 12.1 Plan 06: The fourth string on the wire Summary

**The one writer writes four strings in the order 255/6, 255/0, 0/6, 0/0 from an ordered slot list,
the one fetcher reads the same four in the same order, 255/4 is still never addressed and 255/6 is
addressed exactly once per install and first - and the constant that made 255/6 a wire fact is read
from the package, never typed.**

Band 2 started on `7fcc8e4` after `13-12-SUMMARY.md` existed and was read first. 13-12 left
`sequence.ts` byte-unchanged (it read `restorePageChange` and `targetOf`), `constants.ts` with
`PAGE_SWITCH_WINDOW_MS` added and the "WHY EVENTS 4 AND 6" header untouched, the fake ZONA's switch
model in `synthetic.ts`, and named this plan as the one to introduce `SLOTS`. **12.1-06 is now on the
tree, and 13-14 must not start until Band 2 (12.1-06, 07, 08) has landed** - 13-14 emits calls to the
library by name and asserts `library.ts` unchanged during its run, and it must consume 12.1's shape.

**No device was touched and nothing was deployed.** Every ZONA in this plan is `synthetic.ts`'s. The
four-write order on hardware is 12.1-08's two runbook rows (J and K, after 13-12's I). CAT-04 stays
`[ ]`.

### Task 02 - SLOTS, four writes, four fetches (`585e6cf`)

`SLOTS` as shipped, in `src/lib/transport/sequence.ts`:

```ts
export const SLOTS: readonly {
  readonly element: number;
  readonly event: number;
  readonly key: keyof ConfigSet;
  readonly label: FetchedEvent["label"];
  readonly write: StepId;
  readonly fetch: StepId;
  readonly refetch: StepId;
}[] = [
  { element: ELEMENT_SYSTEM, event: EVENT_TIMER, key: "systemTimer", label: "System timer", write: "write-system-timer", fetch: "fetch-system-timer", refetch: "refetch-system-timer" },
  { element: ELEMENT_SYSTEM, event: EVENT_SETUP, key: "system",      label: "System",       write: "write-system",       fetch: "fetch-system",       refetch: "refetch-system" },
  { element: ELEMENT_TOUCH,  event: EVENT_TIMER, key: "timer",       label: "Timer",        write: "write-timer",        fetch: "fetch-timer",        refetch: "refetch-timer" },
  { element: ELEMENT_TOUCH,  event: EVENT_SETUP, key: "setup",       label: "Setup",        write: "write-setup",        fetch: "fetch-setup",        refetch: "refetch-setup" },
];
```

(prettier lays each row out over nine lines in the file; the content is the above.) Every element and
event address is `ELEMENT_SYSTEM` / `ELEMENT_TOUCH` / `EVENT_SETUP` / `EVENT_TIMER` from
`constants.ts`, which reads them from the pinned package; no address is typed. The order and its rule,
as the comment above the list states them in three independent reasons:

1. **Reason one (Phase 12).** `grid_decode.c:1283-1288` registers a written body and runs it at once,
   so install-time initialisation order is HANGAR's; the touch Setup that calls the library must come
   after the system setup that defines it. Hence 255/0 before 0/6 and 0/0.
2. **Reason two (Phase 2).** `_pad.ts:3908-3913`: `gtt` is a no-op until the Timer holds an action and
   Setup runs immediately, so a Setup-first write arms a timer that does not exist. Hence 0/6 before
   0/0.
3. **Reason three (Phase 12.1, D-03) - reasons one and two together, one element up.** The library's
   second half lives in 255/6 and 255/0 arms it with `self:tim()`; a CONFIG/EXECUTE runs the body it
   registers, so a 255/0 written before 255/6 would arm a timer whose body is still the firmware's
   debug print, once, at install. Hence **255/6 first of all**, on the same rule that already puts
   0/6 before 0/0.

The rule reduces to a property the new test states: within each element the Timer precedes the Setup
that arms it, and the system element precedes the touch element that calls it. 13-17 adds 255/4 as one
row after 255/6 and before 0/6 (whatever the utility button's body calls has to be registered before
the body runs), edits the one `no 255/4 row` line, and nothing else in the test.

`ConfigSet` and `FetchedSet` gained `systemTimer`; `writeAll` is a `for (const slot of SLOTS)` over
`writeOne`, `fetchAll` the same over `fetchOne` with `stage` picking `slot.fetch` or `slot.refetch`;
`writeBack` builds the `ConfigSet` from the list; `runNoOpCycle` guards `SLOTS.map((slot) =>
before[slot.key])` and compares with `SLOTS.every(...)`. The three old rows' step ids and labels are
byte-unchanged, so `write-system` / `fetch-setup` / plan 05's gate still read the same strings.

**The four-write / four-fetch shape as asserted** (`sequence.spec.ts`, the order test and the `SLOTS`
test): the frames recorded by the fake, decoded back, are `[[255, 6], [255, 0], [0, 6], [0, 0]]` with
