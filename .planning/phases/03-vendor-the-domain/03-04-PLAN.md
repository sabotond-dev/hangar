<objective>
Pin the simulator against something that is not the simulator.

Wave 4. `depends_on` is semantic; executors run one plan per wave in the main tree, and the wave
number is the serial execution slot.

BOTOR's ported tests already carry firmware citations, but they were written by the same person who
wrote the simulator, so a misreading of the firmware would be transcribed identically into both and
the suite would be green and wrong. D-05 answers that with a second, independent derivation: an
agent that reads ONLY the firmware clone writes the oracle, and a different author writes the spec
that compares the vendored simulator against it. The independence is the deliverable, not a nicety.

D-08 governs disagreement: on a mismatch the task STOPS and reports the firmware citation, the
oracle value and the simulator value side by side. The oracle is never edited to match the
simulator, and the vendored copy is never patched locally - a fidelity bug is a BOTOR bug, fixed
upstream and re-synced.

Purpose: PREV-06, ROADMAP criterion 4; plus D-07's golden-frame tripwire.
Output: an independently derived oracle, a 7-test agreement spec, and an 11-test frame tripwire.
</objective>

**This is a tripwire, not an oracle.** It is derived from the simulator, so it can only prove that a
change to a shared helper altered a named preset's appearance. It proves nothing about firmware
fidelity - that is task 3-04-02's job. Say exactly that in a `note` field at the top of the JSON and

**Ticks: `[0, 37, 101, 500, 1009]`.** Not `[0, 64, 128, 500]`: measured, the frames at tick 0 and
